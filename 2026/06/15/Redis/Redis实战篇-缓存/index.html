Session共享问题

我们知道反向代理可以连接多个tomcat服务器，当用户访问的时候通过反向代理的负载均衡就会分配一个tomcat服务器来访问那么问题来了：每个tomcat中都有一份属于自己的session,假设用户第一次访问第一台tomcat，并且把自己的信息存放到第一台服务器的session中，但是第二次这个用户访问到了第二台tomcat，那么在第二台服务器上，肯定没有第一台服务器存放的session，所以此时 整个登录拦截功能就会出现问题，我们能如何解决这个问题呢？早期的方案是session拷贝，就是说虽然每个tomcat上都有不同的session，但是每当任意一台服务器的session修改时，都会同步给其他的Tomcat服务器的session，这样的话，就可以实现session的共享了

Session拷贝的两大问题：

  • 每台服务器中都有完整的一份session数据，服务器压力过大。
  • session拷贝数据时，可能会出现延迟。


根据图中替代方案我们可以采用的方案都是基于redis来完成，我们把session换成redis，redis数据本身就是共享的，就可以避免session共享的问题了。

商户查询缓存

什么是缓存

缓存就是数据交换的缓冲区(俗称Cache)，是存贮数据的临时地方，一般读写性能较高。缓存就是缓冲区内的数据,一般从数据库中获取,存储于本地代码

缓存数据存储于代码中,而代码运行在内存中,内存的读写性能远高于磁盘,缓存可以大大降低用户访问并发量带来的服务器读写压力（实际开发过程中,企业会大量运用到缓存技术）在浏览器、数据库、tomcat，CPU和磁盘都有缓存。

缓存更新策略

缓存更新是redis为了节约内存而设计出来的一个东西，主要是因为内存数据宝贵，当我们向redis插入太多数据，此时就可能会导致缓存中的数据过多，所以redis会对部分数据进行更新，或者把他叫为淘汰更合适。

根据上面我们知道只有当查询的数据在Redis没有的时候才会查询数据库，再把数据库中的该数据存到缓存中去。这时候有一个问题，当reids中一直有这个数据，而这个数据在数据库中被修改了，因为Redis缓存中有这个数据，那客户端请求返回的都是缓存中的数据，但是我们在数据库中已经修改了，这会导致数据不一致。所以我们需要缓存更新。

内存淘汰：全部由Redis自己去控制，我们不用管，缺点是reids内存未满的时候，他不会删除缓存所以一致性差。

超时剔除：他和数据库的一致性我们可以控制，TTL越短一致性越高。我们只需要设置TTL就行，所以维护成本低。

主动更新：是我们主动调用方法把缓存删掉。适合用于高一致性的场景。

主动更新策略

有如下常见的三种方案

Cache Aside Pattern ：是我们自己写代码，在更新数据库的同时更新缓存。

Read/Write Through Pattern：这个服务会自动维护一致性问题，但是他最大的问题是我们维护这个服务是非常复杂的。

Write Behind Caching Pattern：就是我们在缓存中执行怎删改查，然后有独立的线程，帮我们将缓存更新的数据写到数据库中。异步处理的效率也高。但是缓存是内存存储一旦宕机或者是断电就会将我们更新的数据丢失。可靠性有问题

解决数据库和缓存数据不一致

由于我们的缓存的数据源来自于数据库,而数据库的数据是会发生变化的,因此,如果当数据库中数据发生变化,而缓存却没有同步,此时就会有一致性问题存在,其后果是:

用户使用缓存中的过时数据,就会产生类似多线程数据安全问题,从而影响业务,产品口碑等;怎么解决呢？综上考虑我们使用方案一比较好。

但是还是有一些问题要考虑：

  • 更新缓存：这种方式是指在每次更新数据库的同时，也更新缓存中的数据。虽然可以保证缓存数据的实时性，但在高并发场景下，可能会导致大量的无效写操作。例如，在无用户访问时，多个请求几乎同时对同一个数据进行更新，可能会造成缓存更新的混乱和资源浪费。
  • 删除缓存：这种方式是指在更新数据库时，不立即更新缓存，而是将缓存中的对应数据删除或标记为失效。当下次有请求访问该数据时，发现缓存失效，再从数据库中读取最新数据并更新缓存。这种方式可以避免频繁的缓存更新操作，减少资源消耗，同时也保证了数据的一致性。在实际应用中，尤其是在面对高并发和大数据量的场景时，这种方式更为推荐，因为它能够更好地平衡缓存的时效性和系统性能。

缓存穿透

缓存穿透是指客户端请求的数据在缓存中和数据库中都不存在，这样缓存永远不会生效，这些请求都会打到数据库。

常见的解决方案有两种：

  • 缓存空对象
  • 布隆过滤

缓存空对象：

当我们客户端访问不存在的数据时，先请求redis，但是此时redis中没有数据，此时会访问到数据库，但是数据库中也没有数据，这个数据穿透了缓存，直击数据库，我们都知道数据库能够承载的并发不如redis这么高，如果大量的请求同时过来访问这种不存在的数据，这些请求就都会访问到数据库，简单的解决方案就是哪怕这个数据在数据库中也不存在，我们也把这个数据存入到redis中去，这样，下次用户过来访问这个不存在的数据，那么在redis中也能找到这个数据就不会进入到缓存了。

布隆过滤：

其实是一种算法。在客户端和Redis中加一个布隆过滤器，客户端的请求会先经过布隆过滤器。由布隆过滤器来判断这个请求数据是否存在，不存在则拒绝，存在则放行，请求会访问Redis，若Redis的数据过期，就访问数据库，因为布隆过滤器已经完成判别，数据库中一点存在这个数据。布隆过滤器的原理就是采用的是哈希思想来解决这个问题，通过一个庞大的二进制数组，走哈希思想去判断当前这个要查询的这个数据是否存在。

布隆过滤器不会像缓存空对象那样产生多余的key去存储不存在的数据，他的内存占用较少。但是布隆过滤器不一定准确，因为布隆过滤器走的是哈希思想，只要哈希思想，就可能存在哈希冲突,从而产生误判。并且实现复杂。

可以了解一下布隆过滤器的实现，也是一个考点

缓存雪崩

缓存雪崩是指在同一时段大量的缓存key同时失效或者Redis服务宕机，导致大量请求到达数据库，带来巨大压力。最严重的是Redis宕机。

解决方案：

  • 给不同的Key的TTL添加随机值，目的是不让大量的缓存key同时失效
  • 利用Redis集群提高服务的可用性
  • 给缓存业务添加降级限流策略
  • 给业务添加多级缓存，比如可以在nginx反向代理等设置缓存

缓存击穿

缓存击穿问题也叫热点Key问题，就是一个被高并发访问并且缓存重建业务较复杂的key突然失效了，无数的请求访问会在瞬间给数据库带来巨大的冲击。

缓存穿透问题的发生的原因：如上图假设线程1在查询缓存未命中后，去查询数据库重建缓存数据，但是因为这是一个缓存重建业务较复杂的数据，所以这一步执行的时间比较长，这个时刻如果有都多个线程都来访问这个数据，因为线程一并没有完成写入缓存，在缓存中查不到，那么无数多的请求都会打到数据库。

  • 重建缓存的触发场景：大多数是在缓存过期的时候，需重新查询数据库。

方案一互斥锁

假设线程一查询缓存未命中，那么他就会去查询数据库重建缓存，我们使用互斥锁的话，当它想要重建缓存的时候，他必须先获取锁，只有获取锁成功的，才可以进行缓存重建。写入缓存后才释放锁，释放锁之后其他的才可以获取锁。如线程二，他在线程一未释放锁的时候来了，所以他获取锁就会失败，那么它就会休眠一会再重新查询缓存，如果命中就会返回，如果未命中就会再次尝试获取锁，获取锁失败他就会再次重试，直到获取锁成功。这样保证了一个线程进行，其他的只能等待
，所以性能比较低。

互斥锁可以优化。可以网上搜一搜。

方案二逻辑过期

方案分析：我们之所以会出现这个缓存击穿问题，主要原因是在于我们对key设置了过期时间，假设我们不设置过期时间，其实就不会有缓存击穿的问题，但是不设置过期时间，这样数据不就一直占用我们内存了吗，我们可以采用逻辑过期方案。

逻辑过期顾名思义就是不是真的过期。而是再value中添加一个过期时间的字段。从而在查询缓存的时候我们需要根据过期时间字段来判断逻辑时间是否过期。即使逻辑过期了它也在缓存中存在。

假设线程一来查询缓存发现逻辑上已经过期，就会获得互斥锁，但是这里和方案一不同的是，重建缓存不是线程一干的事，而是开启一个独立的新的线程去做查询数据，缓存重建，写入缓存的操作。做完后由新线程释放锁，而线程一不会等线程二完成后再返回数据，而是直接返回过期的。如果在线程二未释放锁之前又来了一个线程，那么新来的线程获取锁就会失败它不会像方案一那样休眠，而是直接返回旧数据。线程二完成后其他线程来就会查询到新的数据。加互斥锁是为了确保在同一时刻，保证只有一个线程执行和线程一相同的流程。

这种方案巧妙在于，异步的构建缓存，缺点在于在构建完缓存之前，返回的都是脏数据。

互斥锁和逻辑过期的对比

互斥锁：由于保证了互斥性，所以数据一致，且实现简单，因为仅仅只需要加一把锁而已，也没其他的事情需要操心，所以没有额外的内存消耗，缺点在于有锁就有死锁问题的发生，且只能串行执行性能肯定受到影响

逻辑过期：线程读取过程中不需要等待，性能好，有一个额外的线程持有锁去进行重构数据，但是在重构数据完成前，其他的线程只能返回之前的数据导致数据不一致性，且实现起来麻烦

利用互斥锁解决缓存击穿

核心思路：相较于原来从缓存中查询不到数据后直接查询数据库而言，现在的方案是 进行查询之后，如果从缓存没有查询到数据，则进行互斥锁的获取，获取互斥锁后，判断是否获得到了锁，如果没有获得到，则休眠，过一会再进行尝试，直到获取到锁为止，才能进行查询。

获取到了锁的线程，才可以进行查询，查询后将数据写入redis，再释放锁，返回数据，利用互斥锁就能保证只有一个线程去执行操作数据库的逻辑，防止缓存击穿

互斥锁的实现核心思路就是利用redis的setnx方法来表示获取锁，该方法含义是redis中如果没有这个key，则插入成功，返回1，在stringRedisTemplate中返回true， 如果有这个key则插入失败，则返回0，在stringRedisTemplate返回false，我们可以通过true，或者是false，来表示是否有线程成功插入key，成功插入的key的线程我们认为他就是获得到锁的线程。释放锁就是将这个通过setnx创建的充当锁的key删除。我们还可以设置key的有效期，因为正常的业务一般都是在一秒种以内就完成了，设置有效期是为了防止某种异常，导致锁不能正常释放。
