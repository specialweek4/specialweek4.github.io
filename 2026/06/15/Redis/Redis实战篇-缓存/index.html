Session共享问题

我们知道反向代理可以连接多个tomcat服务器，当用户访问的时候通过反向代理的负载均衡就会分配一个tomcat服务器来访问那么问题来了：每个tomcat中都有一份属于自己的session,假设用户第一次访问第一台tomcat，并且把自己的信息存放到第一台服务器的session中，但是第二次这个用户访问到了第二台tomcat，那么在第二台服务器上，肯定没有第一台服务器存放的session，所以此时 整个登录拦截功能就会出现问题，我们能如何解决这个问题呢？早期的方案是session拷贝，就是说虽然每个tomcat上都有不同的session，但是每当任意一台服务器的session修改时，都会同步给其他的Tomcat服务器的session，这样的话，就可以实现session的共享了

Session拷贝的两大问题：

  • 每台服务器中都有完整的一份session数据，服务器压力过大。
  • session拷贝数据时，可能会出现延迟。


根据图中替代方案我们可以采用的方案都是基于redis来完成，我们把session换成redis，redis数据本身就是共享的，就可以避免session共享的问题了。

(1)key的设计

和Session不同的是每个手机号来访问的时候都是用的自己独立的Session他们的空间互不干扰，而使用Redis的话他们是共享一个Redis，所以我们需要确保不同手机号保存的key不同。发送短信时我们可以手机号为Key，验证码为value进行保存。但是不推荐以手机号为key进行存储。

设计key时要满足这两点：

  • key要保持唯一性
  • key要方便携带

商户查询缓存

什么是缓存

缓存就是数据交换的缓冲区(俗称Cache)，是存贮数据的临时地方，一般读写性能较高。缓存就是缓冲区内的数据,一般从数据库中获取,存储于本地代码

缓存数据存储于代码中,而代码运行在内存中,内存的读写性能远高于磁盘,缓存可以大大降低用户访问并发量带来的服务器读写压力（实际开发过程中,企业会大量运用到缓存技术）在浏览器、数据库、tomcat，CPU和磁盘都有缓存。

缓存的利弊

["{\"id\":1,\"name\":\"水果\"}", "{\"id\":2,\"name\":\"蔬菜\"}"]

对这个字符串解析：

  • 第1层（外壳）：这是 Java 的List集合toString()后自带的最外层数组标志，即 [ … ]。

  • 第2层（字符串边界）：Java 规定，凡是字符串类型，必须用一对双引号（” “）包起来。所以你看每个元素外面都有一对双引号。

  • 第3层（内部数据）：里面的 {id:1, name:”水果”} 本身又包含双引号（因为 JSON 的键和字符串值必须用双引号）。

如果不加\第2层和第3层都直接用双引号，Java 读到 “{“id”:1}” 时，读到 “{“ 后面的 id 就懵了，它会以为字符串在 { 处就结束了。

缓存更新策略

缓存更新是redis为了节约内存而设计出来的一个东西，主要是因为内存数据宝贵，当我们向redis插入太多数据，此时就可能会导致缓存中的数据过多，所以redis会对部分数据进行更新，或者把他叫为淘汰更合适。

根据上面我们知道只有当查询的数据在Redis没有的时候才会查询数据库，再把数据库中的该数据存到缓存中去。这时候有一个问题，当reids中一直有这个数据，而这个数据在数据库中被修改了，因为Redis缓存中有这个数据，那客户端请求返回的都是缓存中的数据，但是我们在数据库中已经修改了，这会导致数据不一致。所以我们需要缓存更新。

内存淘汰：全部由Redis自己去控制，我们不用管，缺点是reids内存未满的时候，他不会删除缓存所以一致性差。

超时剔除：他和数据库的一致性我们可以控制，TTL越短一致性越高。我们只需要设置TTL就行，所以维护成本低。

主动更新：是我们主动调用方法把缓存删掉。适合用于高一致性的场景。

主动更新策略

有如下常见的三种方案

Cache Aside Pattern ：是我们自己写代码，在更新数据库的同时更新缓存。

Read/Write Through Pattern：这个服务会自动维护一致性问题，但是他最大的问题是我们维护这个服务是非常复杂的。

Write Behind Caching Pattern：就是我们在缓存中执行怎删改查，然后有独立的线程，帮我们将缓存更新的数据写到数据库中。异步处理的效率也高。但是缓存是内存存储一旦宕机或者是断电就会将我们更新的数据丢失。可靠性有问题

解决数据库和缓存数据不一致

由于我们的缓存的数据源来自于数据库,而数据库的数据是会发生变化的,因此,如果当数据库中数据发生变化,而缓存却没有同步,此时就会有一致性问题存在,其后果是:

用户使用缓存中的过时数据,就会产生类似多线程数据安全问题,从而影响业务,产品口碑等;怎么解决呢？综上考虑我们使用方案一比较好。

但是还是有一些问题要考虑：

  • 更新缓存：这种方式是指在每次更新数据库的同时，也更新缓存中的数据。虽然可以保证缓存数据的实时性，但在高并发场景下，可能会导致大量的无效写操作。例如，在无用户访问时，多个请求几乎同时对同一个数据进行更新，可能会造成缓存更新的混乱和资源浪费。
  • 删除缓存：这种方式是指在更新数据库时，不立即更新缓存，而是将缓存中的对应数据删除或标记为失效。当下次有请求访问该数据时，发现缓存失效，再从数据库中读取最新数据并更新缓存。这种方式可以避免频繁的缓存更新操作，减少资源消耗，同时也保证了数据的一致性。在实际应用中，尤其是在面对高并发和大数据量的场景时，这种方式更为推荐，因为它能够更好地平衡缓存的时效性和系统性能。

因为我们没有加锁，所以两个线程是可以并行的，第一个线程的任务是删除缓存，然后更新数据库。第二个线程是1.查询缓存，未命中就查询数据库。2.写入缓存。如果在线程一执行删除缓存后线程二就来了，查询数据库此时的数据库是还没有更新，那么就会把旧数据写入缓存中，最后线程一更新数据库，就会导致数据库和缓存数据不一致。

图中的第二种方案展示的也是异常情况，当查询的数据在缓存中失效的时候，线程一来了查询未命中就查询数据库此时查询的是旧数据，然后线程二再更新数据库，删除缓存后，线程一不知道数据库已经更改，写入缓存的数据还是旧数据。

  • 但是这种情况发生的概率极低，因为对缓存的操作的速度是要远远的高于数据库的，基本上在执行更新数据库完成之前，写入缓存的操作已经执行好了。即使发生了我们可以给缓存设置超时时间，将错误缓存删除。

综上我们选择先写数据库，再删缓存
