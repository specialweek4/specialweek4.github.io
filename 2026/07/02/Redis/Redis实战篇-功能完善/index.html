关注推送(Feed流)

关注推送也叫做Feed流，直译为投喂。为用户持续的提供“沉浸式”的体验，通过无限下拉刷新获取新的信息。

对于传统的模式的内容解锁：我们是需要用户去通过搜索引擎或是其他的方式去解锁想要看的内容

对于新型的Feed流的的效果：不需要我们用户再去推送信息，而是系统分析用户到底想要什么，然后直接把内容推送给用户，从而使用户能够更加的节约时间，不用主动去寻找

Feed流的实现方式：

  • TimeLine：不做内容筛选，简单的按照内容发布时间排序，常用于好友或关注。例如微信朋友圈
  1. 优点：信息全面，不会有缺失。并且实现也相对简单
  2. 缺点: 信息噪音较多，用户不一定感兴趣，内容获取效率低
  • 智能排序: 利用智能算法屏蔽掉违规的、用户不感兴趣的内容。推送用户感兴趣信息来吸引用户
  1. 优点：投喂用户感兴趣信息，用户粘度很高，容易沉迷
  2. 缺点：如果算法不精准，可能起到反作用 本例中的个人页面，是基于关注的好友来做Feed流，因此采用Timeline的模式。

三种实现方案：

我们本次针对好友的操作，采用的就是Timeline的方式，只需要拿到我们关注用户的信息，然后按照时间排序即可，因此采用Timeline的模式。该模式的实现方案有三种：

  1. 拉模式
  2. 推模式
  3. 推拉结合

拉模式

该模式也叫读扩散

该模式的核心在于：张三、李四和王五发布消息后，各自保存至其邮箱。当赵六欲读取消息时，系统会从赵六关注的用户中拉取消息并排序展示。

  • 优点：节约存储空间。赵六读取时无重复数据读取，且读取后可清空收件箱，有效节省存储资源。
  • 缺点：数据读取存在延迟。系统需在用户读取时才从其关注的用户处拉取数据。若用户关注人数众多，将导致大量数据的读取，对服务器造成较大压力。

推模式（写扩散）

该模式的核心在于：当张三发布内容时，系统会主动将该内容推送到张三粉丝的收件箱中。这样，当李四查看信息时，可以直接从自己的收件箱获取，无需临时拉取。

  • 优点：实时性高，用户体验好，因为内容已经提前推送到了粉丝的收件箱，粉丝查看时无需等待临时拉取。
  • 缺点：存储压力大。尤其是当大V发布内容时，需要向大量粉丝推送，会导致数据冗余，占用较多存储空间。

推拉结合（读写混合）

兼具推和拉两种模式的优点。

站在发件人的角度：

  • 对于普通用户，由于粉丝数量较少，采用推模式，直接将内容写入粉丝的收件箱，这样操作压力小。
  • 对于大V用户，因粉丝众多，仅将内容写入自己的发件箱，同时仅向活跃粉丝的收件箱推送一份内容。

站在收件人的角度：

  • 活跃粉丝无论是对普通用户还是大V的关注，其收件箱都会直接收到内容。
  • 普通粉丝因不常上线，内容不会提前写入其收件箱。待其上线时，系统再从发件人的发件箱拉取内容。

BitMap的操作命令有：

  • SETBIT：向指定位置（offset）存入一个0或1
  • GETBIT ：获取指定位置（offset）的bit值
  • BITCOUNT ：统计BitMap中值为1的bit位的数量
  • BITFIELD ：操作（查询、修改、自增）BitMap中bit数组中的指定位置（offset）的值
  • BITFIELD_RO ：获取BitMap中bit数组，并以十进制形式返回
  • BITOP ：将多个BitMap的结果做位运算（与 、或、异或）
  • BITPOS ：查找bit数组中指定范围内第一个0或1出现的位置
如：BITFIELD bm1 GET u3 0：在bm1中从第0位开始查询3位，u代表返回不带符号。

签到统计

问题1：连续签到天数的定义

连续签到天数是指从最后一次签到的那一天开始，往前数直到遇到第一次未签到的那一天为止，这中间签到的总天数。

要统计当前用户在本月的连续签到天数，可以按照以下步骤进行：

(1)获取当前用户本月的签到数据：

  1. 使用 Redis 的 BITFIELD 命令获取从月初到当前日期的所有签到记录。
  2. 假设今天是10号，那么获取1号到10号的签到数据。

(2)定义一个计数器：

  • 初始化一个计数器 count 为0，用于记录连续签到的天数。

(3)从当前日期向前遍历：

  1. 从当前日期开始，逐天检查签到记录，直到遇到未签到的那一天为止。
  2. 每遇到一个签到的记录（即该位为1），计数器加1。

(4)返回计数器的值：

  • 最终计数器的值即为连续签到天数。

问题二 如何得到本月到今天为止的所有签到数据

使用 Redis 的 BITFIELD 命令获取从月初到当前日期的所有签到记录（统计1的个数） BITFIELD key GET u[dayOfMonth] 0;

问题三 如何从后向前遍历每个bit位

(1)获取签到记录：

  1. 使用 BITFIELD 命令获取签到记录，结果是一个十进制数字。
  2. 假设返回的数字是 num。

(2)遍历每一位：

  1. 从最低位开始，逐位检查是否为1。
  2. 使用位运算 num & 1 检查最低位是否为1。
  3. 如果为1，计数器加1，并右移一位继续检查下一个位。
  4. 如果为0，结束循环。

UV统计

HyperLogLog介绍

  • UV：全称Unique Visitor，也叫独立访客量，是指通过互联网访问、浏览这个网页的自然人。(1天内同一个用户多次访问该网站，只记录1次)
  • PV：全称Page View，也叫页面访问量或点击量，用户每访问网站的一个页面，记录1次PV，用户多次打开页面，则记录多次PV。这个数据通常用来衡量网站的流量。
  • 通常来说PV会比UV大很多，所以衡量同一个网站的访问量，我们需要综合考虑很多因素，所以我们只是单纯的把这两个值作为一个参考值

在进行独立访客（UV）统计时，若将每位访问用户的标识直接存入 Redis，数据量可能极为庞大。此时，可采用 Hyperloglog（HLL）算法加以优化

HLL 是一种基于概率统计的算法，能够高效估算大型数据集的基数，且无需存储全部数据值。在 Redis 中，HLL 基于字符串结构实现，单个 HLL 的内存占用始终低于 16 KB，具有极高的内存效率。

虽然 HLL 的统计结果存在误差，但对于 UV 统计这类对精度要求不苛刻的场景而言，这一误差(0.81%)可以忽略不计。
