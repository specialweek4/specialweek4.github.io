登录注册

发表于2026-07-07|更新于2026-07-19|知光

在知光APP中，采用 Spring Security + JWT 的双令牌机制，将短期的 accessToken 与长期的 refreshToken 分离：

  • accessToken 负责高性能、无状态的接口访问认证
  • refreshToken 负责长期会话的续期与控制。

这样既提升了账号安全性（缩小单次泄露的影响范围、支持强制下线与风控），又保证了用户的长期免登录体验，同时兼顾了分布式架构下的扩展性和会话管理能力。

什么是双令牌

accessToken（访问令牌）

  • 作用：
    每次访问业务接口时，用来证明“我是某某用户”。
    比如你现在的 Authorization: Bearer xxx 就是 accessToken。

  • 特点：

    • 有效期 很短（比如 15 分钟、30 分钟）。
    • 内部自带用户 ID、角色、权限等信息（JWT 的 payload）。
    • 后端 只需要校验签名和是否过期，一般不查数据库，性能好、扩展性强。

  • 使用方式：
    前端每次调 /api/v1/xxx 时带上它用以权限认证。

refreshToken（刷新令牌）

  • 作用：
    不直接访问业务接口，只用来 换取新的 accessToken。
    当前 accessToken 过期了，前端拿 refreshToken 调 /auth/refresh 这种接口，就能拿到一对新的 accessToken + refreshToken。
  • 特点：
    • 有效期 较长（比如 7 天、14 天甚至 30 天）。
    • 一般只在少数几个认证接口使用：/login、/refresh。
    • 可以结合 Redis / 数据库 做黑名单、版本号等控制（更容易做“踢下线”“注销”）。

为什么要用双令牌，而不是一个长有效期的 token？

（1）安全性更高

如果只有一个长生命周期的 JWT：

  • 比如你设一个 JWT 直接 30 天不过期，一旦这个 token 被窃取，黑客可以在 30 天内随便伪装成用户操作，风险非常大。
  • 又因为 JWT 一般是“无状态”的，后端默认不会存储、也不回收，因此很难“立刻让这个 token 失效”。
    双令牌的改进：
  • accessToken 只活 15~30 分钟 —— 即使被盗，黑客最多用这一小段时间。
  • refreshToken 一般只在“刷新接口”使用，你可以：
    • 把 refreshToken 保存得更安全（比如 HttpOnly Cookie、只在后端存一份、只允许 HTTPS）。
    • 针对 refreshToken 做更严格检查：设备信息、IP、User-Agent、单点登录等。
  • 一旦发现泄露或用户手动“退出登录”，直接把对应的 refreshToken 在 Redis 标记失效：
    • 老的 refreshToken 无法再换新 token；
    • accessToken 也会因为短时过期，自然失效；
    • 这样就实现“可控的强制下线”。

短命的 accessToken + 受控的 refreshToken，比一个长命 JWT 安全得多。

（2）提升用户体验（减少频繁登录）

（3）兼顾“无状态扩展性”和“可控的登录状态”

  • accessToken 校验可以完全无状态（只靠签名+过期时间），非常适合分布式，集群部署：
    • 任意一个服务实例都能根据 JWT 自己完成认证。
  • refreshToken 可以是 “轻状态” 的：
    • 把 refreshToken ID 存到 Redis；
    • 可以做：
      • 单点登录（同一用户只允许一个刷新 token 生效）；
      • 踢人下线（删除某个 refreshToken 记录）；
      • 安全风控（记录设备、IP，异常则禁止刷新）。
        这样就可以做到：
  • 业务接口层（多服务）只管校验 accessToken，不查库，性能高；
  • 认证中心 / 网关 少量存 refreshToken 的状态，用来集中管理登录会话，引入“可控的在线状态”。

下发令牌思路

密钥的准备：AuthConfiguration 初始化编码器。JwtEncoder 的实现类是 NimbusJwtEncoder，它在 AuthConfiguration 中被创建：

  • PemUtils 从 PEM 文件解析出 RSAPrivateKey和 RSAPublicKey 。
  • 使用 Nimbus 的 RSAKey.Builder 构建一个 JWK，同时包含公钥和私钥（私钥用于签名，公钥嵌入 JWK）。
  • 将 JWK 放入不可变的 JWKSource，传给 NimbusJwtEncoder。此后所有编码操作都由该编码器完成。

1.令牌在两种场景下发：

  1. 登录成功：AuthController.login() → AuthService.login()
  2. 注册成功：AuthController.register() → AuthService.register()

这两个方法最终都会调用 JwtService.issueTokenPair(user) 来生成令牌对。

2.JwtService.issueTokenPair() 核心逻辑

3.生成访问令牌 (encodeToken)

调用 JwtEncoder 生成 JWT 字符串，其 声明 (claims) 包括：

  • iss：签发者，配置为 zhiguang
  • sub：用户ID
  • iat：签发时间
  • exp：过期时间（AccessToken 默认 15 分钟）
  • jti：令牌唯一 ID（UUID）
  • token_type：固定为 “access”
  • uid：用户ID（方便业务服务直接取用）
  • nickname：用户昵称

4.生成刷新令牌 (encodeRefreshToken)

  • 与访问令牌类似，区别在于：
  • token_type 固定为 “refresh”
  • 不包含 nickname（刷新令牌仅用于获取新令牌，无需业务信息）
  • jti 使用的是预先生成的 refreshTokenId（后续要存入白名单）

两种令牌都进行签名，签名所依赖的私钥来自 PemUtils.readPrivateKey()。

5.签名过程（了解即可）

NimbusJwtEncoder 会：

  • 将 JwtClaimsSet 转换为 Nimbus 的 JWTClaimsSet；
  • 使用 RSA 私钥 + SHA-256 生成签名；
  • 输出标准的 header.payload.signature 格式 JWT 字符串

在令牌生成的时

JwtClaimsSet 传入 JwtEncoderParameters，然后调用 jwtEncoder.encode(…)。

  • 在 NimbusJwtEncoder 内部，大致流程如下：
  • 从 JWKSource 中选择合适的 JWK（这里是唯一一个，根据算法或 kid 选择）。
  • 提取私钥 RSAPrivateKey。
  • 将 Spring 的 JwtClaimsSet 转换为 Nimbus 的 JWTClaimsSet。
  • 创建 SignedJWT 对象，设置头部（包括 alg=RS256 和 kid=zhiguang-key）。
  • 使用 RSASSASigner，结合私钥对 Header.Payload 进行 SHA-256 哈希并用 RSA 私钥签名，生成签名部分。

最终输出三部分用点号分隔的完整 JWT 字符串：header.payload.signature。

6.返回给客户端

最终 JwtService 返回一个 TokenPair 对象，包含：

  • accessToken
  • accessTokenExpiresAt
  • refreshToken
  • refreshTokenExpiresAt
  • refreshTokenId（不会暴露给客户端）

在控制器中，TokenPair 被映射为 TokenResponse（只包含客户端需要的4个字段）：

7.刷新令牌的特殊处理

普通令牌仅需返回给客户端即可，但刷新令牌还需要额外存入 白名单 (RefreshTokenStore)，以便后续校验有效性。

在 AuthService 中，签发令牌后立即执行：

storeRefreshToken 计算刷新令牌的剩余有效时长，然后调用 RefreshTokenStore.storeToken() 写入 Redis：

  • Key：auth:rt:{userId}:{tokenId}
  • Value：”1”
  • TTL：与刷新令牌的过期时间一致

这样：

  • 刷新令牌只有在白名单中且未过期时才被认为有效；
  • 登出或重置密码时可以主动撤销（删除 Key）；
  • 轮换新令牌时，旧刷新令牌会被删除，新令牌写入。

验证码思路

一、验证码生成

在 VerificationService 中：

  • 使用 SecureRandom 生成指定长度（配置的 codeLength，默认 6 位）的纯数字字符串。
  • 生成后进入发送与存储阶段。

二、验证码的发送

通过 CodeSender 接口定义发送行为，当前使用的实现是 LoggingCodeSender（仅打印日志，不真实发送）。生产环境可替换为对接短信/邮件服务商。

三、验证码的存储与过期时间

1.存储实现：RedisVerificationCodeStore(存储到Redis中)

在 RedisVerificationCodeStore.saveCode() 中：

  • 数据结构：Redis Hash，一个 Key 包含三个字段：code、maxAttempts、attempts。
  • 过期时间：直接使用 redisTemplate.expire(key, ttl) 设置整个 Hash Key 的 TTL（来自配置 verification.ttl，默认 5 分钟）。到期后 Redis 自动删除该 Key，验证码即失效。

四、验证码的校验

业务层调用 verificationService.verify(scene, identifier, code)，最终委托给 RedisVerificationCodeStore.verify()：

校验逻辑

  1. 读取 Redis Hash 的所有字段。
  2. 若 Key 不存在（已被 TTL 过期或从未发送），返回 NOT_FOUND。
  3. 取出 maxAttempts 和 attempts，若已尝试次数 ≥ 最大次数，返回 TOO_MANY_ATTEMPTS。
  4. 比对验证码是否一致：
  • 成功：立即删除 Redis 中的 Key（防止重用），返回 SUCCESS。
  • 失败：attempts + 1 写回 Redis。
    • 若更新后达到 maxAttempts，延长 Key 的 TTL 为 30 分钟（防止攻击者快速重试），返回 TOO_MANY_ATTEMPTS。
    • 否则返回 MISMATCH。

五、附加的速率限制（使用独立的 Redis Key）

VerificationService 还实现了 发送间隔 和 每日上限，它们也基于 Redis 的过期时间：

  1. 发送间隔
  • Key 的有效期就是 sendInterval（默认 60 秒），存在时拒绝发送。
  1. 每日上限
  • 计数器 Key 过期时间为 1 天，利用 Redis 原子递增实现每日限制

项目中是如何对接口鉴权的？

(1)令牌提取与验证

Spring Security 通过 oauth2ResourceServer().jwt() 自动装配一个

BearerTokenAuthenticationFilter，拦截请求执行：

  • 从 Authorization: Bearer token 头中提取 JWT 字符串；
  • 调用自定义的 JwtDecoder（基于 RSA 公钥的 NimbusJwtDecoder）进行验证：
  • 解析 Header、Payload、Signature；
  • 用公钥验证 RS256 签名(就是通过RSA私钥签的名)；
  • 检查 exp(令牌) 是否过期
    验证通过后返回一个 Jwt 对象，包含所有 claims。

(2)授权决策

在 authorizeHttpRequests 中配置的匹配规则决定了哪些请求无需认证即可访问：

  • 完全公开：健康检查、认证相关接口、知文内容浏览等。
  • 必须认证：除上述公开路径外的所有请求（anyRequest().authenticated()）。

决策发生在认证之后：若请求路径属于 permitAll()，直接放行；若属于 authenticated()，检查 SecurityContext 中是否有已认证的 Authentication 对象，有则放行，无则返回 401。

总结：项目使用 Spring Security 资源服务器模式，依靠 RSA 公钥对 JWT 进行无状态验证，配合 URL 白名单公开部分接口，其余全部要求认证；身份信息（userId）从 JWT 的 uid 声明中获取，确保了轻量、可扩展的鉴权体系。

PasswordEncoder可以理解是一个密码加工器

  • 作用1：加密（更准确叫“哈希”）
    用户注册时，你把明文密码（比如123456）喂给它，它吐出一串谁也看不懂的乱码（比如$2a$10$…），存进数据库。

  • 作用2：比对
    用户登录时，它把这次输入的密码和库里那串乱码比较，告诉你“对”还是“不对”，全程不需要把存进去的乱码还原成明文——实际上也还原不了，这就是“不可逆加密”。

BCrypt 是它肚子里一种专门用来腌密码的算法，有两个天生优势：

  • 自动加“盐”：每次加密都会随机撒一把不同的“调料”（盐），这样即使用户密码相同（比如都叫123456），生成的乱码也完全不同，防止黑客用彩虹表撞库。

  • 故意变慢：它不是嗖的一下算完，而是故意耗点时间。这么做是为了恶心暴力破解的人——你正常登录等0.1秒完全没感觉，但黑客想短时间试几亿个密码就根本跑不动。

根据配置的 BCrypt 强度创建这里的“强度”是指“故意慢到什么程度”

强度 10 → 就是 2¹⁰ = 1024 次哈希搅拌

强度 12 → 就是 2¹² = 4096 次搅拌

JWT（JSON Web Token）是一张“电子通行证”，里面写了“谁、能干嘛、什么时候过期”。

在项目里，JWT 最常见的用途就是登录后的身份凭证。 你登录后，服务器发你一个 JWT，之后的请求你带着它，服务器只验证签名和有效期，不需要再去查数据库，就能知道你是谁，这叫“无状态认证”。

JWK（JSON Web Key）是一把“验证通行证真伪的公钥”的标准化描述。

Spring Security 安全配置类

(1)关闭 CSRF

  • CSRF（跨站请求伪造） 原本是防这种攻击的：你登录了银行网站，然后又点了一个恶意链接，那个链接可能偷偷用你的身份发起转账。传统防护是在表单里藏一个随机 Token。
  • 后端是纯 API，用 JWT 做身份验证，不依赖浏览器的 Cookie 会话。每次请求都必须在 Header 里带 Token，恶意站点根本无法伪造。所以 CSRF 防护就多余了，直接关掉。

(2)启用 CORS，当前允许所有来源

  • CORS（跨域资源共享） 是浏览器的一种安全机制：默认情况下，在 http://localhost:3000 跑的前端页面，不能直接请求 http://api.example.com 的接口，因为域名不同（跨域）。
  • 这里开启 CORS 并暂时允许所有来源，意味着任何前端地址都能调我的接口,但后续项目上线后需要替换白名单。

(3)无状态会话

  • 传统 Web 应用会在服务器内存里存一个 Session，记录你的登录状态，每次请求靠 Cookie 里的 Session ID 来查。
  • 这里不存了，完全无状态。因为登录后服务器给你一个 JWT，你每次请求带着它就行。服务器不记你，只验 JWT 的真伪和有效期，验过就认为你是合法用户。这样做的好处是容易水平扩展，不用共享 Session。

(4)公开认证相关接口与健康检查，其余接口需鉴权

  • 就是登录,查看首页等操作直接放行。

(5)资源服务器启用 JWT 校验

  • Spring Security 会配置好对应的过滤器，从我们上面配置的 JWK 地址或本地公钥获取验证密钥，检查 JWT 的签名、有效期等，都通过了解析出用户权限，注入到安全上下文中。

认证业务服务 AuthService.java

核心流程：

  1. 发送验证码

校验标识格式 → 检查存在性是否符合场景（注册需不存在，登录/重置密码需存在） → 调用发送服务 → 返回过期信息。

  1. 注册

检查协议同意 → 标识格式与是否存在校验 → 验证码确认 → 构建用户（密码加密） → 创建用户 → 签发令牌对（Access/Refresh JWT） → 白名单存储刷新令牌 → 记录注册审计日志。

  1. 登录

标识格式与存在性校验 → 选择通道（密码需比对加密密码，验证码需校验） → 签发令牌对 → 白名单存储刷新令牌 → 记录登录审计日志。

  1. 刷新令牌

解析(解码调用JwtService.decode -> jwtDecoder.decode)并验证 refresh token 类型 → 从白名单检查有效性 → 根据 ID 找到用户 → 签发新令牌对 → 撤销旧刷新令牌并存储新令牌。

  1. 登出

安全解析 refresh token → 若是合法 refresh 令牌 → 撤销其白名单记录。

  1. 重置密码

标识格式与密码策略校验 → 校验验证码 → 更新密码（加密） → 撤销该用户所有刷新令牌。

  1. 查询当前用户

根据用户 ID 查库 → 映射为 DTO 返回。

辅助机制：

统一使用 BCrypt 密码加密；

验证码采用状态机逻辑（未找到、过期、错误、尝试超限）；

刷新令牌基于白名单存储，支持轮换与防重放；

审计覆盖注册/登录成功与失败，记录渠道、IP、UA。
