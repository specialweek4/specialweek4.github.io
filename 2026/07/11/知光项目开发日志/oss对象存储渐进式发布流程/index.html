oss对象存储and渐进式发布流程

发表于2026-07-11|更新于2026-07-20|知光

技术亮点：

  1. 客户端直传：不采用服务器中转，而是采用直传的方式降低服务器压力，提升上传效率
  2. 状态机设计：清晰的发布状态流转，支持中断恢复
  3. 幂等保证：所有操作可重试，提升系统健壮性
  4. 完整性校验：多层校验确保数据安全

架构价值：

  1. 支持大文件上传不中断
  2. 提供良好的用户体验
  3. 降低系统运维成本
  4. 便于扩展和故障排查

核心设计思想

编辑时预创建记录→发布后补全OSS信息

传统的”一键发布”模式存在几个痛点：

  • 上传失败风险：大文件上传中断导致内容丢失
  • 用户体验差：长时间等待上传完成
  • 服务器压力：所有流量经过后端，造成瓶颈
  • 并发冲突：多用户同时发布资源竞争

数据库表设计

渐进式发布采用分阶段、可中断、状态化的设计，将发布过程分解为6个原子操作：

详细流程解析

阶段1：创建草稿实例

在知文发布模块中

技术要点：

  • 使用雪花算法生成分布式唯一ID
  • 立即返回草稿ID，避免用户等待
  • 数据库中创建status=’draft’的记录
  • 为后续操作提供上下文标识

阶段2：预签名URL申请

安全设计：

  • 服务端生成PUT预签名URL有效期仅10分钟，防止滥用
  • 生成OSS对象键objectKey包含 postId（该用户的草稿/知文id） 前缀，实现 OSS 存储租户隔离
  • 服务端校验前缀格式，防止越权访问

阶段3：前端直传到 OSS

性能优势：

  • 直接上传到阿里云OSS，不经过应用服务器
  • OSS天生支持断点续传和分片上传

阶段4：内容确认与校验

完整性保障：

  • ETag 校验：确保传输完整性
  • SHA-256 校验：防篡改，提供强一致性sha256 是前端在浏览器中，读取用户选择的文件内容，通过 SHA-256 算法计算出的一个固定长度（64 位十六进制）的哈希字符串,它和 etag、size(文件大小) 一起，用来多重验证上传文件的完整性和正确性。

阶段5：元数据完善

灵活性设计：

  • 正文保存到oss中，标题啥的通过元数据持久化保存到Redis和数据库中。
  • PATCH语义：仅更新提交的字段
  • JSON数组存储：tags、imgUrls支持多值
  • 可见性控制：支持多种隐私级别
  • 置顶功能：重要内容优先展示

阶段6：正式发布

发布逻辑：

  • 状态变更：draft → published(从草稿状态变成已发布状态)
  • 时间戳记录：publish_time = CURRENT_TIMESTAMP
  • 事件触发：异步更新Feed流索引
  • 缓存刷新：清除相关缓存条目

“发布”这个动作只是改变状态（draft → published），同时触发缓存刷新、索引预热等副作用。
在发布之前，内容可以反复修改、上传替换，都不会对外可见；发布之后，内容才进入公开 Feed。：

什么是渐进式发布？

渐进式发布是一种将内容创作流程拆分为多个独立的、可中断的步骤，允许用户逐步完成并持久化中间状态，最终在某个时机一次性“上线”的设计模式。

  • 元数据编辑（PATCH /{id}）：随时修改标题、标签、可见性等。
  • 内容上传（预签名直传 + POST /{id}/content/confirm）：将正文文件传到 OSS 并登记信息。
  • 图片上传（预签名直传）：图片可以随时增删，imgUrls 列表在元数据中维护。
  • 最终发布（可能是一个 POST /{id}/publish 接口，将草稿状态改为已发布）。

每个阶段都是独立的 API，可以按任意顺序、任意时间间隔进行，不用在一个请求里做完所有事。

优势

(1)状态机管理

就是判断当前的状态，在草稿和已发布的状态之间可以重复编辑，发布后可以隐藏或者删除。

(2)幂等性保证

  • 所有接口支持重复调用
  • 重复发布无副作用
    • 将 status 字段从 DRAFT 改为 PUBLISHED。这种状态切换是幂等的，重复调用不会产生“重复发布”的问题：
    • 第一次：DRAFT -> PUBLISHED（成功）
    • 第二次：PUBLISHED -> PUBLISHED（更新计数为 0，不影响任何业务）
  • 中断后可从任意阶段恢复
    • 因为上面的每个阶段都是独立的幂等，用户每次修改正文内容，都需要触发一次完整的上传流程，即使没有上传成功，也可以重新请求一次预签名 URL，再传一次文件即可。只要草稿 ID 不变，最终确认时的 objectKey 会正确指向新上传的文件。旧的半截上传资源会被 OSS 自动丢弃（或由生命周期策略清理）。

用户在任何一步中断（例如断网、浏览器崩溃）后，都可以无缝继续：

  • 元数据写了，但内容没传：下次打开编辑器，可以接着传内容，上传成功后调用 confirmContent。
  • 内容传了，但 confirmContent 没调：可以重新调用 confirmContent，数据库里会补上文件信息（甚至可以设计一个“继续编辑”接口，返回当前已上传的 objectKey，让前端判断是否要重新传）。
  • 图片传了一半：已上传的图片 URL 如果已经加到了 imgUrls 并调了元数据更新，那就已经保存下来了；如果没调用元数据更新，那图片就只在 OSS 上，前端可以重新选择图片（或继续引用已经存在的 URL）。
  • 整个流程中断后：用户再次打开帖子，系统可以查出已有的元数据和 contentObjectKey，展示“已上传的草稿”，允许从当前进度继续编辑。

配合缓存双删，即使重复发布，Feed 流和详情缓存也会被及时清理，不会出现脏读。

生成预签名

预签名主要是为了安全和节省服务器资源而设计的。

第 1 步：前端发起预签名请求

  • 用户在前端选中文件后，不直接上传，而是先调用后端接口 POST /api/v1/storage/presign，带上请求体：

对应的请求体就是定义的 StoragePresignRequest record

第 2 步：Controller 层处理请求并鉴权

1.提取用户身份

- 通过 @AuthenticationPrincipal Jwt jwt 获取当前登录用户的 JWT，调用 jwtService.extractUserId(jwt) 得到 userId

2.校验 postId 合法性及归属

  • 将字符串 postId 转为 long（前端传字符串是为了避免 JavaScript 精度丢失）。
  • 从数据库查出该 postId 对应的 KnowPost。
  • 判断帖子是否存在、是否有创建者，且创建者 ID 必须等于当前登录用户 ID。是防止用户 A 往用户 B 的帖子上传文件。

3.根据 scene 生成 OSS 对象键 (objectKey)，也就是存储路径

  • knowpost_content：路径固定为 posts/{postId}/content{ext}，例如 posts/123/content.md。
  • knowpost_image：路径带日期和随机串，如 posts/123/images/20240315/a1b2c3d4.png，避免重名覆盖。

扩展名 ext 优先取请求中的，若无则根据 contentType 推断（例如 image/png -> .png）

4.调用 OSS 服务层generatePresignedPutUrl方法生成预签名 URL

  • 传入 objectKey、contentType 和有效期 600 秒。

第 3 步：前端直传 OSS

前端收到响应后，用返回的 putUrl 和 headers 直接向阿里云 OSS 发起 HTTP PUT 请求。OSS 收到请求后，会验证签名、有效期，把偶才能文件后会返回前端一个Etag，ETag 本质上是文件内容的哈希值。

第 4 步服务器检验上传完整性

  1. sha256 是由文件原始内容唯一决定的哈希值。

  2. 当以后需要下载或使用这个文件时，可以重新计算一次哈希，和数据库中的 sha256 对比，完全一致就说明文件在 OSS 上没有被损坏或篡改。

  3. 这也比单纯依赖 OSS 的 etag 更可靠（因为 etag 不一定是文件整体 MD5，分片上传时尤其复杂）。

所以说看ETag能够判断传输的完整性，看SHA-256：可以看文件是否被篡改，提供强一致性

  1. 不修改内容，重复上传的话sha256和etag都不会变。

第6步：元数据完善

PATCH /{id} 它只更新元数据（标题，图片啥的），完全不碰正文内容，非常轻量。

问题：如果文件已经上传到OSS了，又修改了元数据怎么办

  1. 元数据和文件是分离存储的
  • 文件实体（图片、Markdown 正文）存储在 OSS，由 objectKey 唯一标识。
  • 元数据（标题、标签、可见性、图片列表等）存储在数据库（know_post 表）里。

当你调用 PATCH /{id} 修改元数据时，系统只做了一件事：更新数据库字段，并清除相关缓存。它完全不动 OSS 上的文件。文件依然可以通过原来的 objectKey 访问。

  1. 如果修改了 imgUrls（图片列表）
  • 元数据里的 imgUrls 是前端在编辑帖子时插入的图片地址列表。如果用户删除了某张图片：
    • 数据库 imgUrls 字段会更新，不再包含那张图的 URL。
    • 但那张图片在 OSS 上并不会自动删除。它依然可以通过直接访问 URL 看到，只是不显示在帖子详情中。

这是一种常见的设计，避免误删导致数据丢失。如果需要彻底清除垃圾图片，通常会通过定期清理任务来删除未被任何帖子引用的 OSS 文件。
