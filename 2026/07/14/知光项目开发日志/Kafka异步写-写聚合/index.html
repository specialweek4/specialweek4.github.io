Kafka异步写 + 写聚合

发表于2026-07-14|更新于2026-07-14|知光

方案背景：高并发行为计数的核心痛点

在社交、电商等高频交互场景中，用户的点赞（like）、收藏（fav）、评论等行为会产生海量计数更新请求。

“同步直写最终计数”的方案在高并发下暴露诸多致命问题，成为系统性能瓶颈，具体可归纳为三大核心痛点：

(一)写热点与写放大问题突出

  • 1.高频细粒度写入引发热点压力：用户每一次行为操作都直接写入最终计数存储，形成高频次、细粒度的写请求。热门实体（如爆款帖子、大V）的计数键会成为“热点行”，集中占用存储节点的CPU、IO资源，导致响应延迟飙升。
    • 问题本质：每一次用户行为（点赞、收藏）都转化为一条对存储的写命令，直接更新某个实体的总计数。
      比如用户给帖子 article:123 点赞，传统做法可能是执行 INCR like_count:article:123。当遇到爆款帖子或大V发布的内容时，同一时刻会有成千上万个用户同时点赞，所有的写请求都会涌向同一个计数键。这个键就成了“热点行”，存储节点（Redis 单线程、数据库行锁）的所有 CPU 和 IO 资源都被它抢占，其他请求的响应延迟就会飙升。
    • 位图分片如何应对
      • 分散键名：位图分片使用键 bm:like:article:123:{chunk}，不同用户根据 ID 落到不同分片键上。写入被自然打散到多个键，消灭了单键热点。
      • 操作变为幂等设位：计数的 INCR 需要严格顺序，而 SETBIT 只是把某一位设为 1，多次重复执行结果一样，进一步降低了对单个键的争抢压力。
  • 2.随机写加剧存储负担：一个实体通常有多个指标（like、fav、comment），传统方案下每个指标是一个独立的键或字段。当用户同时点赞、收藏、评论时，会产生多条写操作，分别更新不同的键，这些键在存储介质上可能并不连续，形成随机写。
    • 磁盘场景：如果是基于磁盘的数据库，随机写意味着大量的寻道操作，IO 效率极低。
    • 锁竞争：即便在内存数据库中，如果这些字段在同一行/同一数据结构中，也会引发锁竞争，导致尾延迟增加。
    • 写放大：存储引擎需要为每一次微小的计数更新写日志、刷新页，实际写入量远大于计数本身的大小。
    • 位图分片如何应对
      • 单一操作：记录用户行为时，不再分别更新多个计数字段，而是在对应行为位图中设置一个 bit。这是一个轻量的、固定大小的操作。
      • 内存友好，无锁：Redis 的位图操作（SETBIT）直接在字符串值上修改，整个命令单线程执行，没有额外的锁竞争。而且因为分片后的键都很小（4KB），操作耗时极短，进一步降低了延迟。
      • 合并写入：如果需要，还可以将多个用户的同一行为打包，用 BITFIELD 或 Pipeline 批量设置，将多次随机写合并为更少的请求，显著减少 IO 开销。
  • 3.网络与存储成本浪费：单条行为的计数更新数据量极小，但高频请求会占用大量网络带宽；同时，存储层需要处理海量零散写请求，硬件资源利用率低，导致成本浪费。

（二）一致性与用户体验的平衡难题

用户行为计数场景存在“双重需求矛盾”：

  • 一方面，用户操作后需要“即时生效”的交互反馈（如点击点赞后立即显示“已点赞”状态），这要求用户维度的状态具备强一致性；
  • 另一方面，实体的总计数（如某Feed的总点赞数）对实时性要求较低，允许秒级最终一致。

传统方案要么为了总计数一致性牺牲交互体验（同步写阻塞用户操作），要么为了体验牺牲一致性（异步写导致总计数更新延迟且可能丢失），无法实现两者的合理平衡。

（三）可扩展性与容灾能力不足

  • 同步写架构难以水平扩展：当行为量突发增长时，存储层的写压力会直接传导至整个链路，而同步写模式下无法通过简单增加节点分摊压力，系统扩容成本高、响应慢。
  • 缺乏容错与回滚机制：一旦存储层出现故障，直接写操作会导致计数丢失或错乱；同时，新功能灰度、故障恢复时缺乏数据回放与补偿能力，运维风险高。
    • 直接写简单说：用户每一次行为，都立刻转成一条对最终存储（如 Redis、数据库）的写入指令，并等待其完成。其流程是：用户点击“点赞” → 业务服务收到请求 → 立刻调用 SETBIT bm:like:article:123:3 100 或 INCR like_count:123 → 同步等待 Redis/DB 返回成功 → 告诉用户“点赞成功”
    • 不可扩展（痛点 1）
      存储层压力直接与用户行为量绑定。流量突发时，只能硬扛或对存储层进行复杂扩容，应用层加再多节点也没用，因为瓶颈卡在同步等待存储上。
    • 缺乏容错（痛点 2）
      如果 Redis 瞬间抖动或主从切换，这次直接写就直接报错、计数丢失，应用层只能傻等或失败，没有“稍后重试”的缓冲地带。灰度或故障恢复时，也没有地方能回放历史数据。

如果每一次微小的用户行为，都被当作一个独立的、最小的操作单元直接去更新存储，而不是把多次操作合并后再处理（细粒度）。那么这样高频的、细粒度的直接写，完美制造了热点键冲突和随机 IO 压力。

基于上述痛点，本设计通过“异步解耦+写聚合+批量刷写”的核心思路，在保障用户体验的前提下，彻底解决高并发计数的性能与稳定性问题。

新架构模式：行为 → 异步写入消息队列/内存缓冲区 → 本地聚合累加（比如内存里先记着 article:123 加了 3 个赞）→ 定时或定量批量刷写到存储

这样就把存储和突发流量解耦了，既削峰，就像水库拦住暴雨（尖峰流量），再用泄洪闸细水长流地放出去，下游（存储）就安全了，又能合并零散操作为批量写，还能在故障时通过缓冲区重放，彻底解决了那些痛点。

二、核心设计思想

核心逻辑是“解耦与聚合”：通过三层架构拆分写路径，将“高频细粒度写”转化为“低频批量写”，同时平衡用户体验与系统性能，具体设计思想如下：

  1. 路径解耦：将写路径拆分为“同步事实写”和“异步汇总写”。同步路径仅处理用户维度的即时状态更新（保障交互体验），异步路径处理总计数的汇总与落地（降低系统压力），两者通过事件队列解耦，互不影响。
  2. 写聚合优化：引入中间聚合层，将同一实体、同一指标在时间窗口内的多次增量更新聚合为一次批量更新。通过“时间窗口折叠”减少最终存储的写次数，从根源上解决写放大问题。
  3. 可靠传输保障：使用Kafka作为事件中间件，实现增量事件的高可靠传输、水平扩展与容灾备份。支持事件回放、灰度发布与故障降级，提升系统灵活性。
  4. 幂等与原子性保障：全链路设计确保“至少一次投递”+“幂等处理”，避免重复计数；关键环节采用原子操作，防止数据错乱，确保最终计数的准确性。

核心架构与流程设计

本方案的整体架构分为“生产端（行为采集）、中间层（事件传输+聚合）、消费端（批量刷写）”三层，各层分工明确、协同工作，以下详细拆解每层设计与完整流程：

（一）整体架构概览

  • 生产端：嵌入业务系统，负责同步更新用户事实状态（用户立刻看到已点赞）、异步生产增量事件；
  • 中间层：包含Kafka事件队列与Redis聚合层，负责事件可靠传输与增量聚合；
  • 消费端：独立部署的消费服务与刷写任务，负责聚合增量的批量刷写与最终计数落地。

（二）详细流程设计

1.第一步：同步快速路径（保障用户体验）

用户触发行为操作（如点赞、取消点赞）后，首先进入同步路径，核心目标是“即时响应、状态可见”，流程如下：

  • 触发事实写：同步更新用户维度的事实状态存储（如使用Redis位图、布隆过滤器或数据库行存储）。例如，用户点赞某Feed时，更新“user:123:like:feed”的位图，标记该用户已点赞，确保用户再次访问时能即时看到自己的操作状态。
  • 轻量无阻塞：同步路径仅执行单一、原子的状态更新操作，无复杂计算与锁竞争，确保响应时间控制在毫秒级，不阻塞用户交互。
  • 失败快速反馈：若同步写失败（如缓存超时），直接返回用户操作失败，避免用户感知“虚假成功”，同时触发重试机制，确保状态一致性。

2.第二步：事件生产（异步解耦）

同步路径完成后，异步触发增量事件生产，将计数更新请求剥离到Kafka队列，流程如下：

  • 构造增量事件：事件包含核心字段：实体标识（entityId，如Feed ID）、实体类型（entityType，如feed/article）、指标类型（metric，如like/fav）、变更值（delta，如+1/-1）、时间戳（timestamp）、幂等键（idempotentKey，如“user123_feed456_like_1699999999”）、事实层版本号（version，用于去重）。
  • 异步写入Kafka：通过异步线程将事件写入Kafka，不阻塞同步路径。生产端配置如下：
    • 可靠性配置：acks=all（确保所有ISR副本写入成功）、开启幂等生产（enable.idempotence=true），避免事件丢失或重复生产；
    • 性能优化：设置合理的linger.ms（如5ms，批量发送）、batch.size（如16KB，批量大小），启用lz4/zstd压缩，提升吞吐并降低网络开销；
    • 分区策略：以entityId为分区键（hash(entityId) % 分区数），确保同一实体的所有事件进入同一Kafka分区，保障事件顺序，且在消费端集中处理，避免跨分区乱序。
  • 可选Outbox模式Outbox 事件驱动模式（本项目中，关注等操作采用 Outbox 模式，点赞没有）：对于核心业务场景，可采用“本地事务+Outbox表”保障事件生产与业务写的一致性。具体为：在同一数据库事务中，更新业务状态（如用户点赞记录）与写入Outbox表（存储事件数据），再通过独立进程读取Outbox表并投递到Kafka，彻底避免“业务成功但事件丢失”的情况。

3.第三步：事件消费与聚合累加（中间层缓冲）

Kafka消费端不直接写最终计数，而是先将增量事件聚合到中间层（Redis），实现“批量折叠”，流程如下：

  • 消费端部署：采用Kafka消费组模式，支持水平扩展（消费组内消费者数量≤分区数），每个消费者独占处理部分分区，确保同一分区的事件顺序消费。
  • 聚合桶设计：
    • 键结构：聚合桶键为agg:{schema}:{entityType}:{entityId}:{timeSlot}，其中timeSlot为时间槽（如小时级“2024100114”），用于拆分键空间，避免跨时段集中失效与热点聚集；
    • 存储结构：采用Redis Hash类型，Hash的字段为指标名称（如like/fav），值为该指标在当前时间窗口内的累计增量。例如，agg:v1:feed:456:2024100114的Hash字段like值为10，代表该Feed在14时的点赞累计增量为10。
  • 原子累加操作：消费端接收到事件后，执行Redis HINCRBY命令，将事件中的delta值(+1点赞/-1取消点赞)累加到对应聚合桶的指标字段中。该操作是原子性的，无需加锁，支持高并发写入，但可能会出现重复消费同一事件会重复累加delta的问题，我可以在消费者端维护一个已处理消息的标识，但会增加负担。
  • 活跃聚合桶管理：通过Redis Set或Sorted Set维护“活跃聚合桶列表”（如active:agg:v1:feed:2024100114），每次更新聚合桶时，将桶键加入该列表，便于刷写任务快速定位需要处理的聚合桶，避免全量扫描。
  • 聚合桶TTL设置：为聚合桶设置合理的TTL（如2小时），确保长时间无更新的陈旧桶自动清理，避免Redis内存膨胀；同时，TTL需长于刷写周期，防止刷写前桶被清理。再刷写机制中我们扫描了所有的聚合桶没有的刷过的和没有的都删了所以并没有设置TTL。

对于在这里不处理重复消费的原因

  1. 上游第一步的 toggleScript 已经做了业务防重
  • 同一个用户对同一个实体的同一种操作（比如反复点赞），只有第一次会触发状态变更（changed=1）并发出事件。后续重复请求直接返回，根本不会进入 Kafka。这从源头消灭了绝大多数“重复操作”类型的事件。
  1. Kafka 生产者幂等保证了日志内消息不重复
  • 配置了 enable.idempotence=true，确保同一条逻辑事件不会因为生产者重试而在分区日志里出现两次。所以消费者拉到的每条消息在日志层面是唯一的。
  1. 消费者“至少一次”的重复主要来自 Rebalance 或崩溃
  • 这是小概率事件，且影响面有限（通常只会重复最近一小批消息）。对于很多计数的业务场景（如展示侧的非金融级计数），短暂的不一致是可接受的，最终会被后续的正确数据覆盖或通过离线对账修复。
  1. 去重存储本身有成本和复杂度
  • 如果每消费一条消息都要查一次 Redis（SETNX idempotentKey），会增加一次网络调用、拖慢消费速度，还要管理去重 Key 的过期时间。在系统初期或流量不那么极端时，可能不划算。

4.第四步：批量刷写（最终计数落地）

刷写任务独立运行，定期扫描活跃聚合桶，将累计增量批量写入最终计数存储，流程如下：

  • 刷写触发机制：支持两种触发方式，可根据场景组合使用：
    • 定时触发：固定延迟调度（如每秒执行一次），适用于流量稳定场景；
    • 自适应触发：根据活跃聚合桶数量、Redis队列长度或事件吞吐动态调整刷写周期（高峰期缩短至500ms，低谷期延长至5s），平衡实时性与性能。
  • 扫描与批处理：
    • 刷写任务从“聚合桶列表”中批量读取聚合桶键（如每次读取1000个）；
    • 批量获取每个聚合桶的Hash字段（指标+累计增量），过滤掉增量为0的字段；
    • 按实体维度组装批量更新请求，例如将100个Feed的点赞、收藏增量打包为一个批量更新请求。
  • 原子折叠写入：
    • 最终计数存储：使用SDS（简单动态字符串）定长结构，确保写入为顺序IO、低锁竞争。例如，将每个实体的所有指标存储在一个固定长度的字节数组中，更新时直接偏移写入对应指标位置；
    • 原子操作：通过Redis Lua脚本或数据库事务实现“读取增量→应用到最终计数→删除聚合字段”的原子流程。具体逻辑：
      1. 读取聚合桶中该实体的所有指标增量；
      2. 将增量累加到最终计数中（如SDS字段偏移更新、数据库UPDATE … SET like = like + ?）；
      3. 成功后删除聚合桶中对应的指标字段（或整个聚合桶），避免重复刷写。

四、方案取舍与核心优势

（一）关键设计取舍

  1. 一致性与复杂度的取舍
  • 不追求跨系统“精确一次”语义：放弃复杂的分布式事务（如2PC、TCC），采用“至少一次投递+幂等处理”的务实方案，在业务可接受的最终一致性范围内，显著降低架构复杂度与性能开销；
  • 用户体验优先：同步路径仅保障用户维度的即时性，总计数允许秒级延迟，平衡用户体验与系统性能。
  1. 性能与实时性的取舍
  • 聚合窗口的权衡：聚合窗口越长，写放大系数越低，但总计数更新延迟越高。方案推荐1-3s的刷写周期，既保证秒级最终一致，又能有效降低写压力；
  • 批量大小的权衡：批大小越大，IO效率越高，但单次刷写延迟越高。通过动态批大小（根据流量调整）平衡两者。

（二）方案核心优势

  1. 极致性能：通过写聚合将高频细粒度写转化为低频批量写，写放大系数降低10-1000倍，显著降低存储层IO与锁竞争压力；
  2. 体验与稳定兼顾：同步路径保障用户操作即时反馈，异步路径实现高并发计数处理，两者解耦，互不影响；
  3. 高可靠性：基于Kafka的高可靠传输、幂等处理与重试机制，确保事件不丢失、计数无错乱；
  4. 弹性扩展：生产端、消费端均可水平扩展，聚合层与最终存储层支持集群部署，轻松应对流量峰值；
