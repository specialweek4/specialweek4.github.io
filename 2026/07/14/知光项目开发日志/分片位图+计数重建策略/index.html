分片位图+计数重建策略

发表于2026-07-14|更新于2026-07-15|知光

这套系统本质上是在把“事实”与“计数”拆开：

  • 位图专门记录每个用户的真实行为事实
  • SDS 专门承载最终计数
  • 中间靠事件、聚合、批量刷写把两者连起来，从而在“强一致 + 高并发”与“低成本 + 可重建”之间找到平衡。

用分片位图牢牢抓住“谁对谁做了什么”的事实，用固定结构的 SDS 高效承载“现在统计结果是多少”，中间用“异步事件 + 聚合累加 + 批量刷写”作为桥梁，常态走最终一致，异常时再回到事实层做强一致重建。

要解决的核心问题

在内容平台里，每一次点赞、收藏、关注都是有价值的行为数据：

  • 前台要求：
    • 点了赞，要立刻看到按钮状态变化 → 需要“是否点赞/收藏”等事实毫秒级可读。
  • 后台汇总要求：
    • “某篇知文总点赞数”“某作者总获赞/收藏”等可以容忍秒级延迟，但必须稳定可扩展。
  • 系统还必须能在异常或数据漂移时，从事实层可控地重建计数，避免影响其他关键业务。
    所以设计思路是：

事实层走强一致，汇总层走最终一致，异常时再反向依赖事实层重建。

分片位图：承载“用户态事实”

1.键空间与分片策略

位图键格式为：bm:{metric}:{etype}:{eid}:{chunk}

  • metric：行为指标（like、fav 等）
  • etype：实体类型（article、video 等）
  • eid：实体 ID
  • chunk：分片编号

用户 ID 通过映射规则 → (chunkId, bitOffset)，在对应位图分片中设置某一位 0/1：

  • 点赞：该位设为 1
  • 取消赞：该位设为 0
  • 通过位图分片，把同一内容的用户状态拆在多个键上，避免单键超大 & 热点冲突导致大量请求同时打在同一个 Key 上。

分片大小需要权衡：

  • 片太大：键少但单键操作重、容易成为热点
  • 片太小：键多、管理成本高
  • 依据用户规模与 QPS 做选型，并可以按监控调整。

BitmapShard.java 本方案中，位图分片为一个分片 32K

同时通过以下映射规则来完成映射：

假设 CHUNK_SIZE = 32768，现在要记录用户 userId = 100000 的状态：

  • chunkOf(100000) = 100000 / 32768 = 3 （落在第 3 号分片）
  • bitOf(100000) = 100000 % 32768 = 1696（分片内的第 1696 位）

于是，我们只需要在 3 号分片的位图里，把第 1696 位设为 1 或 0，就能标记该用户的状态。

2.为什么要分片？

避免单键过大 & 热点问题

  • 超大内容如果所有用户全在一个位图里，这个 key 会特别大，BITOP/BITCOUNT 都很重；
  • 分片后：同一内容的读写压力被分摊到多个 key，单键不会“胖死”。

方便并行统计 & 重建

  • 统计总点赞数时，可以对多个分片并行执行 BITCOUNT 再汇总；
  • 出现异常需要重建计数时，也是“分片并行扫”，效率高很多。

按需迁移/清理更简单

  • 某些分片冷了，可以整体迁移到冷实例/冷存储；
    • 分片键名里直接包含了实体 ID (eid) 和行为 (metric)，天然形成了一种按实体和行为的热度管理能力。
    • 识别冷数据：对于一篇去年发布的文章 article:123，它的点赞、收藏位图分片可能已经很少被访问了。由于键名是 bm:like:article:123:0、bm:like:article:123:1…… 我们可以直接用前缀 bm:like:article:123:* 把它们全部扫描出来。
    • 整体搬运：确定这些分片“冷”了之后，就可以把它们批量迁移到冷 Redis 实例或带 SSD 存储的冷集群里。操作对象是一批精确的、固定 4KB 的小键，不会影响其他热数据。
    • 粒度灵活：甚至可以更细，比如发现用户 ID 在 0~32767 这个分片 (chunk:0) 整体都不活跃了，也可以单独迁移该分片。而如果是不分片的超大 Key，它内部夹杂着冷热用户，根本无法拆开迁移，只能整个 Key 一起搬，代价大得多。
  • 删除内容时，只需要按前缀把相关分片删掉，不用在一个超大 key 里做复杂操作。
    • 精准匹配，一键删除：当需要删除 article:123 时，它相关的所有数据（无论哪种行为）都可以用 bm::article:123: 这个模式匹配到。在 Redis 里，你可以轻松地用 UNLINK 命令配合批量操作，把这些小键异步、非阻塞地删除掉。
    • 没有“大Key”包袱：如果不分片，一个文章的所有互动可能挤在一个巨大的 Key 里，比如 bm:like:article:123，这个 Key 可能高达数 MB。直接 DEL 它会导致 Redis 瞬间卡顿。分片后，你只是删除成百上千个 4KB 的小键，每个操作都轻量、安全，甚至可以在后台慢慢清理，对线上服务零冲击。

利于扩展与监控

  • 分片维度天然可以做：热点监控、QPS 统计、容量估算；
  • 将来用户量级上去，只需要增加分片数或调整映射规则，无需推倒重来。


3. 写路径与读路径

  • 写路径：
    • 通过原子位操作修改位图，天然满足幂等性（多次点赞只会置 1）。
    • 在高并发下依赖底层原子指令保证并发正确。
  • 读路径：
    • isLiked(etype, eid, userId)：只需一次映射 + 一次位测试即可返回，满足前台毫秒级交互。
    • 日常统计不直接扫位图，位图主要用在：
      • 前台“是否点赞/收藏”等用户态判断
      • 异常或冷启动时的计数重建。

位图不设短 TTL，作为事实层长期存在；删除内容/用户时，由后台任务清理对应分片与索引。

事件 → 聚合桶 → SDS：承载“最终计数”

具体操作详见：Kafka 异步写+写聚合

1.增量事件与聚合

当用户行为落到位图后，同时产出一条增量事件：

  • 包含：实体信息（etype/eid）、指标索引 idx、增量 delta（+1/-1）、时间戳等。
  • 写入队列后，由消费者侧进行聚合：
    聚合桶键：
    agg:{schema}:{etype}:{eid}
  • 使用 Redis Hash 存储：
    • field = idx（指标索引）
    • value = delta（增量累加）
  • Hash 操作是原子的，适合高并发下累加各类指标。

2.周期刷写与 SDS 结构

后台周期任务定时扫描活跃聚合桶：

  1. 读取各指标增量
  2. 通过 Lua 等原子脚本把增量折叠进计数快照 SDS
  3. 删掉已处理的聚合字段，释放空间、防止重复折叠
    SDS 采用固定结构：
  • 本质是一个固定长度的数组，每个指标 4 字节整型（大端编码）
  • 优点：
    • 存储紧凑、结构固定，便于一次 GET/SET 读写多指标
    • 更新可通过脚本实现单 key 原子更新，顺带做非负截断，防止负数计数出现
      在常态下，所有“知文/作者维度计数”都通过

事件 → 聚合桶 → 周期刷写 → SDS。这条链路稳定产出。

何时重建？如何防护？

知文维度触发条件

在知文维度，当出现以下情况就要触发重建：

  • SDS 缺失
  • SDS 结构异常（长度不符、字段损坏）
  • 值异常（负数、明显越界）或检测到数据漂移

重建时需保证：

  • 对同一 (etype, eid) 加 分布式锁/单飞锁，防止并发重建
  • 清理对应的聚合字段，避免重建后老增量再次折叠导致重复计数

用户维度触发条件

在作者/用户维度，触发重建的场景包括：

  • 作者维度 SDS 缺失
  • 大规模关系/内容变更后的强一致校验（如大版本迁移后的一次性校正）

同样通过锁和单飞机制保证只有一个重建任务在进行。

两类重建流程

知文维度：从位图重算 like/fav

目标：恢复某内容的 like/fav 等总数，数据来源全部在位图事实层各分片。
步骤概括：

  1. 列出该内容某 metric（如 like）下的全部 bm:… 分片键
  2. 对每个分片执行 BITCOUNT 统计 1 的数量
  3. 汇总各分片计数得到总和
  4. 通过原子脚本写入 SDS 对应指标位
  5. 重建期间对 (etype, eid) 加锁，结束后清理旧聚合字段

优化手段：

  • 分片并行计数（多线程/多节点）
  • 对大量空洞用户区段使用稀疏扫描或“分片跳过索引”
  • 超热内容只在异常或冷启动时重建，常态下优先依赖聚合 + SDS。

CounterServiceImpl和源码有所不同，源码中我们在RedissonClient中配置了看门狗。

tryLock的代码实现了一个基于 Redis 单实例的简单分布式锁，利用 SET key value NX PX ttl 命令的原子性来尝试获取锁。如key字段已存在说明已经有人占用了，token为锁的持有者标识（比如 UUID），用于后续释放锁时验证身份，防止误删别人的锁。

bitCountShardsPipelined 借助 Redis 管道（pipeline） 将多次 BITCOUNT 命令合并为一次网络往返，从而大幅降低延迟。具体实现分解如下：

  • 正常执行：客户端发送一条命令 → 等待 Redis 响应 → 发送下一条。若对 100 个 key 做 BITCOUNT，需要 100 次网络往返。
  • 管道执行：客户端将多条命令一次性打包发送给 Redis，Redis 顺次执行并将所有回复一次性发回。网络往返次数降为 1。
  • 所有的bitcount命令结果只能从 executePipelined自身返回的 List<//object> 中统一获取。

用户维度：从关系 + 内容计数重算

  • 关注指标：
    • followings：用户关注了多少人
    • followers：有多少人关注该用户
    • posts：发布内容数量
    • likedPosts：作者获赞总数
    • favedPosts：作者被收藏总数
  • 数据来源：
    • 关系数据（关注/粉丝表或缓存，过滤无效关系）
    • 内容发布数据（作者 → 内容 ID 列表）
    • 各内容的计数快照 SDS（批量读出，汇总 like/fav）
  • 算法步骤：
    • 初始化用户 SDS 缓冲区，保留正常值，覆盖异常位
    • 写入 followings、followers
    • 获取作者内容 ID 列表，写入 posts
    • 批量读取这些内容的 SDS，累计 likedPosts/favedPosts
    • 将完整的 SDS 一次性写回
