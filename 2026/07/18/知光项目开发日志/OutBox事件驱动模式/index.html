OutBox事件驱动模式

发表于2026-07-18|更新于2026-07-18|知光

通过 Canal + Outbox + Kafka 的事件驱动方式来异步更新粉丝表、计数和缓存，可以从根本上解决关注业务中的“双写不一致”问题，使 following 成为唯一可信主表，而所有下游（粉丝表、计数、缓存）都作为可延迟、可修复的投影异步生成；

简单来说下游就是如果你的数据是通过“听事件”得来的，且能通过“回放事件/重扫主表”修复，那它就是下游，如笔记的点赞数我们可以重新进行扫描位图来重新获取。

同时极大简化写路径、提升写入吞吐、增强系统容错与可恢复性，并允许未来无限扩展新的下游功能（如推荐、搜索等），实现高性能、高一致、可演进的社交关系链架构。

OutBox事件表设计

一主多从+事件驱动模型设计与实现

在 following 表的事务提交过程中，将事件写入一个 Outbox 专用表（如事件类型、用户数据和变更内容）

  • Canal 读取数据库的 Binlog（事务日志），关注 Outbox 表的相关变更
  • Canal 通过 CanalKafkaBridge 将事件以 JSON 格式推送到指定 Kafka topic。

CanalKafkaBridge

  • 功能：把 Canal 中的数据库变更事件解析为消息，序列化为 JSON 后发送到 Kafka。
  • 只处理 INSERT 和 UPDATE 类型事件，以确保高效。
  • Kafka 的消息主题为 canal-outbox。

CanalOutboxConsumer

  • 订阅 Kafka 主题 canal-outbox 的消息内容。
  • 将消息转换为 RelationEvent，并调用 RelationEventProcessor 进一步进行伪从同步、计数更新等逻辑。

RelationEventProcessor

接收到消息后，处理关系事件

插入粉丝表，更新计数

这里我们写入Redis，并且设置2小时的TTL目的是，让他过期从数据库中查在更新redis数据，从而保持数据库和缓存的数据一致性，我们在查看用户的关注列表和粉丝是会用到这个键。关注粉丝计数重建是直接查的数据库中的follows字段。

优势

1.彻底解决“双写不一致”问题

在没有 Outbox + MQ 的情况下：这是最常见的 双写不一致问题。

而使用 Outbox + Kafka：

following 表写入 + Outbox 写入

在 同一个数据库事务 里完成

  • DB 成功即 Outbox 事件成功
  • DB 失败则事件不会产生

从而保证事件不会丢、不会串、不会乱。

然后下游（粉丝表、计数、缓存）全部消费 同一条事件 进行投影更新。

最终保证粉丝表、计数、缓存和 following 一致

稍有延时，但绝不会发生“following 是关注状态，但 follower 表没有”这种数据错误。

2.写路径轻量化，避免热点用户导致写放大

那可能就有人问了，那把关注表，粉丝表，计数更新，缓存列表更新都放在同一分布式事务不行吗

想把 MySQL + Redis + Kafka 真正绑成一个事务，只能上 分布式事务/XA/二阶段提交，代价非常高：

  • 性能差（两阶段提交、锁时间变长）
  • 架构复杂（协调者、回滚、阻塞）
  • 高可用变差（任一参与者挂了会拖死全局）

而且强耦合，任一组件故障就整体挂

  • Redis 挂了 → 关注接口也跟着报错，你只能降级成“关注功能不可用”。
  • MQ 或缓存集群问题也会影响主链路。
  • 而事件异步的设计是：主表成功就算主业务成功，下游可以慢一点、甚至短暂挂掉，之后自动追平。

如果在业务侧同步写三个地方：

  1. following
  2. follower
  3. Redis 计数
  4. Redis ZSet 缓存

一个关注操作变成了4次写 + 可能的网络跳转，在高并发下压力巨大。这里解释一下“业务侧同步”：用户点击“关注”时，follow 方法除了往数据库 insert 一条关注记录，还会同步地、在同一个事务内去更新 Redis 中的关注/粉丝 ZSet、更新粉丝计数、发送通知等。所有动作必须全部成功或全部回滚，响应给用户时缓存已经是最新的。

而我们使用 Outbox + MQ 的异步模式：

关注时只做1件事：写 following + outbox（一次事务）

其他的全部异步“自己去处理”

→ 写路径极轻，只需一次 DB 事务操作

→ 不参杂 Redis/粉丝表/缓存更新逻辑，不会阻塞用户请求

→ 写性能大幅提升，P99 延迟显著降低

3.只有 following 是“权威”，下游都是“投影表”

事件流架构（Event Sourcing 思想的一部分）规定：
业务真相（truth）只存一次，其余表都是投影（Projection）

使用 MQ + Outbox 的好处是：

  • 所有下游（follower 表、计数、缓存）都只依赖事件，不耦合主库。
  • 下游任何地方坏了，都不会影响主路径。
  • 下游可以随时丢弃并通过事件回放 / 全量扫描重建。

这在社交关系这种 高变更 + 高查询 + 大体量 的场景里非常关键。

4.高可扩展性：你可以添加无限多的下游服务

如果未来我们要做：

  • 推荐画像：更新用户兴趣图谱
  • 数据仓库（DW）：打入 ClickHouse/Hudi/S3
  • 风控系统：监控异常关注行为
  • 搜索服务：更新 ES 存储库
    那么我们无需修改关注代码，只需：

新增消费者 → 订阅事件 → 做自己的投影

这就是 Kafka 事件驱动架构最大的牛逼之处。→ 业务演进与主线代码彻底解耦

5. 失败可恢复：重试 + 重放 + 对账 + 修复

没有 Outbox 时：

  • follower 表只要有一次失败，就永远不一致
  • Redis 计数异常 + 超卖 + 回滚全靠人工

使用 Outbox + Kafka + Canal 可以得到以下能力：

  1. Kafka 重试与消息保留机制
    : 消费者挂掉了也不会丢消息。
  2. Outbox 幂等事件重放
    : 下游投影可重建（计数可以自动修正）。是指利用 Outbox 表中持久化的事件记录，在需要时（如消费者故障恢复、数据修复、投影重建）重新投递并处理历史事件
  3. Canal 可用于全量快照 & 重建粉丝表:
  • `当粉丝表挂掉：详情见Canal-binlog 增量订阅
  • 全量扫描 following → 重建 follower 表
  1. 计数对账任务
  • 每日自动比对 following 聚合值与 Redis 计数是否一致，并自动修修复。
  • 这些能力允许我们构建一个 可修复 的系统，这在大规模业务中至关重要。
