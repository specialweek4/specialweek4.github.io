Feed三级缓存

发表于2026-07-20|更新于2026-07-23|知光

背景与目标

  • 面向首页公共 Feed 与“我的知文”两种场景，目标是把“读延迟”和“后端压力”降到最低，同时保证在秒级内的最终一致。
  • 设计理念是把“页面装配”和“个性化覆盖”解耦，前者在缓存层解决，后者仅在返回前叠加；
  • 用事件驱动和定时任务保证数据在短周期内纠偏。

摘要

三级缓存就是把同一个页面的数据按“从便宜到贵、从快到慢”拆成三层存放：

  • 第一层（L2）放在本地内存里，直接拿就能返回，是最快、最省成本的热页缓存；
  • 第二层（L1）放在 Redis 里存页面骨架，只保存 ID 列表和页面元数据，命中后用它来快速拼页面。重点是“拼接”（拼接碎片）
  • 第三层（L0）也是 Redis，但存的是每条内容的小碎片（里面有作者、封面、计数等），用来按 ID 拼装完整条目（feed:public:item:{postId}存在）。

读取时先查本地，不行再查骨架，再不行才查数据库；

写回时从下往上依次回填。这样做的效果就是：把页面读取的大部分成本都挡在缓存层，让热点页面“本地返回”、普通页面“Redis 拼装”、少数情况才访问数据库，实现低延迟、高命中、不打穿后端的稳定架构。

分层概览

  • 三层缓存是为不同成本/收益的命中点设计的分层：
    • 本地二级缓存（L2，内存）：存放完整页面响应，命中成本最低，适合最热的公共页。
    • Redis 页面缓存（L1）：存放页面“骨架”，即 ID 列表与 hasMore 的页面级元数据，命中后只需拼装碎片。
    • Redis 碎片缓存（L0）：为每个内容项存放轻量元数据片段（含作者昵称、封面、发布时间等）与计数碎片，页面装配时直接拿碎片拼出条目。
  • 读路径优先命中高层，不命中则回退到下一层；写路径在数据库回源后一次性回填所有层，形成“下一次更快”的闭环。

层级详解

  • 本地二级缓存（L2）
    • 存的是完整的页面响应对象（条目数组 + 页码/页大小 + hasMore(是否有下一页)）。
    • TTL短、容量有限，专用于公共 Feed 的热门页和用户“我的知文”的近期页，避免网络与序列化成本。
    • 命中后不再访问 Redis，延迟极低，适用于热点 QPS 峰值。
  • Redis 页面缓存（L1）
    • 存的是页面骨架：ID 列表和 hasMore 标志，以及组装所需的轻量索引信息。
    • TTL略短于 L2，且加入随机抖动，避免同一时间大面积同时失效导致瞬时回源。
    • 命中后只需读取对应 ID 的碎片缓存（计数/条目片段）进行装配，数据库不会被打到。
  • Redis 碎片缓存（L0）
    • 粒度是“条目级”：为每个内容项缓存轻量 JSON（作者信息、封面、发布时间、置顶标记等）与计数碎片（如点赞/收藏），并为每个条目设置单独 TTL。
    • 装配页面时按“ID 列表”批量获取碎片；当部分碎片缺失时，按需批量回源（如一次性批量读计数）并回填，提升后续命中率。

读流程

  • 优先读 L2：本地命中则直接返回完整页面，延迟最小。
  • L2 未命中则读 L1：拿到页面骨架（ID 列表与 hasMore），随后按 ID 批量读取 L0 的条目碎片与计数碎片；缺片则进行最小化补全。
  • L1 未命中则回源数据库：用单次查询拉取页面数据，同时并行批量获取计数；把结果写回 L0/L1，并把完整响应写入 L2，最后返回给用户。
    • 返回前个性化覆盖：结合当前用户态（是否点赞/收藏），仅在内存中叠加，不写入缓存，避免把个性化状态污染公共缓存。

KnowPostFeedServiceImpl.java

在回源数据的时候我们将拿到的条目的，liked/faved 置为 null 以免污染用户维度缓存,顺便填充计数。

设计

按小时分片这是非常精细的一个设计：

把缓存键挂上当前的小时槽。

优点：新一小时的 Feed 内容可能发生变更（有新帖发布），旧小时槽的缓存自然被“版本隔离”，避免了因一个帖子更新而导致整个缓存链全部失效的雪崩。

与快速衰减的关联：热点内容具有时间窗口属性（比如当天的新闻），用小时分片，使得旧时间段的缓存随着时间推移而自动“失活”，无需主动清理，完美匹配 Feed 的时效性。

写入与缓存回填

  • 数据库回源后：
    • 将条目切分写入 L0（碎片），为每个条目设置 TTL（带抖动）。就是数据库返回的一个页面可能包含 10~50 个帖子，就是让每个帖子都变成一条独立的 feed:item:{id} 缓存。
    • 将页面骨架（ID 列表、hasMore）写入 L1，为页面设置相对更短 TTL。
      • 虽然碎片缓存会独立更新（比如点赞数 +1），但如果页面缓存还持有旧的 ID 顺序，不同用户看到的列表顺序和包含的帖子可能是过时的。缩短页面 TTL 可以让 ID 列表更快刷新，一旦页面缓存重建，就会从数据库获取最新的 ID 序列，再碎片缓存快速拼装出最新页面。
    • 将完整响应写入 L2（“公共”与“我的”分别配置不同 TTL）。
  • 后续读命中 L1 / L0 时，能够用碎片快速装配，不再访问数据库；命中 L2 时则无需 Redis。

每个帖子（条目）独立缓存

提取 ID，批量写入 List，在构造页面的时候会用到即方法assembleFromCache

失效与一致性

  • 内容发布/置顶/可见性变更等会触发事件驱动的失效：
    • 公共 Feed：采用双删模式删除相关页面键（先删，再延迟几十毫秒二次删），避免并发回源时旧值回写造成短暂不一致。
    • 我的 Feed：按用户维度清理对应前缀键，保证个人列表的及时反映。
  • 计数碎片采用秒级最终一致：增量事件先入聚合桶，定时任务将其折叠到固定结构计数（SDS），页面装配读取计数时若碎片缺失则批量补齐并设置与页面骨架一致的 TTL。

个性化覆盖

liked/faved 等用户态不缓存到页面或碎片中，而是在返回前按需查询位图（极低成本）叠加到条目

用户态意思是，公共页面需要判断某个帖子，自己是否点赞了。这属于用户个人的状态，这种就不能加入到公共缓存，不然就乱套了

问题

为什么不只用一个层级？

  • 单 L1（Redis 页面级）会让装配时仍需网络与反序列化成本，极热公共页的收益不够；引入 L2 可把最热请求完全本地化。
  • 只做 L0（碎片级）会在页面装配时产生大量键合并与排序逻辑，首次装配复杂且时延不稳定；加入 L1 提供骨架可显著稳定装配路径。

为什么个性化不进缓存？

  • 混入个性化会把公共缓存切碎、命中率剧降，且缓存雪崩风险上升；
  • 改为“覆盖”能把个性化与公共缓存解耦，既稳又快。

为什么采用双删与单飞？

  • 所谓单飞是以页面骨架键为“单飞键”，同一页在并发下仅允许一次数据库回源，其他并发请求等待其结果。
  • 双删防止旧值回写；
  • 单飞防止并发击穿，是工程上规避高峰边界条件的必要手段。

为什么采用热键扩展 TTL？

  • 热点页是长尾流量的头部，把头部页留在缓存层更久，能显著降低全链路资源消耗（DB、Redis、网络），同时保障峰值延迟。
