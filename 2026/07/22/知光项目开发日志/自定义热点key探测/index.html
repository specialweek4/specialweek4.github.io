自定义热点key探测

发表于2026-07-22|更新于2026-07-22|知光

本方案以 “滑动窗口热键探测” 为核心，通过 “分级阈值定义热度、动态 TTL 延长缓存、多缓存层协同、稳定性机制兜底” 的完整设计，实现了热门 Feed 页缓存的智能化管理。

  • 其核心价值在于：
    • 以极低的性能开销实现了热点的快速识别与自动降级，将热门页面的缓存命中率显著提升，有效平滑了流量峰值下的数据库与 Redis 压力；
    • 同时通过事件驱动双删、随机抖动等机制，平衡了 “命中率” 与 “数据新鲜度”，避免了缓存雪崩、数据陈旧等风险。

方案无需重构现有架构，配置灵活、运维成本低，可快速落地并根据业务反馈持续优化，是高流量 Feed 场景下提升系统稳定性与访问效率的高效解决方案。

我们自定义的这个算是一个简单实现：属于轻量化本地热键治理
两者都使用 滑动窗口 作为核心机制

一、方案背景与核心目标

在高流量 Feed 场景中，热门页面的访问请求往往呈现 “瞬时集中、快速衰减” 的特征。

  • 瞬时集中：
    指的是大量用户几乎在同一时刻涌入，访问请求在短短几秒到几分钟内急剧堆积到峰值。
  • 快速衰减：
    指的是热度维持时间非常短，达到峰值后便急剧下滑，往往几分钟到几小时就回到正常水平。
    还是上例，当用户刷到消息、看完讨论后，兴趣迅速转移，新话题又涌现，原来的热门页面流量会“断崖式”下跌，很快就无人问津。

传统缓存策略（固定 TTL、无差别缓存）面临三大核心痛点：

  • 一是热点页面频繁失效导致大量回源请求，数据库与 Redis 负载居高不下；
  • 二是热点衰减后缓存未及时降级，造成资源浪费；
  • 三是缓存集中失效时易引发 “雪崩”，瞬间回源洪峰冲击后端稳定性。

本方案的核心目标的是解决上述痛点，具体包括：

  1. 提升热门 Feed 页的缓存命中率，减少无效回源，降低数据库与 Redis 的读写压力；
  2. 应对热点时变性，实现热点快速识别与自动降级，避免资源浪费；
  3. 控制缓存失效瞬间的回源洪峰，保障系统在流量峰值下的稳定性；
  4. 平衡缓存 “命中率” 与 “数据新鲜度”，避免因缓存过期导致的用户体验下降。

二、核心设计思想


本方案的核心逻辑是 “热度驱动缓存生命周期”，通过 “滑动窗口探测热点 → 分级阈值定义热度 → 动态 TTL 延长缓存 → 多缓存层协同” 的闭环，实现 “热点页面久存、冷态页面自然淘汰” 的智能缓存管理。

关键设计思路拆解：

  1. 热点识别不依赖复杂算法，采用 “滑动窗口计数” 实现轻量高效的热度统计，兼顾实时性与资源开销；
  2. 缓存 TTL 与热度强绑定，热度越高的页面，缓存停留时间越长，最大化热门页面的命中率收益；
  3. 分离 “公共维度” 与 “用户个性化维度”，仅对公共页面骨架做缓存优化，避免个性化状态（如点赞、收藏）导致的缓存碎片化，保障缓存命中率；（即是否点赞，是否收藏属于用户个人数据，不放到公共缓存中）
  4. 与现有缓存架构、回源保护机制协同，形成 “探测 - 缓存 - 回源 - 降级” 的完整链路，不重构核心业务逻辑即可落地。

三、核心计数设计

(一)热度探测：滑动窗口计数模型

热度探测是方案的基础，需实现 “轻量统计、快速响应、自动衰减” 三大特性，具体设计如下：

1. 核心数据结构

为每个 “公共页面键”（pageKey，不含用户个性化信息）维护一个整型计数数组，数组的每个元素对应滑动窗口内的一个 “时间切片”，用于存储该时间段内的页面访问次数。

2. 窗口与分段参数定义

滑动窗口的核心参数由 “总时长” 和 “分段粒度” 决定，参数关系为：

  • 滑动窗口总时长（window-seconds）：统计热度的时间范围（如 60 秒，即仅统计最近 60 秒的访问量）；
  • 分段粒度（segment-seconds）：每个时间切片的时长（如 10 秒，即把 60 秒窗口划分为 6 个连续切片）；
  • 分段数量（segments）：滑动窗口包含的时间切片总数，由公式 segments = window-seconds / segment-seconds 计算得出（示例中 60s/10s=6，即数组长度为 6）。

参数设计的核心原则：让分段数量（segments）保持在 6-12 的合理范围 —— 既保证热度统计的细腻度，又避免数组过长导致的求和开销与内存占用。

3. 热度统计与轮转机制

  • 全局指针管理：设置一个 “当前段指针”（currentSegmentIndex）就是下面我们用到的 current.get 来获得当前索引，通过 current.set 来维护索引，实时标记当前正在接收访问计数的时间切片；
  • 访问计数逻辑：每次页面被访问时（调用 record (pageKey) 方法），仅对 “当前段指针” 指向的数组元素执行原子自增操作（O (1) 开销，无锁竞争，性能极高）；
  • 热度计算逻辑：调用 heat (pageKey) 方法时，对计数数组的所有元素求和，结果即为该页面在最近 window-seconds 内的总访问量（热度值），求和开销为 O (segments)，因 segments 数量有限，性能可忽略；
  • 窗口自动轮转：按照 segment-seconds （因为他是分片长度，每段数组代表的时间长度）的固定频率（如每 10 秒）触发窗口轮转：
    1. 计算下一个时间切片的索引（当前指针 + 1，当索引超出 segments 则归零，使数组记载的都是近60秒的访问次数）；
    2. 将该索引对应的数组元素清零（重置为 0）；
    3. 将 “当前段指针” 指向该索引，开始新时间段的计数。

4. 热度自动衰减特性

滑动窗口的轮转机制天然实现了热度的自动降级：旧时间切片的访问计数会随着窗口轮转 “移出” 统计范围（不再计入求和结果，他会被覆盖），无需额外的降级逻辑。

例如：页面在第 1-10 秒被访问 100 次（数组第 0 位 = 100），第 11-20 秒被访问 80 次（数组第 1 位 = 80），当窗口轮转至第 61 秒时，第 1-10 秒的计数（数组第 0 位）已被清零且移出窗口，热度值自动剔除该部分历史访问量，确保 “热点上得快、冷下来也快”。老的数据自动去除。

（二）热度分级与 TTL 动态扩展

通过 “分级阈值” 将热度值映射为不同等级，再为每个等级配置对应的 TTL 扩展规则，实现 “热度越高，缓存越久” 的动态管理。

1. 热度分级规则

预设三个阈值（可配置），将 heat (pageKey) 计算出的热度值划分为 “低、中、高” 三个等级，默认配置示例如下（实际需根据业务 QPS 分布调整）：

  • 低热度：热度值 < 50（最近窗口内访问量较少）；
  • 中热度：50 ≤ 热度值 < 200（访问量中等，开始形成热点）；
  • 高热值：热度值 ≥ 200（访问量集中，属于核心热点）。

分级计算为 “即时触发”：每次缓存命中、缓存写入时，都会实时计算当前页面的热度等级，确保 TTL 扩展与最新热度匹配。

2. TTL 扩展策略

缓存系统的每一层（L0/L1/L2）均配置 “基础 TTL”，在此基础上根据热度等级叠加 “扩展 TTL”，同时加入 “随机抖动（jitter）” 避免缓存同时集中失效。具体规则：

  • 低热度：仅使用基础 TTL，不额外扩展；
  • 中热度：基础 TTL + 扩展 TTL（如 60 秒），延长缓存停留时间；
  • 高热值：基础 TTL + 扩展 TTL（如 120 秒），最大化热点页面的缓存生命周期。

示例：若 L1 层基础 TTL 为 30 秒，某页面为中热度，则实际 TTL=30 秒 + 60 秒 + 随机抖动（±5 秒），最终 TTL 在 85-95 秒之间。

3. 个性化状态处理

为避免缓存碎片化，用户个性化状态（如是否点赞、是否收藏）不纳入缓存存储：

  • 缓存中仅存储 “公共页面骨架”（如 Feed 内容、作者信息、基础点赞数）；
  • 用户请求返回前，在内存中动态叠加当前用户的个性化状态（liked/faved），确保用户看到专属内容；
  • 该设计既保证了公共缓存的复用率，又不影响个性化体验。

（三）多缓存层协同架构

方案基于 “三级缓存”（L0 碎片缓存、L1 页面骨架缓存、L2 本地完整页缓存）构建读路径，各层分工明确、协同工作，进一步提升访问效率与稳定性。

1. 三级缓存定义

  • L0（碎片缓存）：存储 Feed 页的原子碎片数据（如单条 Feed 详情、用户基础信息），存储于 Redis，粒度细、复用性高；
  • L1（页面骨架缓存）：存储 Feed 页的 “组装结构”（如页面包含的 Feed ID 列表、排版信息），存储于 Redis，用于快速组装页面；
  • L2（本地完整页缓存）：存储已组装完成的完整 Feed 页（不含个性化状态），存储于应用本地内存，访问速度最快。

2. 页面读路径流程

用户请求 Feed 页时，按 “L2→L1→数据库” 的顺序查询，同时触发热度统计，具体步骤：

  1. 优先查询本地 L2 缓存：若命中完整页，直接返回给用户（返回前叠加个性化状态），同时调用 record (pageKey) 记录访问热度；
  2. 若 L2 未命中，查询 Redis L1 缓存：若命中页面骨架，从 L0 缓存中读取对应的碎片数据组装成完整页，返回给用户（叠加个性化状态），同时调用 record (pageKey) 记录热度，并重写 L2 缓存；
  3. 若 L1 未命中（打穿到数据库）：从数据库查询完整数据，拆分并回填 L0 碎片缓存与 L1 页面骨架缓存，组装完整页写入 L2 缓存，返回给用户（叠加个性化状态），最后调用 record (pageKey) 记录热度。

3. 缓存 TTL 协同规则

为确保各层缓存数据一致性，避免 “骨架存在但碎片失效” 或 “本地缓存有效但 Redis 失效” 的情况，TTL 策略做如下协同：

  • L0、L1、L2 三层均使用 “基础 TTL + 热度扩展 TTL + 随机抖动” 的配置；
  • L0 碎片缓存的 TTL 与对应 L1 页面骨架的 TTL 保持一致，确保组装时碎片数据有效；
  • L2 本地缓存的 TTL 不超过 L1 缓存的 TTL，避免本地缓存长期有效但 Redis 缓存已失效，导致数据不一致。

（四）并发与稳定性保障机制

方案与 “单航班回源”“事件驱动双删” 等机制协同，形成全方位的稳定性防护，具体如下：

1. 单航班回源保护

当某页面缓存失效，多个并发请求同时打穿到数据库时，“单航班” 机制确保仅允许一个请求执行数据库查询，其余请求等待该请求返回后复用结果。
与本方案的协同价值：热键 TTL 延长减少了缓存失效频率，使单航班机制的触发次数显著降低，进一步平滑回源压力，避免并发回源冲击数据库。

2. 事件驱动双删策略

为解决 “缓存数据陈旧” 问题，当 Feed 页内容更新（如发布新 Feed、修改内容）时，通过事件驱动触发 “双删”：

  1. 先删除 Redis 中的 L0 碎片缓存与 L1 页面骨架缓存；
  2. 再删除所有应用节点本地的 L2 完整页缓存；
  3. 同时调用 reset (pageKey) 方法，将该页面的热度计数数组归零，避免旧热点持续影响缓存策略。

该机制确保缓存数据与数据库数据一致，抵消了 TTL 扩展可能带来的 “数据陈旧” 风险。

3. 随机抖动防雪崩

所有缓存的 TTL 均加入 ±5%~±10% 的随机抖动，即使大量页面处于同一热度等级，其缓存失效时间也会分散，避免 “集中失效→集体回源” 的缓存雪崩场景。

五、方案权衡与核心优势

（一）关键设计权衡

  1. 本地热键探测 vs 分布式探测

选择 “本地探测” 而非分布式热度同步，核心原因：

  • 本地探测开销极低（O (1) 计数、O (segments) 求和），无需跨节点网络通信，与页面回填逻辑天然耦合，落地成本低；
  • 分布式探测需解决一致性、时延、通信成本等问题，复杂度高，而本方案通过 “本地判定 + Redis TTL 延长” 已能覆盖大部分热点场景，收益性价比更高；
  • 若后续需全局热键调度，可基于本地探测数据聚合上报，无需重构核心逻辑。
  1. 滑动窗口 vs 指数衰减 / 直方图
    选择 “滑动窗口” 而非其他热度统计模型，核心原因：
  • 滑动窗口逻辑简单、易于理解和调参，开发与运维成本低；
  • 热度上升与下降响应速度一致（“上快下也快”），无需额外设计降级规则；
  • 指数衰减依赖衰减系数调参，直方图模型复杂度高，均不如滑动窗口适配 “热点时变性” 的需求。
  1. 缓存命中率 vs 数据新鲜度
    通过 “事件驱动双删” 与 “合理 TTL 配置” 平衡两者：
  • TTL 扩展可能导致热点页面缓存停留更久，但双删机制确保内容更新时缓存及时失效；
  • 扩展 TTL 不超过 window-seconds 的 2 倍，且基础 TTL 本身限制了缓存最大停留时间，进一步降低陈旧风险。

（二）方案核心优势

  1. 轻量高效：热度探测基于内存数组与原子操作，无复杂计算与网络开销，不影响核心链路性能；
  2. 自适应热点：滑动窗口实现热度自动衰减，无需人工干预，适配热点 “瞬时集中、快速衰减” 的特征；
  3. 稳定性强：与单航班、随机抖动、双删机制协同，全方位防范回源洪峰与缓存雪崩；
  4. 配置灵活：多维度参数支持精细化调参，可根据业务流量特征动态优化；
  5. 落地成本低：基于现有三级缓存架构扩展，不重构核心业务逻辑，兼容现有回源与缓存机制。
