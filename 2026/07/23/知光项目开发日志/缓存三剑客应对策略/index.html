缓存三剑客应对策略

发表于2026-07-23|更新于2026-07-24|知光

总体策略：

  • 多层缓存分担与隔离：本地缓存 + 页面缓存 + 片段缓存（ids/item/count）分层承压，分片设计将大对象拆成更细粒度的片段，减少单点失效面。Feed 三级缓存设计
  • 失效分散与延长：热点动态延长 TTL，配合随机抖动分散过期峰值，避免“同一秒集体过期”的拥塞点。
  • 并发序控制：单飞（single-flight）策略将并发下的“第一次回源”限制为单个请求，其余排队复查缓存，抑制击穿瞬时洪峰。
  • 负面结果缓存：不存在对象用 NULL 哨兵短期缓存，阻断重复无效请求的穿透。
  • 精准失效：构建页面集合索引与内容反向索引，内容更新时仅定向失效受影响页面，避免大范围清理导致雪崩。
  • 读写解耦与幂等：写入经 Outbox/Kafka 异步化、幂等去重；读路径优先缓存命中再有限度修补，稳定整体行为。
  • 限流与降级：令牌桶保护高风险入口，配合软缓存（如分页 hasMore 的短 TTL）与本地 Top 缓存对大用户人群降压。
    防穿透（缓存穿透）

防穿透

  1. NULL 哨兵占位：对“不存在内容”的查询直接写入一个短 TTL 的 NULL 值，下次请求命中后不再打数据库。这是最直接的“结果级防穿透”，对黑名单或非存在 ID 尤为有效。（缓存空值）

简单来说是和这个一样。

  1. 参数与存在性前置校验：控制层验证 ID 格式、场景合法性，服务层对权限/归属进行快速校验，尽可能早失败，避免无意义回源。
  2. 片段缓存优先：列表页先拉 ids 与每个 item 的元数据片段，再补齐 count 片段；只有缺片段时才按需回源修补，显著减少“整页同时回源”的穿透面。
  3. 写入口限流：对可能导致指数级读取的写操作（如关注/取消、批量更新）置令牌桶，削减恶意或峰值穿透的源头。

防击穿

1. 单航班（单飞）机制

同一页或详情的首次回源被限定为单请求，其余并发在锁内复查缓存或直接返回已有分片，击穿峰值被削到“单连接 + 排队”，避免瞬时洪峰。

这是基于 ConcurrentHashMap + synchronized 的 per-key 互斥锁（单航班锁），用来防止缓存击穿和惊群效应

那个singleFlight是这样创建的

用 ConcurrentHashMap 来存储 idsKey（即”航班号”）对应的锁对象。

具体流程分析：

1.获取/创建锁对象（原子操作）

  • computeIfAbsent 是 原子的，保证同一时刻多个线程并发调用时，只有一个线程会创建锁对象，因为是key相同所以其他线程直接拿到已存在的那个。
  • 第一个到达的线程创建锁 → 进入 synchronized 块 → 回源数据库。

2. 后续线程阻塞等待

  • 后续相同 idsKey 的线程从 computeIfAbsent 拿到 同一个锁对象，在 synchronized 处排队阻塞。

3. 第一个线程写完缓存后释放

  • 第一个线程完成 DB 查询 → 写入缓存 → 调用 singleFlight.remove(idsKey) → 退出 synchronized 块。

此时：

  • 等待队列中的一个线程被唤醒，拿到同一个锁对象，进入同步块。
  • 它先执行 assembleFromCache() → 命中缓存 → 直接返回，不再查 DB。
  • 也调用 singleFlight.remove(idsKey)（此时 key 已被移除，相当于空操作）。

4. 确保不击穿的关键

remove 在 synchronized 块 内 调用，但唤醒的线程 仍然持有对旧锁对象的引用，所以能继续互斥执行。同时新来的线程调用 computeIfAbsent 会创建idskey锁对象，不影响已在等待的线程，在重查三层缓存拿到了他也会执行删除锁对象。

我们在synchronized (lock)传的是这个锁对象，所以他锁的是"对象，synchronized(lock) 对同一个 lock，同一时刻最多只有一个线程能持有 Monitor → 其他线程必须 阻塞等待。

2. 本地缓存兜底：

热点页先命中本地 Caffeine，RTT 极短、失效独立，不会拖累远端 Redis；即使远端短时失效，本地可作为“止损层”

3. 计数锁重建

汇总计数（如 SDS 固定结构）缺失或异常时，先以分布式锁保护重建过程，防止并发下重复重建；重建后清理聚合增量，保证“只加一次”语义

4. 软缓存辅助判断

分页“是否有更多”（hasMore）以短 TTL 的软缓存承载，减少为一个布尔判断而全量回源导致的击穿。

放雪崩

  1. TTL 随机抖动：页面与片段写入引入 10–30 秒的随机抖动，不同键的过期时间在一个区间内均匀分散，避免爆点。

  1. 热点 TTL 动态延长：基于滑窗计数的热度分级（LOW/MEDIUM/HIGH），对高热键延长 TTL，热点在高峰期更长久保活、降低集体过期概率。

  2. 分层与分片键：以布局版本与时间槽（如小时）对分页键分片，同一页面的不同时间窗口分别缓存；即使失效也只影响该窗口，不会波及整站。

  1. 精准失效与双删：更新内容“先删缓存后写数据库 + 延迟再删缓存”，避免并发下在完成写数据库之前旧值回写缓存。同时通过内容反向索引精准定位受影响页面进行按需失效，降低大范围清理引发的雪崩。
  2. 异步化与幂等去重：写事件通过 Outbox→Canal→Kafka 异步传播，消费者使用去重键保证幂等；即便出现重放或抖动，也不会造成“重复清理/重复写”的雪崩效应。
