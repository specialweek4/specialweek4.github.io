本文主要介绍Spring特性：IoC容器、AOP、事务管理、MVC框架等

spring 框架中的bean是线程安全的吗？

这里解释以下什么是无状态，无状态就是不能被修改，spring bean并没有可变的状态，因为bean是单例的，注入的都是无状态的对象（一个类型的bean只有一个）。所以某种程度上Spring的单例bean是线程安全的。

如果在bean中定义了可修改的成员变量的话，是要考虑线程安全问题的。可以使用bean多例（使用@Scope注解修改成多例）和加锁来解决。

bean的生命周期

Spring Bean 的生命周期概括为五个阶段：实例化 → 属性填充 → 初始化 → 使用 → 销毁。

  1. 实例化：Spring 通过反射调用构造方法创建 Bean 实例。
  • 比如你写了一个 UserService 类，Spring 在启动时通过反射调用 UserService.class.newInstance()（底层等价于 new UserService()），在内存中创建出这个类的对象，这就是实例化。
  1. 属性填充：给 Bean 注入依赖的属性值（依赖注入）。

依赖属性值，简单说就是：

  • 一个 Bean 里面用 @Autowired 或 @Value 标注的那些东西。
  • 属性填充这一步，就是 Spring 把这些东西塞进已经 new 出来的对象里。塞完之后，这个对象才算”完整”了，可以进入下一步初始化。
  1. 初始化：执行各种 Aware 回调（BeanNameAware、BeanFactoryAware、ApplicationContextAware），然后经过 BeanPostProcessor 的前置处理，再执行 @PostConstruct 或 InitializingBean 的 afterPropertiesSet()，最后经过 BeanPostProcessor 的后置处理（AOP 代理就在这一步生成）。
  2. 使用：Bean 就绪，正常对外提供服务。
  3. 销毁：容器关闭时，执行 @PreDestroy 或 DisposableBean 的 destroy() 方法。

Bean的作用域

  1. Singleton(单例):在整个应用程序中只存在一个Bean实例。默认作用域,Spring容器中只会创建
    一个Bean实例,并在容器的整个生命周期中共享该实例。
  2. Prototype(原型):每次请求时都会创建一个新的Bean实例。每次从容器中获取该Bean时都会创建
    一个新实例,适用于状态非常瞬时的Bean。
  3. Request(请求):每个HTTP请求都会创建一个新的Bean实例。仅在Spring Web 应用程序中有效,
    每个HTTP请求都会创建一个新的Bean实例,适用于Web应用中需求局部性的Bean。
  4. Session(会话):Session范围内只会创建一个Bean实例。该Bean实例在用户会话范围内共享,仅
    在Spring Web 应用程序中有效,适用于与用户会话相关的Bean。
  5. Application:当前 ServletContext 中只存在一个Bean实例。仅在Spring Web应用程序中有效,该
    Bean 实例在整个ServletContext范围内共享,适用于应用程序范围内共享的Bean。
  6. WebSocket(Web套接字):在WebSocket范围内只存在一个Bean实例。仅在支持WebSocket的应
    用程序中有效,该Bean实例在WebSocket 会话范围内共享,适用于WebSocket会话范围内共享的
    Bean.
  7. Custom scopes(自定义作用域):Spring允许开发者定义自定义的作用域,通过实现Scope接口来
    创建新的Bean作用域。

介绍一下AOP

Spring AOP是面向切面编程，通过动态代理在不修改源码的情况下，给目标方法添加额外功能。核心概念有目标对象，即被增强的原始对象；连接点，是程序执行中的特定点，比如方法执行；切入点，是要增强的连接点，通过表达式定义；通知，是增强的逻辑，有前置、后置、环绕、异常、最终通知；切面，是切入点和通知的组合；织入，是将切面应用到目标对象生成代理对象的过程。

在Spring AOP中，代理是实现AOP的方式，当目标对象实现接口时，默认用JDK动态代理，通过接口生成代理类；如果没有实现接口，就用CGLIB代理，通过继承目标类生成代理子类。

在 AOP 中有以下几个核心概念:

  • 切面（Aspect）：抽离的通用功能模块（比如日志切面、事务切面）；
  • 切点（Pointcut）：指定切面织入到哪些业务方法（比如所有com.service包下的方法）；
  • 通知（Advice）：切面的执行时机（前置通知 @Before、后置通知 @After等）；
  • 织入（Weaving）：将切面应用到目标对象的过程（Spring 中是运行时织入）。
  • AOP 代理（AOP Proxy）：Spring AOP 通过动态代理生成的、包含切面逻辑的代理对象，Spring AOP 的两种代理方式有JDK 动态代理和CGLIB 动态代理。


连接点是可以被AOP控制的方法，切入点是实际被AOP控制的点，有Aspect注解的就是切面。通知也就是对原始方法的增强，增了有计时功能，在运行被控制的方法时，先运行切入类的方法，当执行到 join Point.proceed 时在执行原始方法，然后在运行切入类后面的代码

Spring AOP 的两种代理方式

动态代理是在运行时动态生成代理对象，而不是在编译时。它允许开发者在运行时指定要代理的接口和行为，从而实现在不修改源码的情况下增强方法的功能。

  1. JDK动态代理（原生方式）
  • 要求目标对象必须实现至少一个接口（上图实现了DeptService接口），底层通过「接口代理」实现
    • 运行时动态，利用 Proxy.newProxyInstance()，生成一个实现了目标对象所有接口的代理类（字节码）；
    • 代理类的所有方法调用，都会转发到 InvocationHandler 接口的 invoke 方法，开发者在方法中实现增强逻辑，再调用目标方法。
    • 缺点：强制要求目标对象实现接口；只能代理接口中定义的方法，无法代理目标类的非接口方法
  1. CGLIB 动态代理（第三方、基于子类）
  • 底层通过子类继承来实现。
  • 当代理类没有实现接口时，Spring会使用 CGLIB 库生成一个代理类的子类作为代理。

AOP常用的注解

  • @Asepct
  • @Pointcut
  • @Before

  • @Around：在方法执行前后执行通知，是功能最强的一种
  • @AfterReturning：在方法正常返回结果后执行通知

Spring 中的事务实现

spring实现的事务本质就是aop完成，对方法前后进行拦截，在执行方法之前开启事务，在执行完目标方法之后根据执行情况提交或者回滚事务。

Spring事务的失效场景

Spring Boot通过Spring框架的事务管理模块来支持事务操作。事务管理在Spring Boot中通常是通过 @Transactional 注解来实现的。事务可能会失效的一些常见情况包括：

  1. 异常被try-catch吞掉：如果事务方法内用了 try-catch 捕获了异常却没有在抛出，Spring的代理感知不到异常，事务正常提交，回滚失效
  2. 受检异常: 默认情况下，Spring对非受检异常（RuntimeException或其子类）进行回滚处理，这意味着当事务方法中抛出这些异常时，事务会回滚。当抛出受检异常（IOEXCETION,SQLEXCETION）的时候默认不会触发回滚。
  3. 事务传播属性设置不当: 如果在多个事务之间存在事务嵌套，且事务传播属性配置不正确，可能导致事务失效。特别是在方法内部调用有 @Transactional 注解的方法时要特别注意。
  4. 多数据源的事务管理: 如果在使用多数据源时，事务管理没有正确配置或者存在多个 @Transactional 注解时，可能会导致事务失效。
  5. 同类内部方法调用（this调用）：如果一个事务方法内部通过 this 调用另一个带 @Transactional 的方法，由于用到了 this 他就绕过了代理对象，被调用方法的事务注解会失效。
  6. 事务在非公开方法中失效: 如果 @Transactional 注解标注在私有方法上或者非 public 方法上，事务也会失效

候选人：

  • 第一个，如果方法上异常捕获处理，自己处理了异常，没有抛出，就会导致事务失效，所以一般处理了异常以后，别忘了抛出去就行了
  • 第二个，如果方法抛出检查异常，如果报错也会导致事务失效，最后在spring事务的注解上，就是@Transactional上配置rollbackFor属性为Exception，这样别管是什么异常，都会回滚事务
  • 第三，我之前还遇到过一个，如果方法上不是public修饰的，也会导致事务失效

这里解释一下第四点

  1. 多个数据源，事务管理器没配好
  1. 一个方法里用多个 @Transactional，管不住两个库

两个事务管理器各管各的——用户库的事务提交了，订单库的事务可能还没提交甚至失败，做不到一起成功一起失败。

什么是Spring循环依赖

循环依赖其实就是循环引用，指的是两个或两个以上的 bean 互相持有对方:例如A类中有B属性,B类中有A属性,从而形成了一个依赖闭环,如下图。

循环依赖问题在Spring中主要有三种情况:

  • 第一种:通过构造方法进行依赖注入时产生的循环依赖问题。
  • 第二种:通过setter方法进行依赖注入且是在多例(原型)模式下产生的循环依赖问题。
  • 第三种:通过setter 方法或字段(Field)进行依赖注入且是在单例模式下产生的循环依赖问题。

只有【第三种方式】的循环依赖问题被Spring解决了,其他两种方式在遇到循环依赖问题时,Spring都
会产生异常。

Spring在 DefaultSingletonBeanRegistry 类中维护了三个重要的缓存(Map),称为“三级缓存”:

候选人：
嗯，好的，我来解释一下

  • 循环依赖：循环依赖其实就是循环引用,也就是两个或两个以上的bean互相持有对方,最终形成闭环。比如A依赖于B,B依赖于A
  • 循环依赖在spring中是允许存在，spring框架依据三级缓存已经解决了大部分的循环依赖
    • ①一级缓存：单例池，缓存已经经历了完整的生命周期，已经初始化完成的bean对象
    • ②二级缓存：缓存早期的bean对象（生命周期还没走完）
    • ③三级缓存：缓存的是ObjectFactory，表示对象工厂，用来创建某个对象的

步骤：

一级缓存的作用：限制bean在beanFactory中只存一份，即实现singleton scope，解决不了循环依赖。

如果先要打破循环依赖，就需要一个中间人的存在，这个中间人就是二级缓存。

候选人：

假设存在两个相互依赖的单例Bean: BeanA 依赖 BeanB，同时 BeanB 也依赖 BeanA。当Spring容器，启动时,它会按照以下流程处理:

  • 第一，先实例A对象，同时会创建ObjectFactory对象存入三级缓存singletonFactories
  • 第二，A在初始化的时候需要B对象，这时候就会走B的创建的逻辑
  • 第三，B实例化完成，也会创建ObjectFactory对象存入三级缓存singletonFactories
  • 第四，当Spring填充B的时候发现，B需要注入A，通过三级缓存中获取ObjectFactory来生成一个A的对象同时存入二级缓存，这个是有两种情况，一个是工厂生成的是A的普通对象，另一情况如果A需要AOP代理工厂生成的是A的代理对象，这也是三级缓存的关键
  • 第五，B通过从二级缓存 earlySingletonObjects 获得到A的对象后可以正常注入，B创建成功，存入一级缓存singletonObjects
  • 第六，回到A对象初始化，因为B对象已经创建完成，则可以直接注入B，A创建成功存入一次缓存singletonObjects
  • 第七，二级缓存中的临时对象A清除

整个机制通过中断初始化流程、逆向注入半成品、延迟代理生成三大策略,将循环依赖的死结转化为有序的接力协作。

值得注意的是,此方案仅适用于Setter/Field注入的单例Bean;构造器注入因必须在实例化前获得依赖,仍会导致无解的死锁。

SpringMVC的执行流程


候选人：

  1. 用户发送出请求到前端控制器DispatcherServlet，这是一个调度中心
  2. DispatcherServlet收到请求调用HandlerMapping（处理器映射器）
  3. HandlerMapping找到具体的处理器(可查找xml配置或注解配置)，生成处理器对象及处理器拦截器(如果有)，再一起返回给DispatcherServlet
  4. DispatcherServlet调用HandlerAdapter（处理器适配器）
  5. HandlerAdapter经过适配调用具体的处理器（Handler/Controller,也叫页面控制器）
  6. Controller执行完成返回ModelAndView对象
  7. HandlerAdapter将Controller执行结果ModelAndView返回给DispatcherServlet
  8. DispatcherServlet将ModelAndView传给ViewReslover（视图解析器）
  9. ViewReslover解析后返回具体View（视图）
  10. DispatcherServlet根据View进行渲染视图（即将模型数据填充至视图中）
  11. DispatcherServlet响应用户

当然现在的开发，基本都是前后端分离的开发的，并没有视图这些，一般都是handler中使用Response直接结果返回

SpringBoot重要的注解


候选人：

Spring Boot的核心注解是@SpringBootApplication , 他由几个注解组成 :

  • @SpringBootConfiguration： 组合了- @Configuration注解，实现配置文件的功能；

  • @EnableAutoConfiguration：打开自动配置的功能，也可以关闭某个自动配置的选项

  • @ComponentScan：Spring组件扫描

  • @Controller:标识控制器类,处理HTTP请求。

  • @RestController:结合@Controller和@ResponseBody,返回RESTful风格的数据。

  • @Service:标识服务类,通常用于标记业务逻辑层。

  • @Repository:标识数据访问组件,通常用于标记数据访问层。

  • @Component:通用的Spring组件注解,表示一个受Spring管理的组件。

  • @Autowired:用于自动装配Spring Bean。

  • @Value:用于注入配置属性值。

  • @RequestMapping:用于映射HTTP请求路径到Controller的处理方法。

  • @GetMapping、@PostMapping、@PutMapping、@DeleteMapping:简化@RequestMapping的GET、POST、PUT和DELETE请求。

另外,一个与配置相关的重要注解是:

  • @Configuration:用于指定一个类为配置类,其中定义的bean会被Spring容器管理。通常与@Bean配
    合使用,@Bean用于声明一个Bean实例,由Spring容器进行管理。

SpringBoot自动配置

SpringBoot的自动装配原理是基于Spring Framework的条件化配置和@EnableAutoConfiguration注解实
现的。这种机制允许开发者在项目中引入相关的依赖,SpringBoot 将根据这些依赖自动配置应用程序的上
下文和功能。

自动装配的原理

其中Spring Boot项目中的引导类上有一个注解@SpringBootApplication，这个注解是对三个注解进行了封装，分别是：

  • @SpringBootConfiguration
  • @EnableAutoConfiguration
  • @ComponentScan

其中@EnableAutoConfiguration是实现自动化配置的核心注解。

  • 该注解通过@Import注解导入对应的配置选择器(Autoconfigurationinportselector)。关键的是这个配置选择器内部就是读取了该项目和该项目引用的Jar包的的classpath路径下META-INF/spring.factories文件中的所配置的类的全类名。
  • 对于每一个发现的配置类，Autoconfigurationinportselector 会使用条件判断注解所指定的条件来确定是否将其导入到Spring容器中。
  • 一般条件判断会有像 @ConditionalOnXxx 这样的注解，判断是否有对应的class文件，如果有则加载该类，把这个配置类的所有的Bean放入spring容器中使用。
