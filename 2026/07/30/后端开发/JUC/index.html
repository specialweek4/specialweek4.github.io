线程和进程的区别

一个进程包含一到多个线程

  • 进程是正在运行程序的实例，进程中包含了线程，每个线程执行不同的任务
  • 不同的进程使用不同的内存空间，在当前进程下的线程可以共享内存空间
  • 线程更加轻量

并发和并行的区别

  • 并发：多个事件在同一时间间隔内发生
  • 并行：多个事件在同一时刻发生

创建线程的方式有哪些？

1.继承Thread类

2.实现runnable

3.实现Callable接口

4.使用线程池来创建线程

Runnable 和 Callable的区别

  • Runnable 接口的run方法没有返回值
  • Callable 接口的call（）方法允许抛出异常，而Runnable接口的Run（）方法只能在内部笑话异常，不能继续上上抛

run方法和statr方法的区别

  • start方法是开启一个线程.一个线程对象只能调用一次start方法。
  • run（）封装了要被线程执行的代码，可以被调用多次。

线程包含哪些状态

新建（NEW），可运行（RUNNABLE），阻塞（BLOCKED）, 等待（WAITING），时间等待，终止。

线程状态之间是如何变化的

  • 创建线程对象是新建状态。
  • 调用了start()方法转变为可执行状态
  • 线程获取到了CPU的执行权，执行结束时终止状态
  • 在可执行状态的过程中，如果没有获取CPU的执行权，可能会切换其他状态
    • 如果没有获取锁进入阻塞状态，获得锁在切换为可执行状态
    • 如果线程调用了wait()方法进入等待状态，其他线程调用notify()唤醒后可切换为可执行状态
    • 如果线程调用了sleep(50)方法，进入计时等待状态，倒时间后可切换为可执行状态

新建T1、T2、T3线程，如何保证他们按顺序执行？

额可以使用join()方法，让一个线程等待另一个先成完成后再执行。

notify和notifyAll的区别

  • notifyALL: 唤醒所有wait线程
  • notify：只随机唤醒一个wait线程。

wait和sleep方法的不同

Thread.sleep() 和 Object.wait() 的区别：

  • 所属不同：sleep 是 Thread 的静态方法，可以在任何地方直接通过 Thread.sleep() 调用，不需要对象实例；wait 是 Object 的实例方法，需要对象实例。
  • 锁的释放：Thread.sleep()在调用的时候,让线程暂停执行，但不会释放持有的对象锁，直到synchronized中的方法执行完才会释放锁，也就是说，在sleep期间，其他线程无法获得该线程持有的锁；Object.wait() 调用该方法的时候，线程会释放锁，进入等待状态，直到另一个线程调用 notify() 或 notifyAll() 唤醒它。
  • 使用条件：sleep 可以在任何地方调用，不需要事先获取锁；wait 必须在 synchronized 代码块或方法中调用，否则抛出 IllegalMonitorStateException。
  • 唤醒机制：sleep 会在时间结束后自动恢复执行，等待 CPU 调度；wait 需要其他线程调用 notify() 或 notifyAll() 来唤醒等待的线程。

如何停止一个正在运行的线程

  • 异常法停止:线程调用interrupt(), 方法后,在线程的run方法中通过Thread. currentThread() .isInterrupted(),判断当前线程的中断状态(注意不要用静态方法Thread. interrupted(),它会清除中断标志),如果是中断状态则抛出异常,达到中断线程的效果。
  • 在沉睡中停止:先将线程sleep,然后调用interrupt标记中断状态,interrupt会将阻塞状态的线程中断。会抛出中断异常,达到停止线程的效果
  • stop()暴力停止:线程调用stop()方法会被暴力停止,方法已弃用,该方法会有不好的后果:强制让线程停止有可能使一些请理性的工作得不到完成。
  • 使用return停止线程:调用interrupt标记为中断状态后,在run方法中判断当前线程状态,如果为中断状态则return,能达到停止线程的效果。

轻量级锁

加锁流程

  1. 判断对象处于”无锁”状态（即Mark Word 为 hashcode age 01）
  2. 线程在自己的栈帧中创建 Lock Record（锁记录）
  3. 把对象的 Mark Word 复制到 Lock Record 的 Displaced Mark Word 字段（图中保存的是 “hashcode age 0 01”，即无锁时的原样备份）
  4. 用 CAS 尝试把对象的 Mark Word 替换为”指向 Lock Record 的指针”，并置低 2 位为 00（图中从 Lock Record 指向 Object 的 “CAS” 箭头）
  5. 线程 Thread-0 进入同步块 A 时创建第一个 Lock Record（Displaced Mark Word = hashcode age 0 01，即无锁原始值）。进入同步块 B 重入时，CAS 会发现是自己持锁，于是创建第二个 Lock Record，其 Displaced Mark Word 为 null——这就是图中第一个 Lock Record 里写着 null 的原因：null 表示重入记录，不参与真正的锁释放。

解锁流程

  1. 取出当前 Lock Record
  2. 判断 Displaced Mark Word 是否为 null
  • 情况 A：Displaced Mark Word == null（重入记录）
    • 直接弹出该 Lock Record，不需要 CAS，解锁结束。
    • 对应图中第一个 Lock Record（内容是 null）。
  • 情况 B：Displaced Mark Word != null（首次加锁记录）
    • 用 CAS 把 Displaced Mark Word 写回对象的 Mark Word，恢复为无锁状态（01）。
    • CAS 成功 → 解锁完成，对象回到无锁态。
    • CAS 失败 → 说明期间锁已膨胀为重量级锁，需要走 Monitor 释放流程（唤醒等待线程）。

CAS是比较并交换：无锁、无阻塞，比重量级锁（互斥/系统调用）快，但是会出现ABA问题

偏向锁

  • 轻量级锁在没有竞争时(就自己这个线程),每次重入仍然需要执行CAS操作。
  • Java 6中引入了偏向锁来做进一步优化:只有第一次使用CAS将线程ID设置到对象的Mark Word头,之后发现
  • 这个线程ID是自己的就表示没有竞争,不用重新CAS。以后只要不发生竞争,这个对象就归该线程所有

  1. 偏向锁只会在第一次添加锁记录的时候进行CAS操作在对象头中添加线程id 并 改写biased_lock 的值。
  2. 第二次加入锁记录的时候只会判断对象头中的线程id是否是自己，而不进行CAS操作了。性能方面要比轻量级锁好。

一旦发生了锁冲突的都会升级成重量级锁

JMM（java内存模型）


当线程A对共享线程进行修改的时候，修改后会同步到主内存中，然后线程B同步主内存的变量。

  • JMM(Java Memory Model)Java内存模型,定义了共享内存中多线程程序读写操作的行为规范,通过这些规则来规范对内存的读写操作从而保证指令的正确性
  • JMM把内存分为两块,一块是私有线程的工作区域(工作内存),一块是所有线程的共享区域(主内存)
  • 线程跟线程之间是相互隔离,线程跟线程交互需要通过主内存

CAS

CAS的全称是:Compare And Swap(比较再交换),它体现的一种乐观锁的思想,在无锁情况下保证线程操作共享数据的原子性。

当线程A修改变量a成功后，a = 100; 这样在线程B修改的时候旧值A与内存中a不同，CAS就会通过自旋的方式，就是读取最新的变量的值即A=101后再次CAS操作。B就会修改成功。

CAS 你知道吗?

  • CAS的全称是:Compare And Swap(比较再交换);它体现的一种乐观锁的思想,在无锁状态下保证线程操作数据的原子性。
  • CAS使用到的地方很多:AQS框架、AtomicXXX类

volatile

  1. 保证线程间的可见性
  2. 禁止进行指令重排序

AQS

AQS也是一种锁机制，全称是 AbstractQueuedSynchronizer，即抽象队列同步器。它是构建锁或其他同步组件的基础框架

AQS与Synchronized的区别

synchronized AQS
关键字，c++/java语言实现 java 语言实现
悲观锁，自动释放锁 悲观锁，手动开启和关闭
锁竞争激烈都升级为重量级锁，性能差 锁竞争激烈的情况下，提供了多种解决方案

AQS常见的实现类

  • ReentrantLock 阻塞式锁
  • Semaphore 信号量
  • CountDownLatch 倒计时锁


当线程想要获取这个锁的时候就会把这个被 volatile修饰的state变量修改为 1 ，成功修改就获取到了锁，当其他线程来获取锁的时候发现state为1就会进入到FIFO先进先出的双向队列，其中维护着两个指针head和tail，当锁被释放的时候会唤醒对列中的head，线程进入队列是从尾端插入。

为了保证多个线程共同抢这个锁（修改state的值）的原子性，采用的是CAS

ReentrantLock的实现原理

ReentrantLock翻译过来是可重入锁，相对于synchronized它具备以下特点：

  • 可中断
  • 可以设置超时时间
  • 可以设置公平锁
  • 支持多个条件变量
  • 与synchronized一样，都支持重入

使用


ReentrantLock的公平锁和非公平锁的父类继承了AQS。

工作机制和AQS的基本相同。

ReentrantLock的实现原理

  • ReentrantLock表示支持重新进入的锁,同一个线程可以多次调用lock方法获取锁。
  • ReentrantLock主要利用CAS+AQS队列来实现
  • 支持公平锁和非公平锁,在提供的构造器的中无参默认是非公平锁,也可以传参设置为公平锁

synchronized和Lock有什么区别?

语法方面

  • synchronized 是关键字，源码再JVM中，用C++语言实现
  • Lock 是接口，源码由JDK提供，用java语言实现
  • 使用 synchronized 时，退出同步代码块锁会自动释放，使用Lock时需要手动调用 unlock 方法释放锁

功能方面

  • 二者都属于悲观锁，都具备互斥，同步，锁重入功能
  • Lock 提供了许多 synchronized 不具备的功能,例如公平锁、可打断、可超时、多条件变量
  • Lock 有适合不同场景的实现,如ReentrantLock,ReentrantReadWriteLock(读写锁)

新能方面

  • 在没有竞争时,synchronized做了很多优化,如偏向锁、轻量级锁,性能不赖
  • 在竞争激烈时,Lock的实现通常会提供更好的性能

死锁产生的条件是什么？

死锁：一个线程需要同时获取多把锁，这时就容易发生死锁

如线程t1持有A的锁等待获取B锁,线程t2持有B的锁等待获取A的锁。他们就这样一直僵持下去，导致死锁

如何进行死锁诊断

当程序出现了死锁现象，我们可以使用JDK自带的工具：jps和jstack

  • jps: 输出JVM中运行的进程状态信息
  • jstack：查看JAVA进程内线程的堆栈信息，查看日志

JDK提供了一个可视化工具 jconsole ，也可以进行死锁的诊断
