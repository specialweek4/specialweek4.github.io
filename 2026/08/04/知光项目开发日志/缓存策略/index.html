缓存策略

发表于2026-08-04|更新于2026-08-06|知光

我们先从整个的读写缓存流程看起

知文

知文数据库表设计

回源数据库都是查的这张表，数据库存储的是知文的元数据，正文存贮在OSS

Cache基础模块

该模块本身不主动读写业务数据，只负责创建 Caffeine Bean：

  • feedPublicCache：公共 Feed，本地缓存，TTL 15 秒，最大 1000。
  • feedMineCache：个人 Feed，本地缓存，TTL 10 秒，最大 1000。
  • knowPostDetailCache：知文详情，本地缓存，默认 TTL 30 秒，最大 5000。
  • HotKeyDetector：在内存中记录热点访问次数，每 10 秒轮转窗口，用于动态延长 Redis TTL。

流程

注意：我们在每步返回给前端之前都会更新用户态liked/faved，而计数（点赞数和收藏数）我们业务不同情况实时更新，什么时候更新下面都有标注。注意我们在进行回源的时候存入公共缓存Redis和Caffine的前写入计数，并将用户态设为null，防止污染。
但是因为我的发布不是属于公共的缓存，就是按用户id查的，这个在写入缓存的时候用户态正常填充。

更新用户态和计数的方法：

  • enrich方法：只更新用户态
  • mapRowsToItems: 用于从数据库中查找数据后填充计数和用户态，如果传入currentuserID则用户态正常填充，如果currentuserid传入为null表示让用户态为null。在我的发布和获得公共Feed的时候使用
  • enrichDetailResponse：在getDetail时使用这个方法比mapRowsToItems多了个 refreshCounts 是否需要从 CounterService 刷新计数（缓存命中时需要，DB 回源时不需要），userid一样的机制。

Knowpost知文模块

公共Feed

代码中把页面缓存（L1）和碎片缓存（L0）放到一个方法（assembleFromCache）中做了顺便补齐了用户维度的数据，因为L1要依赖于L0，所以可以看成二级缓存，但是L1,L2,L3的缓存时间互不影响。

键设计

缓存 Key 示例 过期时间

Redis ID 列表 feed:public:ids:20:{hourSlot}:1 60～89 秒
Redis 内容片段 feed:item:{postId} 60～89 秒，可按热度延长

读取流程

这样可能造成误报”还有下一页”，但是宁可误报，也不少读。这是读的兜底，事实上我们在写入的时候也是在满页的时候才把hasmore设为true。后端把hasmore传给前端，如果为true就可以显示加载更多。

完整流程

写入流程：

内容片段：单条知文的元数据（标题、描述、封面、作者信息、tags 等，不含计数和 liked/faved在返回前端的时候再补充）

写入本地缓存的流程是 使用分页查询从数据库中拿到数据 KnowPostFeedRow (每一行对应一个知文元数据) -> 经过mapRowsToItems方法将KnowPostFeedRow转换成FeedItemResponse（两者就多了liked、faved、点赞数、收藏数这四个，实际上就是将行数据复制到FeedItemResponse，再填充四个计数数据）-> 最后将分页查询的这几个知文元数据放到一个集合中作为FeedPageResponse存到本地缓存中。

对于反向索引使用于知文被编辑、发布、删除、修改可见性或置顶状态时，定位到那些页面包含包含了该知文，他是通过 一个知文 × 一个小时”对应一个 Redis Set。因为一个知文可能出现多个页面所以这个set力可能有多个pagekey。

为什么Caffeine页面是15秒？

本地缓存15秒过期，当知文更新的时候也会主动删除本地缓存中的页面。

  • Caffeine 是单机缓存，不同应用实例之间不共享。
  • 设置为较短的 15 秒主要是为了：
  • 吸收短时间内针对首页的高并发请求。
  • 避免多实例之间长期保留不一致的数据。
  • 知文编辑、发布、删除后，即使主动失效失败，15 秒后也能自动重建。
  • 控制整页对象的本地内存占用。

为什么 Redis ID 和内容片段是 60～89 秒？

基础 TTL 是 60 秒，并增加 0～29 秒随机抖动：
设计原因：

  • Redis 是多实例共享缓存，可以比 Caffeine 保存得更久。
  • 内容片段能被多个页面复用，适合比整页缓存拥有更长 TTL。
  • 60 秒能显著减少数据库 Feed 查询和知文基础信息查询。
  • 0～29 秒抖动使不同页面、不同知文不会在同一秒集中失效，防止缓存雪崩。
  • TTL 不设置得过长，避免知文编辑后长期返回旧片段。

为什么使用小时槽？

我们ID列表key、Hasmore 和 反向索引使用了小时槽，本地缓存并没有使用小时槽的设计，所以会导致一下行为：

  • 整点前 L1 命中：请求在 10:59:59 写入本地 feed:public:10:1:v1（数据来自 10 点的 Redis key），11:00:01 的请求如果还在 L1 的 15 秒 TTL 内，会直接返回这份”旧小时”的数据——本地 key 没变，所以 L1 不会察觉小时切换。

  • 整点后 L1 未命中：请求去查 Redis 时，hourSlot 已变成新值，走新 key feed:public:ids:10:{newSlot}:1，可能触发一次回源（受 singleFlight 保护）。

  • 命中 L2/L3 后，会重新 feedPublicCache.put(localPageKey, …)，覆盖成新小时的数据。

使用小时槽的主要目的是减少新内容发布后继续命中过旧列表的概率。除了等key自动过期，在整点过后当有请求来的时候，也会重建当前小时的ID列表key等，上一小时idkey不会被查询到会自动过期。

使用小时槽只是减少新内容发布后继续命中过旧列表的概率，现在依然有一个问题因为片段并没有小时槽，即使ID列表是当前小时的key，但是用到的片段可能是上个小时旧的数据。

热度检测机制

在触发回源的时候不会触发热度检测机制，只要每命中一个缓存页面（无论 L1 还是 L2），都会遍历该页的每条知文调用 recordItemHotKey(item.id())，适当延长片段缓存的的TTL

我的发布

也是分页查询，和公共Feed不同的是，不是采用片段组装的形式，而是在Redis中直接存一个页面的数据，存的是整页快照。

涉及的缓存键

缓存 Key 过期时间
Caffeine 页面 feed:mine:{userId}:{size}:{page} 10 秒
Redis 整页 JSON 同一个 Key 30～49 秒，可按热度延长

读取流程

如果在Redis缓存命中了，因为是整页快照其中的liked和faved是存入的时的所以调用enrich来刷新一下用户状态liked和faved。

写入流程

依旧时那一套

使用分页查询从数据库中拿到数据 KnowPostFeedRow (每一行对应一个知文元数据) -> 经过mapRowsToItems方法将KnowPostFeedRow转换成FeedItemResponse（两者就多了liked、faved、点赞数、收藏数这四个，实际上就是将行数据复制到FeedItemResponse，再填充四个计数数据）-> 最后将分页查询的这几个知文元数据放到一个集合中作为FeedPageResponse,写入到本地缓存中并返回给前端,不同的是这次是直接把整页数据装换成json字符串的形式存到 Redis 中。

为什么本地缓存只有 10 秒

“我的发布”包含：

  • 是否置顶
  • 发布状态
  • 当前用户的点赞/收藏状态
  • 用户刚刚发布或修改的内容

这些数据对当前用户而言更强调“修改后立即可见”，因此本地 TTL 比公共 Feed 的 15 秒更短，设置为 10 秒。

为什么 Redis 是 30～49 秒

相比公共 Feed 的 60～89 秒，个人页面 TTL 更短，原因是：

  • 用户刚发布内容后，希望列表快速出现新数据。
  • 置顶、取消置顶和修改内容后，希望快速看到变化。
  • 页面包含用户维度状态，陈旧容忍度更低。
  • 个人页面流量通常低于公共首页，没有必要长时间缓存。

增加 0～19 秒抖动仍然是为了避免大量用户页面同时过期

依旧热点 key 检测

失效策略

当前“我的发布”没有主动失效逻辑。

知文发布、修改、删除、置顶后不会立即删除：

因此主要依赖：

  • Caffeine 10 秒自动过期。
  • Redis 30～49 秒自动过期。
  • 热点页面最长可能保持到 150 秒。
  • 这一策略实现简单，但用户修改内容后可能短暂看到旧列表。

权限校验

为什么这里的Caffeine详情是 30 秒

详情页通常比单个 Feed 页面复用率高，因此本地 TTL 设置为 30 秒：

  • 热门知文详情能够在 JVM 内快速返回。
  • 比公共 Feed 的 15 秒更长，提高热点详情命中率。
  • 又不会长时间遮蔽知文编辑或权限变化。
  • 修改操作发生后还有主动删除作为保障。

为什么 Redis 详情是60 ~ 80秒

设计原因与 Feed 内容片段相似：

  • 详情序列化和数据库关联查询成本更高，适合更长 TTL。
  • Redis 跨实例共享，能降低数据库压力。
  • 60 秒在性能和新鲜度之间折中。
  • 0～29 秒随机抖动避免大量知文详情同时过期。
  • 热点详情可以进一步续期。

依旧有热点续期

每次查询该知文的时候都会进行热点检测。

空缓存为什么是30 ~ 60 秒

空值缓存的目的：

  • 防止恶意或错误请求不断查询不存在的 ID。
  • 避免缓存穿透，把压力直接打到数据库。
  • 随机 TTL 避免大量非法 ID 的空值缓存同时过期。

空值 TTL 不宜过长，因为：

  • 数据可能随后被创建或恢复。
  • 过长会让新的合法数据继续被判断为不存在。
  • 空值缓存只是临时保护，不应成为长期事实数据。

为什么只缓存大 V：

  • 大 V 的粉丝列表访问量通常更高。
  • 前几页访问频率远高于深分页。

  • 本地缓存无法在多个实例之间共享。
  • 关注事件当前不会主动清理 Caffeine。
  • 设置 10 分钟是为了限制陈旧数据的最长存在时间。

十二、当前实现中的注意点

  • 关注/取关事件只更新 Redis ZSet，没有更新或失效 Caffeine Top 缓存，可能陈旧 10 分钟。
  • isBigV() 注释表示根据粉丝数判断，但当前读取 ucnt 的偏移是第三段，实际上更像读取发文数，可能导致大 V 本地缓存无法按预期启用。
  • Redis ZSet 事件更新会刷新 TTL，活跃用户的列表 Key 可能长期不失效。
  • 事件异步更新存在短暂窗口：MySQL 关注已经成功，但 Redis 列表还没收到 Kafka 事件。
  • Redis 未命中且 MySQL 也为空时，没有写空列表缓存，重复请求可能持续查数据库。
