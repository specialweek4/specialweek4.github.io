订单超时自动取消

发表于2026-08-13|更新于2026-08-14|java面试

要实现自动取消我们需要用到延时任务：

我们来看一下几个非常常见的业务场景：

  1. 某电商平台，用户下单半个小时未支付的情况下需要自动取消订单。
  2. 某媒体聚合平台，每 10 分钟动态抓取某某网站的数据为自己所用。

这些场景往往都要求我们在某指定时间之后去做某个事情，也就是延时去做某个事情。

用其来实现订单超时自动取消：

方案一

每分钟执行定时任务：扫描MySQL数据库 取出未支付且超时的订单

  • 实现细节：
  • select * from orders where status = ‘未支付’ and order_time < (当前时间-15分钟) 为(status, order_time)创建联合索引
  • update orders set status = ‘取消’ where id = ? and status = ‘未支付’另外如果状态更新成功，才会去增加库存，否则不增加库存，这里可能又有一个问题，如果订单状态更新为关闭，但是库存增加失败了怎么办，解决方案：可以引入消息队列来异步增加库存，若失败则消息队列重试补偿
  • 优点是实现简单
  • 缺点是在数据量很大时可能会对数据库造成一定的压力，但只要创建好索引查询效率也很快,还有可能会有延时比如定时3分钟的话，最坏的延时就是3分钟，这会导致订单明明超时了但是用户依然可以看到，但是这个我们可以做优化。

针对延时优化:

由于定时任务的执行时间的不精确性，有些时候，订单可能已经超时了，但是用户还能查看到待支付的订单，这就是因为分钟级的定时任务恰好还没有执行，这时候，其实可以在用户查看订单时（即返回订单列表时），检查一下订单是否超时，这时候就把订单状态给他改成关闭，然后用户看到的订单就是已取消状态。这其实是一种被动关单的思想，被动关单就是当用户来查看时才去关闭超时订单。

常见面试题

问题：会不会存在重复关闭订单，重复增加库存，相当于增加了额外的库存？

答：不会，因为我们关闭订单是执行的SQL 其实是update orders set status = '取消' where id = ? and status = '未支付', 如果状态更新成功，我们才会去增加库存，因为where条件加上了 status = ‘未支付’, 即使有定时任务重复调度/消息重复消费，这个状态更新成功只能执行一次，也就只释放一次库存.

问题：如果订单状态设置为关闭，但是库存增加失败怎么办？

答：引入消息队列异步增加库存，若消费者内增加库存失败，则消息队列的机制重试补偿，多次重试依然失败则触发告警，人工介入排查原因修复

方案二

利用消息队列 (RocketMQ) 的延迟消息，在订单创建时发送延迟消息，在一定时间后，消息被消费关单

  • 优点：通过延迟消息，我们就可以将系统解耦，只需关注生产及消费消息即可
  • 缺点：
    • 大量无效调度：大部分的消息可能都是无效的，因为这些消息对应的订单可能都是已支付。
    • 消息可靠性：尽管消息队列能提供相对可靠的消息投递，但在极端情况下，消息丢失或重复消费依然可能发生。这会给订单的准确关闭带来风险，如订单未关闭或多次错误关闭

缺点一

举例：一天下单 1 万单，90% 的订单 5 分钟内就付款了，那么 30 分钟后：

  • 1 万条消息都被消费
  • 其中 9000 条查完状态发现是”已支付”，白跑一趟，只为了确认”不用关单”
  • 真正有用的只有 1000 条

缺点二

极端场景：消费者执行完关单逻辑，但在发送 ACK 确认之前宕机了 → MQ 认为没消费成功 → 消息重投 → 消费者又执行一遍关单逻辑。

方案三

利用 Redis 过期监听，为每个订单设置一个带TTL的key，并接收key过期消息执行关单操作

  • 实现细节：在 redis.conf 中，加入一条配置 notify-keyspace-events Ex 开启过期监听，然后在代码中实现一个 KeyExpirationEventMessageListener，就可以监听key的过期消息了。这样就可以在接收到过期消息的时候，进行订单的关单操作。
  • 优点：由于redis 的高性能，所以我们在设置key，或者消费key 时，速度上是可以保证的。
  • 缺点：
    • redis 自动过期的实现方式是：定时任务离线扫描并删除部分过期键；在访问键时惰性检查是否过期并删除过期键。
    • 也就是说，由于redis 的key 过期策略原因，当一个key 过期时，redis 从未保证会在设定的过期时间立即删除并发送过期通知，自然我们的监听事件也无法第一时间消费到这个key，所以会存在一定的延迟。实际上，过期通知晚于设定的过期时间数分钟的情况也比较常见。

总结

对于单体项目订单量不大，所以使用方案一

如果后续订单量太大，定时任务扫描MySQL数据库耗时很长，每分钟扫描数据库的方案不再适用，也可以考虑引入消息队列的延迟消息来完成。同时我们应该设计一个兜底策略，假如少量的消息丢失，我们可以 (每天凌晨 / 每隔N个小时) 跑一次定时任务，批量将未支付的订单进行关闭。

衍生问题支付和关单的并发问题

支付和关单的并发：使用乐观锁解决订单支付和关单的并发问题；

如果一笔订单在 “超时取消” 的那一刻 “用户刚好付款” 了

支付成功的回调 和 超时关单 在并发的场景下，都查询到订单的 状态为 “未支付”

此时后台对于 “支付成功的处理” 以及 “超时关单的处理”。这两者应当是一个成功，一个失败

所以要保证并发场景下一个成功、一个失败。我觉得有两种方案

方案一

  • 方案一：数据库乐观锁

    • 超时关单的处理中：查询出未支付状态的订单后，执行 update orders set status = ‘取消’ where id = ? and status = ‘未支付’
    • 支付成功的处理中：查询对应订单确认状态是未支付后，执行 update orders set status = ‘已支付’ where id = ? and status = ‘未支付’
    • 注意这两个SQL中的where条件中都加了 status = ‘未支付’，这就能保证只有一个执行成功，另外一个一定失败，这就是乐观锁的方式。（当然如果你要使用version版本号的方式去实现乐观锁也可以）

  • 方案二：一锁二判三更新

    • 对于状态的变更，如果有并发场景，常见的解决方式是一锁二判三更新，即第一步先加分布式锁，锁住该订单，第二步判断订单状态是否未支付，若是则第三步更新订单状态
