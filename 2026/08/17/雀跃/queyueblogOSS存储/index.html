blogOSS存储v1.0

存储设计

核心流程

雀跃就是对OSS对象存储的简单实现,整体流程如下：

读取的时候后端把 objectKey 拼成公开访问 URL 返回给前端

具体流程展示：

第一步：前端请求预签名（StorageController.java）

前端发起 POST /storage/presign，body 是 PresignRequest

第 二 步：进入 StorageController.presign()

进入presign方法后做四件事：

1.登录校验：UserHolder.getUser() 拿当前登录用户，没登录直接返回”请先登录”。（/storage/** 不在拦截器放行列表里，所以未登录在拦截器就被挡了，这里属于双保险。）V1.0版本使用ThreadLocal实现的，拿的USER信息，后续使用Secuity实现。

2.博客归属校验：

这里我设计的是传图片之前要先有这个草稿的id。

3.生成 objectKey ：根据前端传过来的scene来走对应的分支（这里以blog_cover为例）：

即blogs/23/cover/1f2e3d4c-xxxx.png。

4.推断后缀（方法中调用normalizeExt()）：如果前端传了 ext: “png”，直接规范化成 .png；如果没传 ext，会按 contentType 映射比如：image/jpeg→.jpg、image/png→.png、image/webp→.webp、其余 .img。

第三步 后端生成签名 URL（OssStorageService.generatePresignedPutUrl()）

这里的签名原理：SDK 用 AccessKeySecret 对 PUT + bucket + objectKey + 过期时间 + Content-Type 做 HMAC 签名，拼进 URL 的 query 参数。所以：

  • 因为把 contentType 放进签名中了，所以前端需要带上contentType,用于验签，在响应 headers 返回了。
  • 600 秒过期 —— 过期后 URL 失效，需要重新申请。

第四步: 返回给前端（StorageController）

第 五 步：前端直传（不经过后端）

前端拿 putUrl，直接 PUT 图片二进制，带上 Content-Type: image/png 头。OSS 验证签名、过期时间，通过后存储对象。图片字节流从头到尾没经过后端服务器 —— 这就是预签名方案的核心价值。

第 六 步：objectKey或URL 落库

前端把 objectKey或访问URL 塞进博客数据，调 POST /blog/draft（BlogController.saveDraft()，BlogController.java）保存草稿。此时 Blog.coverUrl = “http://queyue.oss-cn-hangzhou.aliyuncs.com/blogs/23/cover/xxx.png“ 存进 tb_blog.cover_url 字段。如果是正文的话存的是Objectkey

第 七 步：读取时拼 URL

别人看博客时，前端调 GET /blog/detail/23（queryBlogById，BlogController.java），后端把 objectKey 通过 OssStorageService.publicUrl()（OssStorageService.java）拼成可访问地址，图片的话存的就是地址不需要拼接了：

前端拿到 contentUrl 后直接加载图片。

第 八 步：换图 / 删除

用户换封面时，旧图要清理：前端调 DELETE /storage/object?key=blogs/23/cover/旧uuid.png（StorageController.java）→ OssStorageService.deleteObject()（OssStorageService.java）→ SDK 的 client.deleteObject(bucket, key) 删除对象。

blogOSS存储2.0

V1.0 的痛点

2.0 是在 V1.0 基础上的一次重构，先回顾 1.0 埋下的两个问题：

  1. 预签名直接发正式区 key：1.0 里 presign 一步就生成了 blogs/{postId}/cover/{uuid}.png 这样的正式 key，前端传完后如果用户放弃编辑、换图、删图，旧对象就永远残留在 blogs/ 正式区，变成没人引用的垃圾。
  2. 删除依赖前端主动调用：1.0 里清理旧图靠前端调 DELETE /storage/object，漏调就是垃圾文件，调错 key 还可能误删正在使用的文件。
  3. 1.0版本有一个问题当用户在创建草稿的时候前端提交图片后保存草稿，如果再取消上传图片，那么OSS哪里会删除图片，但是数据库依然记录的图片的访问URL，当用户查看草稿的时候就会查不到图片报错。

所以 2.0 的核心思想是：上传先进”临时区”，提交时才搬进”正式区”，数据库只存正式区引用，垃圾回收只针对临时区——从机制上保证永远不会误删被引用的文件。

2.0 存储设计

数据库设计没变，变的是 OSS 侧的 key 规划：

OSS 对象分成两个区：

分区 key 前缀 说明
临时区 unconfirmed/{postId}/... 预签名直传的目标，还没确认，OSS 生命周期规则只清理这个前缀
正式区 blogs/{postId}/... confirm 确认后搬入，数据库只保存这里的引用，生命周期绝不触碰

核心流程

未提交的临时对象由 OSS 生命周期规则自动回收（只删 unconfirmed/ 前缀），前后端都不用写删除代码。

具体流程展示

第一步：前端请求预签名（StorageController.presign()）

请求体和 V1.0 完全一样，变化发生在后端生成的 objectKey——全部进临时区：

和 1.0 的区别：

  • 封面 key 从 cover/{uuid}.png 变成固定的 cover.png——同一篇博客换封面时旧临时对象被直接覆盖，临时区不会堆积。
  • 正文 key 固定为 content.md，反复保存覆盖旧版本。
  • 多图 key 按天分目录：images/20260818/{uuid}.png，避免单目录对象过多。

正文和封面都是固定的key可以覆盖。

第二步：生成签名 URL（OssStorageService.generatePresignedPutUrl()）

与 V1.0 完全一致：PUT + objectKey + 过期时间 + Content-Type 参与 HMAC 签名，600 秒过期。

第三步：前端直传临时区

前端拿 putUrl 直接 PUT 二进制到 OSS，字节流不经过后端。此时对象落在 unconfirmed/ 临时区，还不是正式文件。

第四步：前端只保留临时引用，不落库、不删 OSS

这是 2.0 前端最大的行为变化。1.0 上传完就把 objectKey 存进草稿；2.0 上传完只把 {url, objectKey} 放进本地 state（StoredFile）：

  • 换封面、删图只改本地引用，不发任何 OSS 删除请求——被抛弃的临时对象交给生命周期规则回收。
  • 正文也是先直传临时区：presign("blog_content", id, "text/markdown", "md")，把编辑器文本包成 Blob PUT 上去，返回临时 contentKey。
  • presign 要求先有 postId，所以前端第一次上传/保存时会”懒创建”一个空草稿（ensureDraft → POST /blog/draft 空 body 拿 id）。

第五步：确认提交 POST /storage/confirm（2.0 新增的核心接口）

保存草稿 / 发布前，前端把当前引用的临时区对象一次性交给后端确认：

后端对每个 key 做”归属校验 + 搬移”（StorageController.confirmObject()）：

搬移用的是 OSS 同桶服务端复制（OssStorageService.copyObject()），字节流全程在 OSS 内部流转，不经过后端服务器：

接口返回正式区引用：

三个设计细节：

  • 幂等：blogs/ 开头的 key 原样返回，前端重复 confirm 不会重复搬移。
  • 源对象不急着删：复制成功后临时对象删不删都行，删失败也不影响提交，由 unconfirmed/ 生命周期规则兜底。
  • segment 校验：cover 只接受 .../cover、content 只接受 .../content.、image 只接受 .../images/ 的 key，且必须挂在当前 postId 下，防止搬移别人的对象。

第六步：用正式区引用落库（BlogEditPage.buildPayload()）

前端拿到 confirm 的返回后，用正式区 URL 组装载荷存草稿 / 发布，同时把本地 state 同步替换成正式引用（否则页面还显示临时 URL，生命周期到期会裂图）：

数据库里最终存的都是 blogs/ 正式区引用。

第七步：读取时拼 URL——与 V1.0 相同

GET /blog/detail/{id}（BlogController.queryBlogById()）里，后端把 contentObjectKey 通过 OssStorageService.publicUrl() 拼成可访问地址放到 contentUrl 返回，前端直接 fetch；封面和图片库里存的就是 URL，无需拼接。

第八步：垃圾回收——2.0 的核心收益

  • 未提交的临时对象：传了图但没保存就退出，unconfirmed/ 里的对象由 OSS 控制台配置的生命周期规则自动回收（例如”3 天后自动删除 unconfirmed/ 前缀对象”），前后端一行删除代码都不用写。
  • 换封面/删图产生的正式区孤儿：本地只移除引用，文件暂留 blogs/，交给”未来的差集 GC”（拿数据库被引用的 key 集合与 OSS 实际对象做差集统一删除）清理。
  • 删笔记：软删除 status=2 进回收站，7 天内可恢复（BlogServiceImpl.delete()）。
  • 1.0 的 DELETE /storage/object 接口在 2.0 已从控制器移除，OssStorageService.deleteObject() 方法保留但不再由前端触发。

2.0 其它改动

  • normalizeExt 支持正文场景：text/markdown→.md、text/html→.html、text/plain→.txt、其余 .bin；图片类型映射与 V1.0 相同。
  • OssProperties 新增 publicUrl 配置项：publicUrl() 统一拼接访问地址，不再硬编码域名。
  • 拦截器配置不变：/storage/** 仍不在放行列表里，presign 和 confirm 都要求登录（MvcConfig.java），TODO 依旧是后续换成 Security。

以后要做的事

  1. 正文每次保存都是全量重传 + 全量确认，这个倒时候优化一下，可以加一个算Hash去重
  2. 后期用到Security/JWT需要替换
  3. 加缓存
  4. 回收站的开发
  5. 针对OSS的GC
  6. 图片串行for循环的问题

已知痛点:全量重传、串行 copy、无 CDN、固定 key 可枚举、差集 GC 未落地;

计划 V3.0:增量确认(只搬 unconfirmed 新 key)、正文 hash 去重、并发 copy、读侧挂 CDN;

到后面可能要改成登记薄GC的模式:临时区 vs 登记表 GC 的取舍。

V2.1

  1. 前端加入了正文Hash对比，和confirm 增量化(前端过滤 + 后端天然幂等)现在 buildPayload 把全部图片 key 传进 confirm,其实只有 unconfirmed/ 前缀的是”新对象”,其余都是上次确认过的正式区引用,根本不用再传
  2. 后端之前每次保存 N 张图要建 N+1 个客户端、每个都重新握手，现在复用同一条连接池，就是把 OSS 注册成单例 Bean，复用了。

本次升级减缓了写放大。改标题保存 = 0 次 OSS 操作；新增图片 = N 次元数据复制（服务端秒级，不走后端流量）。临时区的代价降低。

v2.1.1

前端新增快照对比，如果用户不该任何东西连点保存，在以前的版本中每次都 1 SELECT + 1 UPDATE 写库，现在第一次之后全部本地拦截，0 请求

未来计划对于热门笔记，添加冷数据机制，只推送热门笔记和最新笔记

v3.0

增加商铺和商品上传：设计的话是这样的，用户在未提交申请之前选择的图片都会放到临时区，提交申请后会直接放到正式区，申请通过后直接复制申请表中的数据放到正式表中。具体是这样改的

1.保持原有的PresignResponse（预签名响应体）

2.商铺和商品申请DTO

StorageController

ShopApplicationServiceImpl
