雀跃计数模块后端代码设计与讲解

一、设计亮点

使用BitMap在Redis中记录用户行为（是否点赞，收藏），SDS快照(二进制GET + 聚合桶)

dirty 脏版本 + CounterCheckpointJob：每 30 秒把逻辑计数写回 tb_blog.liked/favorites（热榜排序用），批次完成后失效一次热榜缓存 L1/L2；

BitmapStateReader：整页 pipeline GETBIT 批量用户态

counter_read.lua：原子读取“SDS + 聚合桶”的逻辑计数

关注/粉丝计数由MySQL事务维护

counter_read.lua 逻辑同时读（SDS + 桶，立即正确）

三、Schema 与 Key

3.1 CounterSchema —— v1 五指标位固定结构

counter/schema/CounterSchema.java

SDS 布局（固定 20 字节，大端无符号 Int32 × 5）：

字节偏移 下标 含义
0 0 read（预留，恒 0）
4 1 like
8 2 fav
12 3 comment（预留，恒 0）
16 4 repost（预留，恒 0）
  • 预留位让评论/转发等指标将来不换 key、不迁移数据即可扩展
  • 没有在上面名单的未知指标由 SUPPORTED_METRICS 白名单过滤，Controller 层拒绝非法 metric。

3.2 CounterKeys —— Redis Key生成

counter/schema/CounterKeys.java

  • 所有计数键不设 TTL；dirty 是检查点专用的逻辑标记。

4.2 CounterServiceImpl —— 核心实现

counter/service/impl/CounterServiceImpl.java

  1. toggle：TOGGLE_LUA 只负责位图事实（位图中对应位置值的修改），返回 1 才代表”状态确实变了”；变化后在 Java 里同步写聚合桶（HINCRBY，field=指标下标）和脏版本（INCR）。后期准备将这两个同步写改成kafka异步写。
  2. getCounts：读侧走 counter_read.lua 拿“SDS + 未刷桶”的逻辑计数（原子，不会漏算/重算）；返回 -1（缺失）或 -2（长度异常）时触发 rebuild 后重读。
  3. rebuild：按位图事实重建 —— SCAN bm:{metric}:{etype}:{eid}:* 找到全部分片，pipeline BITCOUNT 求和，写入各指标偏移，最后清理聚合桶对应字段避免重复加算。Redisson 锁/限流/退避“以后再添加”，目前这里是无锁直做。后期准备加上Redssion走多实例
  4. getCountsBatch：整页 pipeline EVALSHA，一次往返；缺失/异常按零值降级并记日志。使用toLong 兼容 String/byte[]/Number 三种反序列化形态。
  5. isLiked/isFaved：GETBIT直接获得位图状态，毫秒级，不依赖 SDS。

五、聚合任务（每秒折叠）

counter/job/CounterAggregationJob.java

  • 逐字段“SDS 加增量 → 桶扣增量”，桶字段归零删除、整桶清空后删 key；SDS 缺失时 Lua 自动零初始化 20 字节。
  • 用 SCAN 分批（每轮最多 200 个桶）。
  • 单字段折叠失败只跳过该字段（留存，下一轮重试），不影响其他桶。

六、MySQL 检查点任务

counter/job/CounterCheckpointJob.java

  • 脏版本键形如 dirty:v1:blog:123，按 : 解析出实体类型与 ID；只有 blog 实体（ID 为数字）才写 tb_blog。
  • dirty_ack.lua 确认版本未变化才删脏键：写库期间又有新点赞则保留下轮同步；数据库故障不删键，天然重试。
  • 一批同步完成后只失效一次热榜 L1/L2，名次按检查点周期（约 30 秒）刷新。

7.2 CounterController（通用计数读取接口）

7.3 BlogController 博客端点

  • unlike/favorite/unfavorite 同构，分别调 unlike/fav/unfav，返回 CounterActionResult(blogId, active, changed, 实时逻辑计数)。
  • 写前验证博客已发布（防止对不存在的实体造位图键），替代旧实现中的存在性短缓存。
  • 详情页/个人页/关注流通过 getCounts/getCountsBatch/BitmapStateReader.getFlagsBatch 返回前覆盖计数与用户态。

7.4 BitmapStateReader —— 整页批量用户态，填充公共缓存

counter/service/BitmapStateReader.java（关键逻辑）

同一用户整页 chunk/bit 固定，每篇博客两个 GETBIT 合并进一次 pipeline。

八、脚本配置与预加载

counter/config/CounterScriptConfig.java

  • TOGGLE_LUA、INCR_FIELD_LUA、DECR_FIELD_LUA 内联在类里（setScriptText），Spring 的 script executor 会自动 EVALSHA/EVAL 并处理 NOSCRIPT。
  • 两个资源 Lua 由 CounterScriptInitializer 启动时 SCRIPT LOAD 预加载；pipeline 批量读遇到 NOSCRIPT 会自动补加载重试。

十、与三级缓存的配合

计数模块不感知缓存层。三级缓存只缓存稳定公共字段（HotBlogBaseItem），返回前由：

  1. CounterService.getCountsBatch("blog", ids, ["like","fav"]) 覆盖实时计数；
  2. BitmapStateReader.getFlagsBatch 补齐 isLike/faved；
  3. FollowStateService.getBatch（qy:state:follow:*，10~12 分钟）补齐 followed；

点赞/收藏不失效任何缓存；MySQL 检查点批次完成后由 CounterCheckpointJob 触发一次热榜 L1/L2 失效。详见《雀跃Feed三级缓存后端代码设计与讲解.md》。

十一、V3.0版本的规划

以后（P1）接入 Kafka 时的切换点：在CounterServiceImpl.toggle() 里变化后的两行（写桶 + INCR 脏版本）改为 CounterEventProducer.publish(...)；新增 CounterAggregationConsumer消费事件写聚合桶；CounterAggregationJob 的折叠逻辑可直接复用为消费者的定时 flush。其他的都不用变。
