雀跃：商铺、商品与优惠券申请审核后端改造方案

本文只描述改造方案和示例代码，不修改当前项目源代码。

采用“独立申请表”方案：商铺和商品申请先持久化到 MySQL 申请表，管理员审核通过后在事务中生成正式记录；普通优惠券和秒杀优惠券均由已审核店铺的店主自主创建，直接写入正式优惠券表。Redis 只用于草稿、缓存和防重复提交。

一、业务边界

把“商品”和“优惠券”作为两个独立业务对象：

  • 商品：店铺实际售卖的商品，例如奶茶、套餐、蛋糕；有名称、图片、价格、库存、上下架状态。
  • 优惠券：店铺发放的代金券/折扣券，对应当前项目的 tb_voucher；有支付金额、抵扣金额、使用规则、有效期和优惠券状态。

商品和优惠券分开建模；审核策略为：商铺和商品必须管理员审核，普通优惠券和秒杀优惠券均由商家自主发布：

优惠券默认属于店铺，不强制绑定某个商品。若以后需要“仅适用于某件商品”，再给优惠券增加可选 product_id，但仍不把优惠券和商品合并成一张表。

二、当前项目与改造目标

当前项目已有：

  • tb_shop/Shop，以及直接写入的 POST /shop；
  • tb_voucher/Voucher，当前代表优惠券；
  • GET /shop/**、GET /voucher/** 公开查询；
  • JWT 的 sub 为用户 id；
  • Redis 店铺详情缓存。

当前没有商品表，因此需要新增商品领域。改造后：

  1. 普通用户不能直接写商铺、商品正式表；
  2. 商铺和商品使用独立申请表，审核通过后才创建正式记录；
  3. 普通优惠券由已审核店铺的店主直接创建；
  4. 秒杀优惠券由已审核店铺的店主自主创建，不经过管理员审核；
  5. 店主只能操作自己店铺下的申请和正式商品/优惠券；
  6. 客户端只查询正式表中已上架的数据；
  7. tb_voucher.status 继续只表示优惠券销售状态，不表示审核状态。

五、商铺申请流程

1. DTO 和接口

申请人只填写地址，不需要手动填写经纬度。管理员审核通过时必须补齐并校验 x/y；拒绝申请时可以不填写坐标。

方法 路径 权限 说明
POST /merchant/shop-applications 登录用户 提交商铺申请
GET /merchant/shop-applications/mine 登录用户 查看自己的申请
PUT /merchant/shop-applications/{id} 申请人 修改待审核/已拒绝申请
GET /admin/shop-applications 管理员 分页查看申请
PUT /admin/shop-applications/{id}/audit 管理员 通过或拒绝

2. 提交和审核

提交申请只插入 tb_shop_application，不调用 shopService.save()。审核通过时在一个 @Transactional 方法中：

  1. 锁定并确认申请仍为待审核；
  2. 管理员根据地址补齐经纬度，并校验经度范围 [-180,180]、纬度范围 [-90,90]；
  3. 坐标缺失或无效时不能审核通过，只能退回补充或拒绝；
  4. 创建正式 tb_shop，写入审核补齐的 x/y，并初始化 sold/comments/score；
  5. 将生成的 shop.id 回写 approved_shop_id；
  6. 将申请状态改为已通过；
  7. 必要时写 tb_audit_record。

审核更新必须带旧状态条件，防止重复生成正式店铺：

正式商铺创建时使用同一组审核坐标：

实际实现建议让实体字段使用 BigDecimal，避免经纬度在 Java double 与数据库 DECIMAL 之间反复转换。

拒绝时更新为 audit_status = 2 并要求填写 reject_reason。待审核或已拒绝申请允许申请人修改；已通过申请对应正式商铺，后续资料变更应走正式商铺编辑流程。

七、优惠券流程（普通券和秒杀券均自主发布）

1. DTO 和接口

普通优惠券不需要提交管理员审核申请，仍应使用独立 DTO：

方法 路径 权限 说明
POST /merchant/shops/{shopId}/vouchers 店主 创建普通优惠券（type=0）
PUT /merchant/vouchers/{id}/status 店主 普通优惠券上架/下架
POST /merchant/shops/{shopId}/seckill-vouchers 店主 创建秒杀优惠券（type=1）
PUT /merchant/vouchers/{id}/status 店主 秒杀优惠券上架/下架

1. 普通优惠券直接创建

服务端必须确认店铺存在、已审核通过，且当前用户是店主或管理员；如果 productId 不为空，还要确认商品属于该店铺且已审核通过。请求中的 shopId 使用路径参数，不能信任请求体。

普通优惠券无需写申请表或等待管理员，但金额、折扣比例、有效期、使用规则、重复领取限制等必须做服务端校验，并保留管理员强制下架能力。

2. 秒杀券直接创建

秒杀券不需要管理员审核，也不进入申请表。店主提交时必须校验店铺归属、商品归属、库存大于 0、开始时间早于结束时间、金额规则和时间范围，然后在同一个 @Transactional 方法中创建 tb_voucher(type=1,status=2) 与 tb_seckill_voucher。

创建失败时事务整体回滚，不能留下只有 tb_voucher 没有秒杀库存的半成品。管理员仍保留强制下架和风控能力。

九、Redis 的正确使用方式

Redis 可用于：

  • shop:application:draft:{userId}、product:application:draft:{userId}:{shopId}、voucher:draft:{userId}:{shopId} 草稿；
  • 提交锁，防止重复点击；
  • 正式店铺、商品和优惠券列表缓存。

提交成功后以申请表为唯一事实来源，草稿可以删除。不要把完整申请只放 Redis 等待审核。

审核通过后清理对应正式数据缓存：店铺详情/列表、商品列表、优惠券列表。

十、建议新增或调整的代码文件

商品和优惠券必须有不同的实体、Mapper、Service、DTO、Controller；不要让 Voucher 继承或复用 Product。

十一、事务、并发和安全要求

  • 商铺、商品申请审核通过使用 @Transactional；普通券和秒杀券创建也应使用事务；
  • 申请人 id 从 JWT 获取，不能由请求体传入；
  • 商品/优惠券通过 shop_id 反查店主，防止跨店操作；
  • 优惠券指定 product_id 时校验商品属于同一店铺且已审核通过；
  • 审核通过前不创建正式商铺或商品；普通券和秒杀券按服务端校验后直接创建；
  • 商品库存、优惠券库存和价格做服务端校验；
  • 正式表的统计字段、销售状态、创建时间不能由普通用户直接控制；
  • 记录商铺/商品管理员审核人、时间、原因，必要时写入 tb_audit_record；
  • 普通券和秒杀券创建使用提交锁或业务幂等键，防止重复点击生成重复券。

十二、推荐实施顺序

  1. 增加 tb_user.role、tb_shop.owner_user_id；
  2. 创建 tb_shop_application、tb_product、tb_product_application；
  3. 增加 JWT role claim、Spring Security Authority 和管理员路径；
  4. 实现商铺申请与审核；
  5. 实现商品申请与审核，新增商品公开查询；
  6. 实现普通优惠券和秒杀优惠券自主创建；
  7. 实现店主独立的商品/优惠券上架下架；
  8. 接入缓存清理、审核日志和幂等控制；
  9. 补充越权、重复审核、跨店、未审核不可见、商品券归属校验测试。

十五、实现完成后的最终检查

完成代码后至少验证以下场景：

  1. 普通用户不能访问 /admin/**；
  2. 未登录用户不能提交商铺、商品或优惠券；
  3. 用户提交商铺后，tb_shop 没有记录，只有 tb_shop_application 有记录；
  4. 管理员不补坐标时不能通过商铺审核；
  5. 商铺审核通过后，事务内生成 tb_shop，申请表记录 approved_shop_id；
  6. 未审核商铺不能提交商品或普通优惠券；
  7. 商品审核前不能出现在商品公开列表；
  8. 普通优惠券可由店主直接创建，但不能跨店创建；
  9. 秒杀券可由店主直接创建，且必须同时生成 tb_voucher 和 tb_seckill_voucher；
  10. 普通券和秒杀券重复点击时不能生成非预期重复记录；
  11. 店主不能修改其他店铺的商品、普通券或秒杀券；
  12. 审核通过/优惠券上架后，相关 Redis 缓存被清理。
