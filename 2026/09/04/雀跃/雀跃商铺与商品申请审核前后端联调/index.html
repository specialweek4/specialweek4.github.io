雀跃商铺与商品申请审核前后端联调

发表于2026-09-04|更新于2026-09-04|雀跃

业务设计

  • 商铺必须管理员审核；
  • 商品必须管理员审核；
  • 普通优惠券由已审核店铺的店主自主创建；
  • 秒杀优惠券由已审核店铺的店主自主创建，不需要管理员审核；
  • 用户申请商铺时只填写地址，不要求手动填写经纬度；
  • 经度和纬度由管理员审核时补齐，审核通过后才写入正式 tb_shop；
  • 商铺和商品申请数据先写入 MySQL 申请表，审核通过后才创建正式业务记录；普通券和秒杀券直接写入正式优惠券表。

Controller MerchantShopApplicationController：

Controller 调用 ShopApplicationService.apply，Service 执行以下步骤：

  1. 校验 typeId 是否存在；
  2. 校验名称、图片、地址和营业时间长度；
  3. 从 JWT 获取 applicantUserId；
  4. 设置 auditStatus = 0；
  5. 将申请写入 tb_shop_application；
  6. 返回申请 id。

此时不调用 ShopMapper.insert，所以 tb_shop 中还没有正式商铺。

管理员审核商铺

前端访问：

审核拒绝请求体：

AdminShopApplicationController 从路径上取得该次申请的id 调用 ShopApplicationService.audit。通过时 Service 必须在同一个事务中：

  1. 查询申请并确认 audit_status = 0；
  2. 校验 x、y 不为空且范围有效；
  3. 创建 tb_shop，把申请资料复制过去；
  4. owner_user_id 写申请人的 id；
  5. 初始化 sold=0、comments=0、score=0、business_status=1；
  6. 更新申请的 audit_status=1、audited_by、audited_time、approved_shop_id、x、y；
  7. 更新申请成功调用auditRecordMapper.insert 写入审核历史
  8. 将用户的role改为商家
  9. 清理 cache:shop:{shopId} 和店铺列表缓存。
  10. 返回正式商铺的id。

审核拒绝时不创建 tb_shop，只把申请更新为 audit_status=2 并保存 reject_reason。

普通优惠券：商家自主发布

创建普通优惠券

前端访问：

请求体：

VoucherController 接口接收 VoucherCreateRequest，不要直接接收 ,通过VoucherServiceImpl.createNormal 完成：

  1. 用setNX来防止重复复提交
  2. 查询正式店铺并确认营业状态；
  3. 校验店主归属；
  4. 校验 actualValue >= payValue > 0；
  5. 如果传 productId，确认商品属于同一店铺且已上架；
  6. 强制设置 type=0、status=2、createdBy=当前用户；
  7. 插入 tb_voucher；
  8. 返回优惠券 id。

普通优惠券默认下架，店主再调用状态接口上架；如果业务要求创建即上架，可以由 Service 设置 status=1，但不能让前端直接提交任意 status。

创建秒杀券

前端访问：

请求体：

这个秒杀卷是用户支付 1 员来购买 能够抵 30 元的例子

VoucherServiceImpl.createSeckill 必须校验店铺已审核通过且当前用户为店主（管理员可作为运维角色），并校验商品归属、库存、金额和时间。通过校验后，在同一个事务中：

  1. 插入 tb_voucher，设置 type=1、status=2、created_by=当前用户；
  2. 插入 tb_seckill_voucher，只写入库存、开始时间和结束时间；
  3. 一步失败则整体回滚，不能留下不完整的秒杀券。

优惠券公开查询

前端访问现有接口：

VoucherMapper.xml 的查询仍可同时返回普通券和秒杀券，但只读取正式表且 v.status=1：

因此：

  • 普通券创建后，店主上架即可展示；
  • 秒杀券创建成功后，店主上架（status=1）且到达设定时间后即可展示；
  • 商铺、商品申请表中的待审核数据永远不会被客户端公开查询。

前端联调顺序

  1. 登录并保存 access token；
  2. 普通用户提交商铺申请，确认只出现 tb_shop_application；
  3. 管理员查询申请列表；
  4. 管理员补齐坐标并通过审核；
  5. 普通客户端查询店铺，确认可以看到正式商铺；
  6. 店主提交商品申请；
  7. 管理员审核商品，确认客户端审核前看不到商品；
  8. 店主创建普通优惠券并上架，确认无需管理员审核即可展示；
  9. 店主直接创建秒杀券；
  10. 确认创建事务同时生成 tb_voucher/tb_seckill_voucher，且无需管理员审核；
  11. 店主上架秒杀券后确认客户端在有效时间内可见；
  12. 测试跨店操作、重复提交、库存/时间校验和未登录访问。

常见错误

我在测试中出现了以下的问题，直接问AI就行。

申请成功但客户端看不到

这是正常现象。商铺和商品需要审核；优惠券创建后默认下架，需店主上架。秒杀券没有审核申请，先检查创建接口返回和正式表记录。

审核通过后仍看不到店铺

检查：

  • tb_shop 是否生成；
  • approved_shop_id 是否回写；
  • business_status 是否为 1；
  • 店铺详情/列表 Redis 缓存是否清理；
  • 客户端请求是否仍使用旧数据。

普通优惠券创建失败

检查：

  • 店铺是否已经审核通过并存在于 tb_shop；
  • JWT 用户是否是店主；
  • 金额单位是否为分；
  • actualValue 是否大于等于 payValue；
  • productId 是否属于同一店铺。

秒杀券创建后购买失败

检查：

  • 是否同时创建 tb_voucher 和 tb_seckill_voucher；
  • voucher.type 是否为 1；
  • status 是否已上架；
  • 秒杀开始/结束时间和库存是否正确；
  • tb_voucher 与 tb_seckill_voucher 是否在同一事务中创建；
  • 当前时间是否处于秒杀开始/结束时间范围内。

最终联调状态流转

就是看商铺和商品申请是否持久化、审核是否幂等、秒杀券两张正式表是否原子创建、店主是否只能操作自己的店铺，以及客户端查询是否只读取正式且上架的数据。
