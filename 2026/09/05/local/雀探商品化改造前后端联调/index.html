雀探商品化改造前后端联调

发表于2026-09-05|更新于2026-09-05|local

本文用于说明雀探从“店铺发现”改为“商品发现”后的前后端联调路径。文中的方法名、DTO 和接口是本次改造建议的落点；当前代码中 ProductController 仍然直接调用 ProductMapper，联调前需要按本文把查询逻辑收敛到商品查询服务。本文只描述调用关系，不直接修改项目代码。

一 打开雀探商品发现页

前端访问 /products，由 ProductListPage（可以先沿用现有 ShopListPage.tsx 文件名）渲染商品列表。旧地址 /shops 建议保留兼容路由，跳转到 /products，这样旧书签不会失效。

页面初始化时，ProductListPage 从 URL 读取 q、categoryId、current、size、sort。如果没有传参数，默认值为 q=""、categoryId=null、current=1、size=20、sort="newest"。

然后前端调用 productService.discover(q, categoryId, current, size, sort)。该方法通过 apiFetch 发起：

后端请求进入 ProductController.discover。Controller 只负责接收参数和基础校验，不在 Controller 中直接调用 Mapper：

ProductController.discover 调用 ProductQueryService.discover。服务方法依次完成以下工作：

  1. 调用 normalizeQuery 清理参数：q.trim()，空字符串转为 null；current < 1 时改为 1；size 限制在 1 到 50；sort 只允许 default、newest、priceAsc、priceDesc。
  2. 调用 ProductCacheService.getDiscoverPage，按“本机 Caffeine → Redis → MySQL”的顺序读取商品发现页。
  3. 缓存未命中时调用 ProductMapper.selectDiscoverPage，一次查询商品卡片、商品分类和店铺摘要，不让前端为每个商品再发一次店铺请求。
  4. 调用 toProductCardResponse 把 Mapper 返回行转换为 ProductCardResponse，只保留公开字段。
  5. 组装分页信息并返回 ProductDiscoverResponse。

商品查询 SQL 必须同时限制商品和店铺状态。只有 p.status = 1 且 s.business_status = 1 的数据才能进入公开发现页；分类停用时也不能继续作为公开筛选结果。

前端收到 Result.data 后，将 list 放入商品卡片数组。商品卡片至少展示商品图片、名称、分类、价格、库存、店铺名称和商圈。点击卡片时执行 navigate(/product/${product.id})，进入商品详情页。

四 排序和分页加载

前端排序按钮把 sort 放入 URL，并重新请求第 1 页。排序值和数据库字段的映射必须由后端白名单控制：

  • default：p.create_time DESC, p.id DESC
  • newest：p.create_time DESC, p.id DESC
  • priceAsc：p.price ASC, p.id DESC
  • priceDesc：p.price DESC, p.id DESC

ProductQueryService.toOrderBy(sort) 只能从上述固定映射中返回 SQL 片段，不能直接把请求中的 sort 拼进 SQL。

前端触底时，useInfiniteScroll 调用 loadMore。如果 loadingRef.current 或 finished 为 true，直接返回；否则请求 current + 1。成功后把新页追加到商品数组，并在 hasMore=false 时设置 finished=true。请求失败只提示“加载商品失败”，不能把已经显示的旧列表清空。

六 从商品详情进入店铺

商品详情页的店铺卡片点击后进入现有 /shop/:id 路由，由 ShopDetailPage 渲染店铺详情。店铺详情的店铺主体仍由现有店铺接口提供，后端调用关系为：

前端访问 GET /shop/${shopId}，调用 ShopController.queryById，再调用 ShopServiceImpl.queryById。

ShopServiceImpl.queryById 调用 shopCacheClient.queryWithPassThrough：

  1. 先读取 cache:shop:${shopId}。
  2. Redis 有正常 JSON 时反序列化为 Shop 并返回。
  3. Redis 命中空值标记时直接返回不存在。
  4. Redis 未命中时执行 ShopServiceImpl.getById 回源 MySQL。
  5. 数据库无记录时写入短 TTL 空值，防止缓存穿透。
  6. 数据库有记录时写入店铺缓存，并返回店铺数据。
  7. businessStatus = 3 时对外仍返回“店铺不存在”。

店铺详情页加载本店商品时调用 productService.listOfShop(shopId)，请求 GET /product/list/${shopId}。该接口只返回当前店铺 status = 1 的商品；如果店铺已经关闭，建议后端直接返回店铺不可用，前端不再展示商品列表。

七 商品分类与商品申请

商家中心的商品申请表单增加分类下拉框。页面初始化时调用 productService.categories()，只允许选择 enabled = 1 的分类。提交时形成：

前端访问商家商品申请接口，进入 ProductApplicationController.apply，Controller 从登录态 JWT 解析用户 ID 和角色后调用：

ProductApplicationServiceImpl.apply 的方法作用和调用顺序为：

  1. 使用 lock:submit:product:{userId}:{shopId} 做短时重复提交保护。
  2. 通过 shopMapper.selectById(shopId) 查询店铺，确认店铺存在且 businessStatus = 1。
  3. 非管理员时校验 shop.ownerUserId = userId。
  4. 调用 productCategoryService.requireEnabled(request.categoryId())，确认分类有效。
  5. 把请求 DTO 转换为 ProductApplication，保存 categoryId、名称、图片、价格、库存和 auditStatus = 0。
  6. 调用 applicationMapper.insert(app)，返回申请 ID。

商品申请修改接口的调用关系与提交相同：Controller 调用 ProductApplicationServiceImpl.update，服务方法先查询申请并校验申请人，再重新校验分类启用状态，更新 categoryId 和其他字段，并把审核状态重置为待审核。

当前代码的 ProductApplicationServiceImpl.apply/update 尚未写入 categoryId；联调时如果前端已经发送该字段而后端未补实体和数据库列，申请会出现“请求成功但分类丢失”的问题，应优先检查这一点。

八 管理员审核商品

管理员在后台打开商品申请列表，前端调用商品申请列表接口，后端进入 ProductApplicationServiceImpl.listForAdmin，按 auditStatus 和创建时间分页返回申请记录。

管理员点击通过时，前端访问审核接口并发送：

后端进入 ProductApplicationServiceImpl.audit。通过分支的调用关系为：

  1. applicationMapper.selectById(id) 查询待审核申请，并确认 auditStatus = 0。
  2. ossStorageService.confirmImages 确认申请图片已经正式入 OSS。
  3. 创建 Product，复制 shopId、createdBy、名称、描述、图片、价格、库存和 categoryId。
  4. 调用 productMapper.insert(product) 写入正式商品。
  5. 调用 applicationMapper.approve(id, adminId, product.getId()) 更新申请状态和正式商品 ID。
  6. 写入 AuditRecord，记录 PRODUCT 的审核流转。
  7. 事务成功提交后，删除商品发现页和相关详情缓存。
  8. 返回正式商品 ID。

当前实现审核通过时把新商品状态设为 2)，而公开接口只返回状态为 1) 的商品。联调必须确认产品规则：如果 2) 代表“待上架”，则审核通过后还需要管理员或店主调用上架接口；如果 2) 代表“已上架)，则应统一修改状态判断，不能让审核通过商品长期不可见。

拒绝分支要求 reason 非空，调用 applicationMapper.reject，只更新申请审核状态和拒绝原因，不创建正式商品，也不删除商品详情缓存。

九 商品上架和下架

商家或管理员在商品管理页点击上架/下架时，前端发送商品 ID 和目标状态，后端进入 ProductApplicationController.changeStatus，再调用 ProductApplicationServiceImpl.changeStatus。

changeStatus 依次完成：

  1. 只允许状态值 1)（上架）或 2)（下架）。
  2. 通过 productMapper.selectById(id) 查询商品。
  3. 通过 shopMapper.selectById(product.shopId) 查询店铺。
  4. 非管理员时校验当前用户是店主。
  5. 修改 product.status 并调用 productMapper.updateById(product)。
  6. 事务提交成功后删除商品详情键、商品发现页版本号和本机 Caffeine。

上架后，商品应能在 GET /product/discover 和 GET /product/{id} 中出现；下架后两个公开接口都必须拒绝或过滤该商品。联调时要分别验证列表和详情，不能只验证管理后台的状态字段。

ProductCacheService.getDetail 的读取调用关系如下：

前端 ProductDetailPage → productService.detail → ProductController.queryProductById → ProductQueryService.detail → ProductCacheService.getDetail。

getDetail 先查 Caffeine；本机未命中再查 Redis。Redis 命中正常 JSON 时反序列化为 ProductDetailResponse，并回填 Caffeine。Redis 命中空值标记时直接返回商品不存在，避免反复打数据库。Redis 未命中时使用 singleFlight 或商品 ID 互斥锁，只允许一个请求调用 ProductMapper.selectPublicDetailById；其余并发请求等待结果或读取回填后的缓存。回源为空写短 TTL 空值，回源成功写 Redis 和 Caffeine。

ProductCacheService.getDiscoverPage 的关系相同，但查询键由完整筛选条件组成。发现页不建议枚举所有 q 和分页键做精确删除，而是让 Redis 保存 qy:product:discover:version。每次商品审核通过、上架、下架或分类变化时执行 INCR，下一次查询自然生成新版本键；本机 Caffeine 同时执行 invalidateAll。

缓存读取时只缓存公开、相对稳定的字段。登录用户状态、优惠券领取状态、库存扣减结果和临时活动价格必须实时读取，不能放进长 TTL 商品详情缓存。

十二 前端错误处理和接口约定

前端 apiFetch 统一处理 Result.success。以下情况应按业务错误显示提示，不要当成程序异常：

  • 商品不存在、商品下架或所属店铺关闭：显示商品不可用。
  • 分类不存在或已停用：清空当前分类并提示重新选择。
  • 商家无权发布商品：显示无权操作。
  • 商品申请重复提交：显示“请勿重复提交”。
  • 审核拒绝：在申请列表展示 rejectReason，不跳转商品详情。

公开商品接口的返回 DTO 不应包含 ownerUserId、审核人、申请人、内部审核状态等后台字段。搜索参数、排序参数和分页参数由后端再次校验，不能只依赖前端限制。

十三 联调顺序

先执行数据库迁移，创建 tb_product_category)，给 tb_product和tb_product_application增加category_id`，插入“其他”分类并回填历史数据。

然后发布后端兼容版本：先让商品详情、商品发现和分类接口能够读取 `category_id)，旧商品缺失分类时显示“其他”；再接入 Redis/Caffeine 商品缓存和缓存指标。

后端接口稳定后接入前端 productService.categories、discover、detail，先完成商品详情页，再将雀探列表切换为商品列表。保留 /shops 和 /shop/:id 兼容旧链接。

最后联调商家申请、管理员审核、商品上下架和店铺资料修改，重点观察缓存失效是否在事务提交后执行，以及审核通过商品的状态是否真的能进入公开接口。

十四 联调验收

商品发现

前端打开 /products 能调用 GET /product/discover；关键字、分类、排序和分页参数都能在 Network 面板中看到；列表只显示上架且营业中的商品；触底只加载下一页，不重复加载。

商品详情

点击商品卡片能调用 GET /product/{id}；详情包含 categoryName 和 shop；点击店铺卡片能进入 /shop/{shopId}；商品下架或店铺关闭后，刷新详情页得到不可用提示。

分类

GET /product/categories 只返回启用分类；分类停用后前端刷新不再显示；商品发现接口不会返回停用分类下的商品。

商家和审核

商家提交申请时请求体带 categoryId；后端保存申请分类；修改申请会重新校验分类；管理员通过后正式商品继承分类；拒绝时必须填写原因。

缓存

第一次请求可以看到数据库回源，第二次请求命中 Redis，同一实例热点请求命中 Caffeine；并发冷启动只有一次 MySQL 查询；空结果不会持续穿透数据库；审核、上下架、分类修改和店铺修改后，详情及发现页最终读到新数据。

兼容和安全

旧 /shops 地址仍可用；店铺详情和商家店铺类型流程不受影响；公开接口不泄露后台字段；排序和搜索使用参数绑定；缓存中没有用户登录态和抢购库存。
