雀跃商铺与商品图片上传 OSS 改造方案（照抄可落地）

目标：商铺申请、商铺修改申请、商品申请的”图片”从手填 URL 改为像 blog 一样的 OSS 预签名直传。

说明：UploadController(/upload/blog) 是本地落盘方案，前端现在实际没有用它。blog 前端走的是
storageService.presign → putObject(浏览器直传OSS) → confirm(临时区搬正式区) 这套 OSS 流程，本方案完全对齐这套链路。

零、先说结论

部分 要不要改 说明
数据库 不用改 tb_shop_application.images、tb_shop.images、tb_product_application.images、tb_product.images 已存在，存逗号分隔的 OSS 正式 URL（如 https://qytest4.oss-cn-hangzhou.aliyuncs.com/shops/...）
后端 要改 给 StorageController 增加商铺/商品专用的 presign、confirm 共 4 个接口（照抄第六节），新增 1 个 DTO
前端 要改 storageService 加 4 个方法；新建 ImageUploader 组件；三处表单把 URL 文本框换成上传控件
配置 不用改 OSS 配置（endpoint/accessKey/bucket/publicUrl）已有

一、blog 现有的 OSS 上传链路（要照抄的模板）

关键点：文件由浏览器直传 OSS，不占后端带宽；临时区（unconfirmed/）不能当最终地址用，必须 confirm 拿到正式区 URL 再入库。

二、商铺/商品的差异与方案设计

blog 的 presign/confirm 都依赖”先建草稿拿 postId”并校验 Blog 归属。商铺/商品申请没有草稿概念，所以方案改为：

  • 归属用当前登录用户 id（JWT 的 sub），不依赖任何数据库记录
  • 对象键带上用户 id 前缀：unconfirmed/shop/{userId}/images/{日期}/{uuid}.{ext}、unconfirmed/product/{userId}/images/...
  • confirm 只校验 key 前缀必须是 unconfirmed/shop/{userId}/images/，防止搬走别人的对象
  • confirm 成功后搬入正式区：shops/{userId}/images/...、products/{userId}/images/...，返回可公开访问的正式 URL
  • 上传一张就立即 confirm 一张（单张 confirm），前端拿到的直接就是正式 URL，提交申请时不用再处理临时区——和 blog “换封面旧文件成为孤儿、交给 GC” 的处理方式一致

三、数据库改动

不用改。 各表 images 字段已存在，存逗号分隔的 OSS 正式 URL：

表 字段 长度 OSS URL（约 90 字符/张）能放
tb_shop_application images VARCHAR(1024) 约 11 张
tb_shop images VARCHAR(1024) 约 11 张
tb_product_application images VARCHAR(2048) 约 22 张
tb_product images VARCHAR(2048) 约 22 张

若觉得商铺图片 11 张不够，可选加长（执行前自行判断）：

  • 商家中心店铺卡片、管理后台审核列表、店铺详情商品卡片都在用 (images || "").split(",") + <Thumb>，零改动

七、照着做的落地顺序

  1. 后端：新建 ConfirmImageRequest.java，StorageController 粘贴第五节 4 个方法
  2. 重启后端，先用 Postman 验证：
    • POST /storage/presign/shop-image，body {"contentType":"image/png","ext":"png"} → 拿到 putUrl
    • 用 putUrl 对 OSS 发 PUT 上传一张图（带 Content-Type: image/png）
    • POST /storage/confirm/shop-image，body {"imageKeys":["unconfirmed/shop/1013/images/20260905/xxx.png"]} → 返回 https://qytest4.oss-cn-hangzhou.aliyuncs.com/shops/... 且浏览器可打开
  3. 前端：storageService.ts 加 4 个方法 → MerchantCenterPage.tsx 加两个上传函数 → 新建 ImageUploader 组件和样式 → 替换三处表单
  4. 提交申请/修改申请，确认数据库 images 字段存的是逗号拼接的 OSS 正式 URL

八、常见坑

  1. 直传 403 签名不匹配：PUT 时必须带和 presign 时一致的 Content-Type 头（putObject 已处理，别自己在 headers 里多加头）
  2. 把临时区 URL 直接入库：unconfirmed/ 的地址不能当最终地址（权限可能不公开），必须 confirm 后用返回的正式 URL
  3. 删除预览图会留孤儿文件：上传即 confirm 后，用户取消预览图，OSS 正式区会多一个没人引用的文件——和 blog 现状一致，靠后续生命周期规则/GC 清理，不影响功能
  4. ext 与 contentType 不匹配：前端用文件名后缀 + file.type 上传，两者是配套的；手测 Postman 时注意一致
  5. URL 长度：OSS 正式 URL 约 90 字符，VARCHAR(1024) 能放约 11 张；不够按第三节 SQL 加长
  6. 多图上传：一张一张串行即可；要更快可 Promise.all 并发（每张独立 presign+put+confirm，互不影响）
  7. /storage/ 需要登录**：presign/confirm 都从 JWT 取 userId，未登录直接 401，符合现状
