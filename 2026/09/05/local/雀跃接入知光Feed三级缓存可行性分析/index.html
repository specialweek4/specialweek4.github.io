雀跃热门笔记三级缓存

发表于2026-09-05|更新于2026-09-05|local

雀跃接入知光 Feed 三级缓存与 Bitmap 计数方案

一、结论

雀跃可以实现知光思路的三级缓存，同时学习知光的 Redis 计数模式。首期推荐：

  • L2 Caffeine：缓存热榜前 3 页的公共基础对象。
  • L1 Redis：缓存每页有序博客 ID 骨架。
  • L0 Redis：缓存单条博客的稳定公共展示碎片。
  • 分片 Bitmap：保存用户点赞和收藏事实。
  • Lua：原子置位/清位，并把有效增量写入聚合桶。
  • 聚合任务：每秒把 Hash 增量折叠进 8 字节二进制计数快照。
  • Feed 返回前：覆盖实时点赞/收藏数，再叠加当前用户 liked/faved/followed。
  • MySQL：低频保存点赞/收藏数检查点，不承受每次互动写入。

首期不使用 Kafka、Canal、Outbox、Redisson、动态热点 TTL 和完整关系审计。关注仍用 tb_follow，因为关注/粉丝列表需要关系索引。

二、数据分层

数据库不是三级缓存的一层。三级缓存只负责公共基础内容，Redis 计数内核是另一条横向数据层。

三、为什么计数和用户态必须后置覆盖

3.1 用户态不能进入公共缓存

若把 A 用户的 isLike=true 写进 Caffeine 或 Redis 博客碎片，B 用户会看到 A 的状态。公共缓存 DTO 中禁止出现：

  • isLike / likedByMe。
  • faved / favoritedByMe。
  • followed。

3.2 高频计数不应绑在博客碎片里

若 liked/favorites 放进 L0/L2，每次点赞都要删除博客碎片和完整页，会使热点页面持续失效。新的边界是：

  • L0/L1/L2 只缓存稳定字段。
  • 点赞/收藏数每次响应都从固定二进制快照批量覆盖。
  • 用户状态每次响应从 Bitmap 批量覆盖。
  • 点赞不再删除公共博客碎片。

四、首期范围

只改造公共热榜：

  • 第 1～3 页使用三级缓存。
  • 第 4 页以后直接批量查询 MySQL，但仍叠加 Redis 实时计数和用户态。
  • 每页固定 10 条。
  • 暂不缓存“我的博客”和草稿。
  • 暂不实现关注 Feed。
  • 热榜排序暂时使用 MySQL 点赞数检查点，允许约 30～60 秒排序延迟。
  • 条目中显示的点赞/收藏数仍是实时逻辑值，不必等待 MySQL 检查点。

十二、实时计数批量覆盖

12.1 逻辑计数

聚合桶每秒才刷入快照，所以读取必须计算：

不能只读快照，否则动作接口和 Feed 会短暂显示旧值。也不能在 Java 中分两次依次读取快照和桶，因为两次读取之间可能发生 flush。

12.2 批量读取代码结构

counter_read.lua 在一个原子脚本中读取 8 字节快照和 Hash 的 0/1 增量并相加，完整内容见配套文档。pipelineReadScripts 使用底层连接对每个博客发送已加载脚本的 EVALSHA，Redis 按顺序返回结果，整个页面只有一次网络往返。

快照缺失时：

  • 新博客按 0 初始化。
  • 已有博客首次迁移可从 tb_blog.liked/favorites 编码基线。
  • 结构损坏时用 SCAN + BITCOUNT 重建，禁止 KEYS。
  • 所有互动写入必须先执行幂等 ensureInitialized(blogId)，避免首次 flush 从零覆盖旧基线。

十四、最终装配服务

Redis 计数服务不可用时不能悄悄把点赞状态写成 false 并允许用户再次点赞。学习版建议互动写接口直接返回服务不可用；Feed 读接口可以降级使用 MySQL 检查点计数并把个人状态显示为未知或临时 false，同时记录告警。

十五、Hot Feed Service 与 Controller

/blog/hot 可以继续 permitAll。匿名请求的 jwt 为 null，只读取公共计数，不读取 Bitmap 用户位和关注状态。

十六、聚合与 MySQL 检查点

16.1 一秒聚合

定时任务使用 SCAN qy:agg:v1:* 找到聚合桶，Lua 原子完成：

  1. 读取当前 8 字节快照。
  2. 读取 Hash 的 0/1 增量。
  3. 按大端 Int32 更新两个固定偏移。
  4. 写回快照。
  5. 删除已经折叠的聚合桶。

完整 flush Lua 见配套文档。不得使用 Redis KEYS。

16.2 低频数据库检查点

每次有效状态变化会 INCR qy:dirty:v1:{blogId}。每 30～60 秒处理少量脏博客：

真实实现应让一批数据库更新处于事务中，成功后再比较删除各脏版本。若同步期间产生新点赞，版本变化，脏键不会被删除，下轮继续同步。

一批检查点完成后只失效一次热榜 L1/L2，不要每更新一篇博客就清空一次。

十七、写入与失效规则

写操作 L0 稳定碎片 L1 热榜骨架 L2 基础页 计数/用户态
新发布 可选预热 删除前3页 清空 初始化零快照
修改已发布内容 删除该博客 影响可见性时删除 清空 不变
软删除 删除该博客 删除前3页 清空 可保留待清理
点赞/取消点赞 不删 操作时不删 不删 Lua更新Bitmap和桶
收藏/取消收藏 不删 不删 不删 Lua更新Bitmap和桶
MySQL点赞检查点批次完成 不删 删除前3页 清空 已同步检查点
关注/取消关注 不删 不删 不删 更新follow状态键
评论数变化 删除该博客或后置覆盖 排名不变可保留 清空 首期仍写MySQL

点赞后不清缓存也能立即看到新计数，因为计数和个人状态在返回前覆盖。热榜名次在检查点任务后刷新，属于明确接受的最终一致。

十八、缓存失效代码

业务事务提交后再失效。多实例时，Redis L1 删除对所有实例可见，但其他实例的 Caffeine 仍可能保留 5 秒旧基础页；后续用 Redis Pub/Sub 广播 invalidateAll 即可。

十九、建议文件结构

不必建立知光完整的事件、消费者、重建退避和 Redisson 类层次。

二十、测试清单

三级缓存

  1. L2 命中不访问 L1/L0/MySQL，但仍读取实时计数层。
  2. L1/L0 命中按骨架顺序装配。
  3. 任一碎片缺失时整页回源。
  4. 空页短缓存避免重复查库。
  5. Redis 普通缓存故障时可以查 MySQL 基础页。

计数覆盖

  1. 点赞后不清 L0/L2，Feed 仍立即显示新计数和状态。
  2. flush 前后逻辑计数保持一致。
  3. 一页计数使用 pipeline，不产生逐条 RTT。
  4. A、B 用户共用同一基础页，但 isLike/faved 各自正确。
  5. 匿名用户不读取用户 Bitmap。

排名与检查点

  1. MySQL 检查点任务前，显示计数已更新但排名可保持旧顺序。
  2. 检查点批次完成后只进行一次 L1/L2 排名失效。
  3. 写库期间有新点赞时脏版本不会被误删。
  4. 数据库故障后脏键保留并可重试。

隔离与恢复

  1. 公共缓存 JSON 不含计数和用户态。
  2. 快照损坏时可通过分片 BITCOUNT 重建。
  3. Redis AOF 重启后 Bitmap、桶、快照和脏版本仍存在。
  4. 不使用 KEYS，扫描任务每轮有数量上限。

二十一、实施顺序

  1. 先消除热榜作者 N+1，建立 HotBlogBaseItem。
  2. 增加 favorites 检查点字段并确认历史点赞迁移策略。
  3. 实现 Bitmap 分片、toggle Lua 和幂等互动接口。
  4. 实现“快照 + 聚合桶”的单条及批量计数读取。
  5. 实现 pipeline Bitmap 用户态覆盖。
  6. 先在无三级缓存的热榜上验证最终 View 正确。
  7. 实现 L0/L1，再加入 L2 Caffeine。
  8. 实现聚合 flush 和 MySQL 检查点任务。
  9. 完成关注关系和 followed 批量覆盖。
  10. 开启 AOF，进行重启、故障和恢复测试。
  11. 压测后再调整 TTL、批次和周期。

二十二、以后建议添加

P0

  • 计数 Redis 独立实例、AOF 备份和恢复演练。
  • 聚合桶年龄、脏键积压、Lua P99、Bitmap 内存监控。
  • 管理员重建指定博客快照的工具。
  • 多实例 Caffeine 失效的 Redis Pub/Sub。

P1

  • Kafka 可靠发送有效点赞/收藏增量。
  • 消费者维护聚合桶、关系审计和用户收藏列表。
  • 热榜 Redis ZSet，按实时点赞数或衰减热度排序。
  • 可靠 Outbox 或可重放事件源。

P2

  • 自动重建锁、限流和指数退避。
  • 热键检测和动态 TTL。
  • 评论/转发扩展到新的二进制 Schema。
  • 关注 Feed 的推拉结合。
  • 大 V 关注/粉丝列表的 Redis ZSet。

二十三、最终落地检查表

实施前：

  • 确认 Redis 是单实例还是 Cluster；同一博客所有 Lua key 必须同 slot。
  • 确认计数事实键不设 TTL、不被淘汰并开启 AOF。
  • 决定历史无关系点赞数清零还是作为不完整基线。
  • 明确热榜排序接受 30～60 秒延迟。

实现中：

  • 公共基础 DTO 不含计数和用户态。
  • PUT/DELETE 明确目标状态，Lua 只在变化时写增量。
  • 计数读取始终合并快照与未刷聚合桶。
  • Feed 使用 pipeline 批量读计数和 Bitmap。
  • 聚合、重建和脏键发现使用 SCAN，不使用 KEYS。
  • 关注继续使用 MySQL 关系，不强行 Bitmap 化。

上线前：

  • 完成重复请求、并发切换、flush 竞争和检查点版本测试。
  • 使用两个账号验证用户态不串数据。
  • 验证 Redis 重启后事实键完整。
  • 验证计数 Redis 故障时互动写接口明确失败。
  • 记录三级缓存命中率、计数读取耗时和数据库写入下降比例。

二十四、最终建议

新的组合比“每次点赞写 MySQL并清三级缓存”更适合学习高并发计数：Bitmap 负责用户事实，Lua 负责原子幂等，聚合桶负责吸收写入，固定快照负责高频读取，三级缓存只负责稳定内容。

首期没有 Kafka 时，必须把 Redis 当作持久数据系统管理，而不是普通可丢缓存。等这条链路跑通后，再加入 Kafka 做可靠事件、关系审计和用户收藏列表，比一开始复制知光全部基础设施更容易理解每一层的作用。
