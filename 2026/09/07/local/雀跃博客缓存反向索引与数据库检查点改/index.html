雀跃公共feed流改造 3

发表于2026-09-07|更新于2026-09-11|local

1. 目标和最终结论

本次改造的目标是：

  1. 热门页不在根据热度排行，转换成根据发布时间排行
  2. Redis 页面 ID Key 增加小时时间槽，避免不同时间生成的页面互相覆盖。
  3. 写入页面时建立 blogId -> 页面引用 反向索引，普通博客内容更新只删除包含该博客的页面。
  4. 删除 CACHED_PAGES = 3，访问过的任意页都可以进入缓存；缓存上限由 Caffeine 容量和 TTL 控制。
  5. 新博客发布时不删除任何公共 Feed 缓存，允许新内容在短时间内等待缓存自然过期或小时槽切换后出现。
  6. 点赞、收藏使用 MySQL 关系表保存最终用户行为，Redis Bitmap 和计数继续负责高速路径；Bitmap 不写入数据库。
  7. 当前先同步写关系表；后续若接入 Kafka，采用“关系表/Outbox 同事务写入 + Canal 捕获 outbox + Kafka 消费”的可靠链路，不在请求线程直接依赖 Kafka。

4. Redis Key、时间槽和页面引用

4.1 推荐 Key

页面缓存布局版本直接升到 v2，避免新旧 Key 混用：

用途 Redis Key 类型
页面 ID 列表 feed:public:ids:{size}:{hourSlot}:{page} List
页面 hasMore feed:public:ids:{size}:{hourSlot}:{page}:hasMore String

博客到页面反向索引 feed:public:index:{blogId}:{hourSlot} Set

hourSlot 使用 Unix epoch 小时，不使用本地格式化时间：

Redis 页面引用（反向索引 Set 成员）使用本地 Caffeine Key，不带时间槽，例如：

它表示 size=20、page=4、布局版本 v2。小时槽只出现在 Redis 页面 ID Key、反向索引 Key 和页面注册表 Key 中。

4.2 Caffeine 本地 Key 不带时间槽

按照知光的做法，Caffeine 本地缓存只使用分页和布局版本作为 Key；小时槽只用于 Redis 的页面 ID 列表和反向索引。这样同一页在本机只有一份本地缓存，失效时可以通过反向索引直接拿到本地 Key：

小时槽切换后，本地页可能短暂返回旧槽内容，这是知光方案接受的最终一致窗口；页面 TTL 和定向失效负责收敛。如果要求小时切换立即隔离本地页，才需要把槽加入本地 Key，但本次不采用。

建议集中定义 Key 方法，禁止在多个方法中手写字符串：

反向索引 Set 的成员直接保存 localPageKey，例如 feed:public:20:4:v2，不要保存带槽的 pageRef。失效时读 Set 成员后直接调用 feedPublicCache.invalidate(localPageKey)，再根据当前/上一小时槽删除对应 Redis 页面键。

页面 List、hasMore、反向索引、页面注册表应使用同一类 TTL。推荐起始值：页面 60～90 秒，随机抖动 0～30 秒；本地 Caffeine 5～15 秒。TTL 是参数，不是业务正确性的唯一保障。

6.1 普通博客内容更新：定向清理

PageKey 可以实现为一个内部 record；它只解析本地 Caffeine Key，不包含小时槽：

失效方法必须是“尽力清理”：单个坏引用、Redis 临时异常不能阻塞博客更新；清理失败由 TTL 兜底并记录日志。

6.2 哪些操作不能只清理一页

最新 Feed 使用 offset 分页。博客从列表中加入、移除或改变发布时间，会让后续页面整体移动。因此：

操作 推荐处理
修改标题、描述、图片、正文 invalidateFeedCache(blogId) 定向失效
新博客发布 不清理任何公共 Feed 页面，等待 TTL/小时槽
草稿发布 与新发布相同，不清理公共 Feed
删除/下架已发布博客 invalidateFeedRanking() 清理所有已登记页面；否则后续页可能出现空洞或重复
修改 publish_time invalidateFeedRanking()
点赞/收藏 不清理 Feed 页面；最新 Feed 不按点赞排序，计数由 enrich() 实时读 Redis

如果产品愿意接受删除/下架后的短暂旧数据，也可以对删除只做定向清理，但必须明确这是最终一致而不是严格分页一致。

10.4 Kafka Outbox 消费者：只更新 Redis 派生状态

关系表已经在请求事务中写入，消费者不再重复 INSERT/DELETE 关系表。消费者负责：解析 Canal envelope，使用一个 Redis Lua 脚本按目标状态修正 Bitmap，并在 bit 真正发生变化时同步更新聚合和 dirty，最后手动 ACK。这样重复投递不会重复计数，也不需要依赖一个可能在失败前已写入的去重键。

批量容器需要设置 factory.setBatchListener(true)、AckMode.MANUAL 和 max.poll.records: 500。applyEventAtomically() 必须通过 Lua 在一次 Redis 操作中完成“检查旧 bit → 按目标状态设置 → 必要时增减聚合 → 增加 dirty”；重复事件看到 bit 已是目标状态时返回 0，不会重复计数。若还要记录审计处理状态，再增加持久化 Inbox 表（PRIMARY KEY(event_id)），但 Inbox 不能替代 Lua 的幂等状态更新。本文不使用 last_sequence。

包装类需要注入 StringRedisTemplate redis，并导入 DefaultRedisScript、List、BitmapShard 和 CounterKeys。如果项目使用 Java 8，不能使用文本块 """，应改为普通字符串拼接；当前雀跃代码已经使用 List.of，按 Java 17 模板实现即可。

返回 1 表示这次 Redis 状态确实从旧值变成了目标值，返回 0 表示重复事件或已经修复完成；只有返回 1 才需要认为本次派生聚合发生了变化。关系表仍然是最终事实，Redis 执行失败时抛异常，不 ACK Kafka，让消息重试。

Redis 整体丢失后的恢复要先做一次“关系表重建”：清理对应博客的 Bitmap、agg 和 dirty，按 state=1 的关系重新写入 Bitmap 并初始化聚合，再让 Kafka 从恢复点继续消费。不要在已经用关系表重建出聚合后，再把历史 Outbox 全量从头重放，否则每条历史事件都会被当成一次新的 bit 变化而重复累加。

10.5 最终提交顺序和故障处理

必须遵守：

  1. 关系表和 Outbox 不得分成两个事务，否则可能出现关系已提交但事件丢失。
  2. Canal 发送 Kafka 失败不能 ACK Canal；消费者 Redis 失败不能 ACK Kafka，靠重放恢复。
  3. Kafka key 使用 userId:blogId:type，同一关系有序；不同用户不能合并成一条关系事实。
  4. 软删除关系表是事实来源，Redis Bitmap 和聚合是可重建派生状态；检查点仍把聚合数最终写回 tb_blog。

11. 实施顺序

建议按以下顺序逐步落地：

  1. 先修改 Feed SQL 为 publish_time DESC, id DESC。
  2. 升级 Feed Key 到 v2，加入 size/hourSlot/page。
  3. 删除 CACHED_PAGES 分支，补页面注册表和博客反向索引。
  4. 实现定向失效；验证普通内容更新只清理命中的页面。
  5. 发布新博客时删除全量失效调用；验证旧缓存不被清空，新内容在 TTL/槽切换后出现。
  6. 删除 CounterCheckpointJob 对 Feed 的全量失效调用。
  7. 建立 tb_blog_like、tb_blog_favorite，先同步写关系表。
  8. 增加“我的点赞/我的收藏”查询接口。
  9. Redis 开启 AOF/RDB，并准备按关系表重建 Bitmap 的管理任务。
  10. 压测后再接入 Outbox + Canal + Kafka；Kafka 消费者只维护 Redis 派生状态，不重复写关系表。

12. 验证清单

Feed

  • 请求第 1、4、20 页都能进入 Redis 页面缓存，不再因为页码大于 3 直接查库。
  • 同一小时内发布新博客，不会调用 invalidateFeedRanking()，旧页面不会被主动删除。
  • 小时槽切换后，Redis 使用新槽 Key；旧槽依靠 TTL 过期。
  • 修改某博客标题时，只命中该博客反向索引的页面被清理；其他页面的 Caffeine Key 保留。
  • 删除或下架博客后，所有已登记页面被清理，后续页不会长期出现空洞。
  • FeedItemResponse 的 liked/faved 不会写入共享缓存，两个用户不会互相污染状态。
  • Redis 页面 List 的顺序与 SQL 返回顺序一致。

点赞/收藏

  • 同一用户重复点赞，关系表仍只有一行，changed=false。
  • 同一用户重复取消，关系表没有负计数，changed=false。
  • Redis Bitmap 丢失后，可以从关系表重建用户状态。
  • Redis 计数实时变化，tb_blog.liked/favorites 由检查点最终更新。
  • 检查点成功不会再清空公共 Feed 页面。
  • 大量不同用户同时点赞时，关系表每个用户仍是一条事实；只有批量写入或 Kafka 削峰，不能错误合并成一条。
  • Outbox 与关系状态在同一事务中提交；Canal 转发失败可以重放，Kafka 消费者用 Lua 按目标状态幂等更新，outboxId 仅用于追踪/可选 Inbox。

这套设计解决的是“缓存范围过小、更新时全量清理、无法查询用户行为”的问题，同时保留了雀跃现有 Redis Bitmap 和计数结构。它不承诺动态 offset 分页在所有并发变化下形成严格快照；如果以后需要严格分页一致性，还要为 Feed 增加 snapshotToken 和版本化页面快照。

14. 实施后的职责边界

关系表仍是用户行为事实；Outbox 保证数据库提交后事件不会丢；Canal 负责把数据库变更可靠送入 Kafka；Bitmap 和 Redis 聚合都属于可重建派生状态。本文不使用 last_sequence，也不要求把 Bitmap 原样写入 MySQL。
