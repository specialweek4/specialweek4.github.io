雀跃公共feed流改造

发表于2026-09-07|更新于2026-09-07|local

雀跃公共 Feed、反向索引与点赞收藏关系表落地改造手册

适用项目：D:\queping\queyue_be-main
参考项目：D:\zhiguang\zhiguang_be-main
本文只提供改造方案和代码模板。本次没有修改两个项目的任何源代码。

1. 目标和最终结论

本次改造的目标是：

  1. 公共 Feed 不再是“热门排行”，改为像知光一样按博客发布时间展示最新发布内容。
  2. Redis 页面 ID Key 增加小时时间槽，避免不同时间生成的页面互相覆盖。
  3. 写入页面时建立 blogId -> 页面引用 反向索引，普通博客内容更新只删除包含该博客的页面。
  4. 删除 CACHED_PAGES = 3，访问过的任意页都可以进入缓存；缓存上限由 Caffeine 容量和 TTL 控制。
  5. 新博客发布时不删除任何公共 Feed 缓存，允许新内容在短时间内等待缓存自然过期或小时槽切换后出现。
  6. 点赞、收藏使用 MySQL 关系表保存最终用户行为，Redis Bitmap 和计数继续负责高速路径；Bitmap 不写入数据库。
  7. Kafka 尚未接入时，先同步写关系表；以后接入 Kafka 时，再切换为可靠事件 + 批量合并写库。

6. 反向索引失效策略

6.1 普通博客内容更新：定向清理

标题、描述、图片、正文对象地址等更新不会改变最新 Feed 的排序。应只清理包含该博客的页面：

PageRef 可以实现为一个内部 record：

失效方法必须是“尽力清理”：单个坏引用、Redis 临时异常不能阻塞博客更新；清理失败由 TTL 兜底并记录日志。

6.2 哪些操作不能只清理一页

最新 Feed 使用 offset 分页。博客从列表中加入、移除或改变发布时间，会让后续页面整体移动。因此：

操作 推荐处理
修改标题、描述、图片、正文 invalidateFeedCache(blogId) 定向失效
新博客发布 不清理任何公共 Feed 页面，等待 TTL/小时槽
草稿发布 与新发布相同，不清理公共 Feed
删除/下架已发布博客 invalidateFeedRanking() 清理所有已登记页面；否则后续页可能出现空洞或重复
修改 publish_time invalidateFeedRanking()
点赞/收藏 不清理 Feed 页面；最新 Feed 不按点赞排序，计数由 enrich() 实时读 Redis

如果产品愿意接受删除/下架后的短暂旧数据，也可以对删除只做定向清理，但必须明确这是最终一致而不是严格分页一致。

6.3 全量失效不再按前三页删除

invalidateFeedRanking() 应改为遍历页面注册表，而不是循环 page=1..3：

不要使用 Redis KEYS feed:public:*。页面注册表就是为避免阻塞式全库扫描而增加的。如果注册表数量很大，再改成分页读取或受控 SCAN。

11. 实施顺序

建议按以下顺序逐步落地：

  1. 先修改 Feed SQL 为 publish_time DESC, id DESC。
  2. 升级 Feed Key 到 v2，加入 size/hourSlot/page。
  3. 删除 CACHED_PAGES 分支，补页面注册表和博客反向索引。
  4. 实现定向失效；验证普通内容更新只清理命中的页面。
  5. 发布新博客时删除全量失效调用；验证旧缓存不被清空，新内容在 TTL/槽切换后出现。
  6. 删除 CounterCheckpointJob 对 Feed 的全量失效调用。
  7. 建立 tb_blog_like、tb_blog_favorite，先同步写关系表。
  8. 增加“我的点赞/我的收藏”查询接口。
  9. Redis 开启 AOF/RDB，并准备按关系表重建 Bitmap 的管理任务。
  10. 压测后再决定是否引入 Kafka 批量合并。

12. 验证清单

Feed

  • 请求第 1、4、20 页都能进入 Redis 页面缓存，不再因为页码大于 3 直接查库。
  • 同一小时内发布新博客，不会调用 invalidateFeedRanking()，旧页面不会被主动删除。
  • 小时槽切换后，Redis 使用新槽 Key；旧槽依靠 TTL 过期。
  • 修改某博客标题时，只命中该博客反向索引的页面被清理；其他页面的 Caffeine Key 保留。
  • 删除或下架博客后，所有已登记页面被清理，后续页不会长期出现空洞。
  • FeedItemResponse 的 liked/faved 不会写入共享缓存，两个用户不会互相污染状态。
  • Redis 页面 List 的顺序与 SQL 返回顺序一致。

点赞/收藏

  • 同一用户重复点赞，关系表仍只有一行，changed=false。
  • 同一用户重复取消，关系表没有负计数，changed=false。
  • Redis Bitmap 丢失后，可以从关系表重建用户状态。
  • Redis 计数实时变化，tb_blog.liked/favorites 由检查点最终更新。
  • 检查点成功不会再清空公共 Feed 页面。
  • 大量不同用户同时点赞时，关系表每个用户仍是一条事实；只有批量写入或 Kafka 削峰，不能错误合并成一条。

迁移时把请求路径改为：

必须遵守三条规则：

  1. 不要把事件只放在 JVM 内存队列；Kafka 发送失败必须重试，生产环境最好增加 Outbox。
  2. 不同用户对同一博客的点赞不能合并成一条，只能批量写入；只有同一用户对同一博客的连续操作可以合并。

这样迁移后，Redis 仍负责实时体验，MySQL 关系表仍是最终用户行为事实，Bitmap 仍然只是可重建的 Redis 派生状态，不需要写入数据库。
