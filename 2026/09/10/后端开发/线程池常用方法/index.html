线程池和定时任务常用方法

发表于2026-09-10|更新于2026-09-18|后端开发

线程池的常见用法

线程池用来复用线程并限制并发。适合独立的后台任务、缓存预热和多个互不依赖的查询。它不会自动让数据库更快，也不会自动保证数据一致性。

第一步：创建由 Spring 管理的有界线程池

Bean 初始化和销毁由 Spring 处理，这种写法不需要额外手动调用 initialize 或 shutdown。已有同名 Bean 或 EnableAsync 配置时不要重复添加。

配置 示例值 作用
corePoolSize 4 核心线程数，线程按需创建
maxPoolSize 8 允许创建的最大线程数
queueCapacity 100 等待执行的任务上限
keepAliveSeconds 60 默认用于超出核心数量线程的空闲回收
threadNamePrefix app-task- 方便在日志和线程转储中辨认
awaitTerminationSeconds 10 关闭时最多等待的时间，不是单个任务超时

一般接收顺序是：创建到核心线程数 → 任务进入队列 → 队列满时扩容到最大线程数 → 无法接收时拒绝。4、8、100 是示例参数，应结合 CPU、任务耗时、数据库连接池大小和流量调整。

AbortPolicy 会拒绝任务，Spring 通常以 TaskRejectedException 通知调用方。CallerRunsPolicy 会改为让提交线程执行任务，适合允许提交方承担反压的场景，但可能阻塞 HTTP 请求或调度线程，不能再保证快速返回。不要为支付、审核等重要任务使用悄悄丢弃的拒绝策略。

第二步：使用 execute 提交无返回值任务

下面任务只是打印日志，用来验证线程切换。实际使用时把日志处换成独立业务服务调用。显式构造器上使用 Qualifier，避免依赖 Lombok 是否复制字段注解。

在已有 Service 或 Controller 中注入 BackgroundDemoService，然后调用 backgroundDemoService.submit(userId)。返回 true 只代表任务已被接收，不代表执行成功。示例没有暴露公共接口，避免任何人通过演示接口无限提交任务。

execute 不提供返回结果，所以执行异常要在任务内部处理；提交失败要在提交位置处理，这是两个不同阶段。

什么时候不要只依赖线程池

内存队列中的任务会随进程崩溃丢失。审核成功后必须执行的结算、消息投递等工作，需要持久化任务、事务消息或可靠队列，不应只靠 execute 后立即返回成功。事务、MDC 和当前请求身份也不会自动随业务线程池传播；需要时单独设计传递和清理。

定时任务的常见用法

定时任务负责“什么时候触发”，线程池负责“任务由哪些线程执行”。雀跃计数检查点就是周期触发的业务，和用户点击接口触发不同。

下面配置与前面的 appTaskExecutor 分工不同。新建 TaskSchedulingConfig；如果项目已有 EnableScheduling，则复用已有启用配置，不要重复添加同名调度器。

调度任务会占用这些线程，耗时任务可能拖延其他任务。示例池大小为 2，实际按任务数和耗时配置。如果存在多个调度器，要明确 Spring 使用哪个，不能仅根据类名判断。

第二步：编写三个常见触发方式

下面演示任务只输出日志，可以直接放进扫描范围观察执行时间。真正上线时替换为自己的业务服务调用。

application.yaml 示例：

方式 适合场景 注意点
fixedDelay 批量同步、轮询检查点 上次完成后等待，不让同一个同步任务不断追赶周期
fixedRate 固定节奏的采样 耗时超过周期时可能延后，不能认为每次都准点
cron 每天清理、每小时统计 明确时区，进程停机期间错过的任务不会自动补跑

本例数字单位默认毫秒。Spring cron 常用六个字段：秒、分、时、日、月、星期。例如 0 */5 * * * * 是每五分钟，0 0 3 * * * 是每天 03:00。需要临时禁用 cron 触发可把对应属性设为 "-"，但不会同时禁用其他 fixedDelay/fixedRate 方法。

在本例 ThreadPoolTaskScheduler 中，同一次注册的普通同步 fixedRate 任务不会仅因为周期短就自行重叠执行；多实例、重复注册以及与 Async 组合是另外的情况。Scheduled 方法无参数，也不能靠返回值把结果传给某个 HTTP 请求。

新写任务时，通常让 Job 只负责触发，再调用另一个注入的 Service。事务注解放在业务 Service 的 public 方法上，通过 Spring 代理调用，让事务在执行任务的线程中开启。不要用 this.transactionalMethod() 期待新开启事务；也不能认为数据库事务能原子提交 Redis 的修改。

业务量大时分批处理，每批有明确上限，记录本批成功数和失败项。任务中断后下一次应能继续，不能因为一条记录出错就反复阻塞所有后续记录。

第四步：区分同步调度与提交后台任务

大多数短定时任务直接同步执行即可。如果调度方法只调用 executor.execute(...) 然后返回，fixedDelay 等待的是“提交方法完成”，不是后台业务完成；下一次触发时上一次业务可能还在运行。

下面是可选写法：本实例只允许一个这类后台任务运行，线程池拒绝时也会释放标记。这里只演示日志任务，复用前面的 appTaskExecutor 和 EnableScheduling 配置。

AtomicBoolean 只能协调当前进程，多个实例各有自己的标记。多实例任务要选择允许重复且幂等、数据库抢占、带租期的分布式协调或外部调度系统等策略。锁过期、任务重试时仍应通过业务状态或唯一约束避免重复效果。

怎么验证是否真的生效

  1. 启动项目，确认这些类在 Spring 扫描范围内，且没有重复定义的线程池 Bean。
  2. 从其他 Bean 调用 BackgroundDemoService.submit，日志线程名应是 app-task- 开头。
  3. 调用 AsyncDemoService.sum 并观察 CompletableFuture，成功得到结果，计算溢出等异常能被观察到。
  4. 定时任务日志线程名应是 app-schedule- 开头；调试时可暂用 cron */10 * * * * * 每十秒验证，再恢复正式配置。
  5. 分别验证任务内部失败、提交被拒绝、任务超时、关闭应用和多实例执行，确认不会静默丢失关键操作。

演示类验证完可以移除。业务线程池与任务参数应根据实际负载调整，不要把示例数值当成通用最佳配置。
