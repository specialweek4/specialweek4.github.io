OSS对象存储简单实现

发表于2026-09-11|更新于2026-09-18|后端开发

OSS 图片上传使用教程

文件内容从浏览器直接传给 OSS，应用后端负责授权、归属检查和数据库记录。

字段 含义 是否长期保存
objectKey Bucket 内的对象键，如 images/10001/20260918/UUID.jpg 保存到数据库
putUrl 带签名的临时 PUT 上传地址 不保存
publicUrl 公开域名与对象键组成的读取地址 按需生成
GET 签名地址 私有对象的限时读取地址 不保存，过期后重新生成

对象键是桶内的文件名，斜杠用来组织前缀，并不代表本地磁盘目录。保存对象键可以让应用更容易切换 CDN 或公开访问域名；迁移到另一个桶时仍需实际迁移文件。

下面提供独立示例，使用 Spring Boot 3、Java 17、MySQL 和阿里云 OSS。每个 public 类放入同名 Java 文件，统一放在 src/main/java/com/example/ossdemo/。本次只修改文档，没有把这些示例类写入雀跃项目。

第一步：配置 OSS 和示例工程

Bucket、权限和跨域

创建 Bucket，记下地域 Endpoint 和桶名。给后端 RAM 身份授予目标桶 images/ 前缀所需的上传与读取权限；示例使用 PutObject、GetObject 和 GetObjectMetadata 对应的权限。不要把 AccessKey 放在前端或提交到 Git，也不要开放匿名写入。

本例默认私有桶，读取时生成临时 GET 签名。公开图片也可以使用公开读桶并切换配置，但配置中的 public-read 开关不会自动修改桶 ACL。

浏览器直传需要在 OSS 的 CORS 规则中允许实际前端来源、PUT 方法和 Content-Type 请求头。Spring 的 CORS 配置不能替代 OSS 的配置：

配置项 本地示例
允许来源 http://localhost:8080
允许方法 PUT
允许请求头 Content-Type

上线换成实际前端来源。如果后续通过 JavaScript fetch 读取对象，还需按需放行 GET；本例使用 img 展示图片。

pom.xml

这是独立工程的完整配置。在已有项目中只补缺失依赖，不要覆盖原有 pom.xml。

application.yml

放到 src/main/resources/application.yml，修改桶名、Endpoint 和数据库地址。在运行环境中设置引用的环境变量，DEMO_PASSWORD 是本地演示用户的密码，使用 ASCII 字符即可。

公开读时 public-base-url 可换成已配置好 HTTPS 和回源的 CDN 域名。私有模式使用 SDK 生成的 GET 签名，本例不处理 CDN 私有鉴权。

OssDemoApplication.java

OssProperties.java

Java 17 的 record 可承载配置，不需要另外编写 getter、setter。

OssConfig.java

一个应用复用一个 OSS 客户端，Spring 关闭时释放连接。

DemoSecurityConfig.java

为使示例能独立运行，这里创建两个内存用户 10001、10002，密码均来自 DEMO_PASSWORD。通过 HTTP Basic 认证，保留默认 CSRF 防护。前端会先取得 CSRF token，再发 POST。用户 ID 从认证结果获取，不接受客户端任意指定。

实际项目应复用已有登录功能，不要复制这套演示用户。远程访问必须使用 HTTPS。

第二步：后端生成上传签名

对象键由后端生成，格式为 images/{用户ID}/{日期}/{UUID}.{后缀}。后缀来自允许的 MIME 类型，不使用客户端文件名拼接存储路径。

FileDtos.java

把简单请求、响应 record 放在同一个外部类中。

OssService.java

除了申请 PUT 签名，这个类还提供后续保存、读取流程需要的归属检查、元数据检查和访问地址生成。

setContentType() 把 Content-Type 纳入签名约束，浏览器 PUT 必须使用响应中的请求头。生成签名通常只在本地计算，不会创建对象，也不能证明 Bucket、权限配置正确。

这里的 5MB 检查发生在上传后，超限文件会被拒绝保存到数据库，但已经产生存储。需要在上传入口限制大小时，可进一步使用带大小条件的 POST Policy 等方案。元数据中的 Content-Type 仍是客户端声明，不能证明真实文件格式，正式业务按需要增加内容识别和审核。

第三步：前端直接上传图片

为了形成可直接运行的闭环，页面同时包含下一步的“保存对象键”和“获取访问地址”。先放好页面，再补齐后面的数据库与接口即可运行。

把下面完整页面保存为 src/main/resources/static/index.html。前后端同源，填写演示账号与 DEMO_PASSWORD 后上传。

PUT 请求体直接传 File，不要包成 FormData。OSS 请求使用单独的 fetch，不携带应用 Authorization、CSRF token 或应用 Cookie。PUT 的 Content-Type 必须与签名一致。

只有 PUT 成功后才提交保存接口。如果上传成功但保存失败，可以用页面保留的对象键重试 POST /api/files/images，不必立即重新上传。

第四步：保存对象键到数据库

建表 SQL

在 MySQL 手动执行一次。对象键使用区分大小写的排序规则，符合 OSS 对象键区分大小写的语义。

表中保存 objectKey、归属和元数据，不保存临时上传、读取签名。本例认证用户名是数字 ID；接入其他用户体系时应保证稳定标识符合目录格式和数据库长度。

ImageRepository.java

SQL 使用参数绑定。相同对象键重复提交时保留原记录，避免一次上传创建多行数据。

FileController.java

这里把四个接口完整放在一个 Controller 中：获取 CSRF token、申请上传签名、保存上传结果、获取图片地址。

前端不能直接传 userId 决定归属。签名、保存、读取都从认证身份获取当前用户；访问接口在生成私有 GET 签名前查数据库归属。

本例只有通用图片表。接入头像、文章配图等功能时，可以把对象键关联到业务记录，并按业务权限决定谁有权读取。

本例对象键由安全字符构成，可以直接拼接。任意中文、空格等对象键应正确处理 URL 路径编码，不能对完整路径直接使用表单参数编码。

私有模式下，OssService.accessUrl() 返回 300 秒有效的 GET 签名地址。签名过期后重新调用访问接口，无需重新上传；浏览器已经下载的图片不会因为签名过期自动消失。拿到签名的人在有效期内可以使用它，不应把签名 URL 当作秘密之外的永久文件标识。

不要保存 GET 签名或 PUT 签名，也不要用 putUrl.split(“?”)[0] 推导正式公开地址。公开地址的生成结果不代表文件存在，必须先确认上传成功。

示例边界

上面代码包含完整的签名、直传、落库和读取链路，未加入配额、真实内容审核、孤儿对象清理。

PUT 签名不是一次性令牌，在有效期内可以重复上传同一个对象键。元数据检查只反映检查时刻，之后对象仍可能被覆盖。需要审核或不可变文件的业务应增加上传状态管理、禁止覆盖或复制到独立正式对象，并对正式对象进行校验。

MySQL 事务不能回滚 OSS 上传、复制。上传后用户放弃、保存失败或文件超限都会留下孤儿对象，应通过上传记录和补偿任务清理。本例 images/ 下也有正式绑定的对象，不能直接设置删除整个前缀的短期生命周期。

实际验证顺序

  1. 创建表，配置环境变量和 OSS CORS，在示例工程运行 mvn spring-boot:run。
  2. 打开 http://localhost:8080/，使用 10001 和配置的演示密码上传图片。
  3. 浏览器 Network 中依次检查 csrf、presign、OSS PUT、images、access-url 请求；OSS PUT 不应带应用 Authorization。
  4. 查看 OSS 对象及 uploaded_image，确认数据库保存对象键。
  5. 刷新页面，填写已保存对象键，点击获取访问地址，确认不重传也能读取。
  6. 改用 10002，提交或读取 10001 的对象键，确认归属检查拒绝请求。
  7. 私有 GET 签名过期后重新申请；公开模式同时验证配置域名和桶读取权限。

401 检查登录信息；应用 POST 的 403 检查 CSRF token 和会话 Cookie；OSS 403 检查签名过期、请求头、地域和 RAM 权限。浏览器 CORS 错误检查 OSS 规则；对象不存在则检查 PUT 是否成功、对象键是否一致。

这些步骤用于在自己的环境验证，实际连通需要有效的 OSS 配置和 MySQL 服务。

雀跃已有 OssProperties、OssConfig、OssStorageService、StorageController 和 JWT 登录体系，不需要复制整套示例创建第二套 Bean。

环节 商品图片 商铺图片
申请签名 POST /storage/presign/product-image POST /storage/presign/shop-image
临时对象键 unconfirmed/product/{申请人ID}/images/… unconfirmed/shop/{申请人ID}/images/…
前端直传 storageService.putObject(putUrl, file, headers) 同左
申请保存 images 保存响应中的规范 publicUrl，多张以逗号分隔 同左
审核复制后 products/product/{申请人ID}/images/… shops/shop/{申请人ID}/images/…

通用教程保存 objectKey，雀跃当前申请接口保存规范 URL，这是现有接口设计的差异。本次修改文档不会迁移雀跃数据或修改接口。

商品审核调用已有方法：

商铺将最后一个参数改为 “shop”。必须传申请人的 ID，不能传管理员 ID。confirmImages 是项目方法，不是 SDK 自带方法；它对临时地址校验可信域名、场景和申请人目录，再通过 copyObject 复制到正式目录，返回正式地址。当前实现对不含 /unconfirmed/ 的地址保留原有行为，并不是对所有正式地址重新校验归属。

审核后转正用来区分“用户已上传、尚未通过业务审核”与“正式业务正在使用”的文件。申请被放弃或拒绝时便于清理临时文件，正式记录也不会继续依赖可能被生命周期删除的临时目录。目录名本身不提供访问控制，也不能代替内容审核；临时目录如果公开可读，未通过审核的文件仍可能通过 URL 访问。

审核通过时把正式地址写入商品或商铺及申请记录，申请状态与 images 一起通过 approve 更新，避免旧对象再次回写覆盖审核状态。OSS 复制不受数据库事务控制，回滚不会自动删除已复制对象，需要可重复的目标键及失败补偿；临时目录保留期应覆盖正常审核等待时间。
