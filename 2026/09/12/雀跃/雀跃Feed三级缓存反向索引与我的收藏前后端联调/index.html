一、前端功能和存在的意义

1. 公共 Feed

前端展示已经发布的博客，排序规则是发布时间倒序，同一发布时间再按博客 ID 倒序。它的意义是让用户优先看到新发布内容，而不是把首页结果固定成热门排序。

前端只负责：

  • 展示博客标题、摘要、图片、作者、发布时间和计数；
  • 到达页面底部时请求下一页；
  • 使用博客 ID 作为列表唯一标识，避免同一博客重复渲染；
  • 接收后端返回的实时点赞数、收藏数和当前用户状态。

三级缓存、小时槽和反向索引都在后端完成，前端不需要拼接 Redis Key，也不能直接操作缓存。

2. 点赞和收藏

前端点击按钮后调用对应接口，使用响应中的 active 和 count 更新按钮状态和数字。这样数字以 Redis 的实时逻辑计数为准，不依赖前端自己加一或减一。

changed=false 表示目标状态本来就已经存在，例如重复点赞或重复取消收藏。前端仍然可以使用返回的最终状态刷新界面，但不能再次累加计数。

3. 我的收藏

前端在个人主页提供“我的收藏”列表，按最近收藏关系的更新时间倒序展示已收藏且仍然发布的博客。它的意义是把“收藏关系”转化为用户可浏览的内容列表，而不是只在博客卡片上显示一个收藏数字。

前端需要处理以下状态：

  • 首次进入时显示加载状态；
  • 没有收藏或页码超出范围时显示空状态；
  • 使用 hasMore 判断是否继续请求下一页；
  • 取消收藏成功后，从当前列表移除该博客；
  • 博客已经被作者删除或改成草稿时，接受后端过滤后的结果，不把它当成网络错误。

4. 内容更新和删除

前端保存已发布博客为草稿、删除博客后，应立即从当前页面列表移除或刷新当前页面。后端会负责双删和反向索引清理，前端不需要等待 Redis TTL 到期。

3.2 后端完整调用链

各方法职责如下：

方法 被谁调用 作用
BlogController.queryHotBlog HTTP GET /blog/hot 读取页码、从 JWT 取可选用户 ID，调用 Feed 服务并返回完整的 FeedPageResponse。
BlogFeedServiceImpl.getPublicFeed Controller 负责参数规范化、三级缓存读取、并发回源控制、数据库回源和最终组装。

assembleFromCache getPublicFeed 按 Redis ID List 读取博客 ID，再批量读取 feed:item:{blogId} 并恢复页面。
singleFlight getPublicFeed 对同一 Redis 页面 Key 的并发回源加锁，避免多个请求同时查询数据库。
BlogMapper.selectHotFeed getPublicFeed 从 MySQL 查询 status=1 的博客，按 publish_time DESC, id DESC 排序。多查一条用于判断是否还有下一页。
mapRowsToItems getPublicFeed 把数据库行转换成不带当前用户状态的 FeedItemResponse。
writeCaches getPublicFeed 写 Redis ID List、hasMore、博客片段、页面登记表和反向索引。
enrich 缓存命中或回源后 用实时计数、Bitmap 用户状态和关注状态覆盖共享缓存中的用户态字段。
readCounts enrich 优先调用 CounterService.getCountsBatch 读取 Redis 逻辑计数，失败时回退 MySQL 检查点字段。
readFlags enrich 调用 BitmapStateReader.getFlagsBatch 读取当前用户点赞/收藏状态。
readFollowed enrich 调用 FollowStateService.getBatch 读取当前用户对作者的关注状态。

enrich 不能把 isLike、faved 和 followed 写进公共共享页面缓存，否则一个用户的状态可能被其他用户读到。

3.3 后端缓存 Key

层级 Key 作用
Caffeine feed:public:{size}:{page}:v1 当前 JVM 的本地页面对象；不带小时槽。
Redis 页面 ID feed:public:ids:{size}:{hourSlot}:{page} 保存页面博客 ID 顺序。
Redis hasMore feed:public:ids:{size}:{hourSlot}:{page}:hasMore 保存页面是否有下一页。
Redis 博客片段 feed:item:{blogId} 保存博客的公共基础字段。
页面登记表 feed:public:pages:{hourSlot} 登记该小时槽已经生成过的本地页面 Key。
反向索引 feed:public:index:{blogId}:{hourSlot} 保存包含指定博客的本地页面 Key。

页面 ID、登记表和反向索引的 TTL 约为 60～90 秒随机值；hasMore 的 TTL 约为 10～20 秒；博客片段使用约 10 分钟 TTL。TTL 是兜底机制，内容更新时优先依赖反向索引定向清理本地页面。

七、三级缓存和反向索引的后端职责

7.1 读取时谁调用谁

Controller 不直接操作 Redis 或 Mapper。这样做的意义是把分页、缓存、回源并发控制和用户态组装集中在 BlogFeedServiceImpl，避免不同接口各自实现一套缓存规则。

7.2 写缓存时谁调用谁

本地 Key 不带小时槽，保证同一应用实例的页缓存只有一个定位方式；Redis 页面 Key 带小时槽，让新时间段自然形成新页面集合。

7.3 更新时谁调用谁

反向索引的意义是把“博客 ID”反查为“受影响的本地页面 Key”，从而只删除包含该博客的页面，而不是删除所有用户共享页面。

8.2 方法职责

方法 作用
CounterCheckpointJob.checkpoint 定时扫描发生过计数变化的博客，控制每轮处理数量。
syncOne 读取某博客的 Redis 实时逻辑计数并尝试写入 MySQL。数据库失败时保留 dirty Key，等待下一轮重试。
CounterService.getCounts 从 Redis SDS/聚合桶读取逻辑计数，结构异常时依据 Bitmap 分片重建。
BlogMapper.updateCounterCheckpoint 将 Redis 当前计数写入 tb_blog.liked 和 tb_blog.favorites，形成持久化检查点。
dirtyConfirmScript 比较开始同步时的 dirty 版本；同步期间如果又发生新操作，则不删除新的 dirty 状态。

数据库检查点不是点赞和收藏的实时主读路径。公共 Feed 的 enrich 首先读 Redis；只有 Redis 计数服务异常时，readCounts 才回退到 MySQL 检查点字段。因此检查点的主要作用是：

  1. 持久化 Redis 中的最终计数；
  2. Redis 数据丢失或重建时提供可用的数据库基线；
  3. 让博客表中的统计字段能够用于后台查询、报表和降级读取；
  4. 通过 dirty 版本避免把同步期间的新操作错误地标记为已处理。

顺序 操作 重点观察
1 请求 GET /blog/hot?current=1 首次应走数据库回源，日志出现 source=db。
2 再次请求同页 应命中 source=local 或 source=3tier。
3 查看 Redis 应出现 ID List、hasMore、feed:item、页面登记表和反向索引。
4 修改已发布博客为草稿 更新前后各执行一次定向失效，旧页面不再长期保留。
5 删除博客 status=2，并执行双删。
6 点赞、重复点赞、取消点赞 检查 active、changed 和 count 是否符合幂等语义。
7 收藏博客 检查关系表 state=1、Bitmap、聚合桶和 dirty Key。
8 请求 GET /blog/of/myfavs?current=1 检查关系表分页、已发布过滤、收藏顺序和 hasMore。
9 取消收藏后再次请求收藏页 观察当前实现的 TTL 延迟，以及是否需要补用户页面定向失效。
10 等待检查点任务执行 检查 tb_blog.liked、tb_blog.favorites 是否被更新。

十、当前代码边界

  1. 公共 Feed 使用最新发布时间排序，不是 Redis ZSET 热榜；Redis 这里保存的是页面 ID 顺序，不负责热门排序。
  2. 新博客发布当前不主动删除公共 Feed 页面，因此不能保证已缓存第一页立即出现新博客。
  3. 收藏关系使用软删除；已取消收藏的行保留在关系表中，查询只取 state=1。
  4. 收藏状态变化当前没有主动清理用户收藏页缓存，存在短 TTL 内的旧列表；这不影响关系表最终状态，但会影响立即可见性。
  5. 点赞当前没有写点赞关系表，因此后续要实现“我点赞过的博客”时，还需要把点赞分支统一为关系表事实 + Redis 高速状态的模式。
  6. feedPublicCache 和 feedMineCache 是不同的 Caffeine Bean；构造注入时应确认 feedMineCache 使用正确的限定名，避免同泛型 Bean 注入歧义。
