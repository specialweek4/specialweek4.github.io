一、改造目标

本次改造包含三部分：

  1. 公共 Feed 从原来的热门排序改为按 publish_time DESC, id DESC 展示最新发布内容。
  2. 使用 Caffeine + Redis 页面 ID 列表 + Redis 博客片段组成三级缓存，并用博客到页面的反向索引进行定向失效。
  3. 使用 tb_blog_favorite 关系表保存收藏事实，新增“我的收藏”分页接口。

5.1 singleFlight 的作用

多个请求同时访问同一个未缓存页面时，只允许一个线程回源数据库，其他线程等待同一个锁对象：

锁 Key 使用 Redis idsKey，因此不同小时槽、不同分页不会共用同一个回源锁。

5.2 enrich() 为什么不能放进共享页面缓存

enrich() 会根据当前用户读取：

  • CounterService.getCountsBatch()：实时点赞数、收藏数；
  • BitmapStateReader.getFlagsBatch()：当前用户是否点赞、收藏；
  • FollowStateService.getBatch()：当前用户是否关注作者。

因此共享缓存只保存公共基础字段。若把 isLike 或 faved 写入公共页面缓存，用户 A 的状态可能被用户 B 看到。

十一、当前实现的边界

以下行为是当前代码的真实边界，联调时应明确：

  1. /blog/hot Controller 当前返回 feed.items()，客户端拿不到 hasMore；如果前端采用分页加载，应改为返回完整 FeedPageResponse。
  2. selectFeedByIds() 使用 IN 查询，数据库不保证顺序；若要求严格按最近收藏排序，需要按关系表 ID 顺序在 Java 重排。
  3. 收藏关系 ID 为空时，Service 应在调用批量博客查询前直接返回空页，避免生成空 IN 条件。
  4. 收藏或取消收藏后，应清理对应用户的 feedMineCache 和 Redis feed:mine:*，否则会出现短暂旧列表。
  5. 公共 Feed 的反向索引当前主要失效本地页面引用；Redis 页面/片段主要依赖 TTL 兜底。
  6. BlogFeedServiceImpl 构造函数中 feedPublicCache 使用了 @Qualifier("feedPublicCache")，但 feedMineCache 当前没有使用 @Qualifier("feedMineCache")。项目同时定义了两个相同泛型的 Caffeine Bean，启动时可能出现 Bean 注入歧义；联调前应确认启动日志，必要时给第二个参数补上限定名。

这些边界不影响理解三级缓存和收藏链路，但会影响严格一致性和异常场景联调。
