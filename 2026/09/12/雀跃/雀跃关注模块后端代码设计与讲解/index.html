雀跃关注模块后端代码设计与讲解

发表于2026-09-12|更新于2026-09-21|雀跃

雀跃关注模块后端代码设计与讲解

一、设计目标

关注模块需要解决四件事：

  1. 在 MySQL 中保存当前真实的关注关系；
  2. 防止重复关注、重复取消导致计数重复增加或减少；
  3. 使用 Redis 快速读取关注数和粉丝数；
  4. 为博客详情、博客列表和共同关注提供关系查询。

本设计仿照知光的用户计数方案，同时保留 following 和 follower 两张伪从表，为后续引入 Kafka、Canal 或 Outbox 预留结构。当前阶段不启动消息队列和 Binlog 消费，关注请求在同一个 MySQL 事务中同步写入主表和两张伪从表，事务提交成功后立即用 Redis Lua 修改用户计数。

Redis 计数和列表都是查询加速层，MySQL 关系表是最终事实。Redis 丢失或计数异常时，可以根据 tb_follow、following 和 follower 重新构建。

二、整体架构

这里的“同步写”指 Redis 计数更新在当前请求中执行，不经过消息队列。Redis 更新放在数据库事务提交回调中，避免数据库回滚后缓存先显示成功状态。

tb_follow 是当前关系事实表；following 面向“我关注的人”查询，follower 面向“关注我的人”查询。现在三张表在同一个事务中同步写入，保证请求结束时三者一致。以后接入 Outbox、Kafka 或 Canal 时，只需停止 Service 中对伪从表的直接写入，改为由事件消费者根据 tb_follow 变更维护两张伪从表，查询接口和表结构不需要重新设计。

三、数据库关系表

3.1 tb_follow

字段含义：

字段 含义
user_id 发起关注的用户，也就是关注者
follow_user_id 被关注的用户
create_time 建立关注关系的时间

例如用户 10 关注用户 20，保存为 user_id = 10, follow_user_id = 20。uk_follow_user_target 是幂等的关键，同一用户重复关注同一目标时最多只有一条关系记录。

取消关注采用物理删除：

当前模块只关心当前关系，不保留取消历史，因此不需要软删除字段。

3.2 following 伪从表

它保存“谁关注了谁”的正向查询视图：from_user_id 是关注者，to_user_id 是被关注者。following 的主键和唯一键与关系方向绑定，便于按用户分页查询关注列表。

3.3 follower 伪从表

follower 保存反向查询视图：to_user_id 是被关注者，from_user_id 是粉丝。它与 following 保存同一条关系，但字段顺序针对粉丝列表建立索引。

当前 tb_follow 采用物理删除，而伪从表保留 rel_status 字段，是为了兼容未来的事件消费模型。当前同步取消关注时可以直接删除伪从表记录，也可以更新为 rel_status=0；建议和主表保持同样的物理删除语义。未来切换到 Kafka、Canal 或 Outbox 时，可以改为更新状态而无需立即迁移表结构。

3.4 三张表的写入约定

当前同步写入：

所有操作处于同一个 @Transactional 事务中，任意一张表写入失败，三张表一起回滚。tb_follow 的唯一索引仍然负责判断首次关注；只有主表实际发生变化时，才允许写伪从表和更新 Redis 计数。

四、Redis 用户计数结构

4.1 Key 和二进制布局

用户计数 Key 与知光一致：

Value 不是字符串数字，而是固定 20 字节的二进制字符串：

字节范围 段位 计数名称 当前用途
0-3 1 followings 用户关注的人数
4-7 2 followers 用户拥有的粉丝数
8-11 3 posts 用户发布的博客数，预留
12-15 4 likedPosts 用户发布内容获得的赞数，预留
16-19 5 favedPosts 用户发布内容获得的收藏数，预留

每个段位占 4 字节，使用大端序无符号 32 位整数。关注模块只修改前两个段位，但保留 5 段结构可以与知光的用户计数模型保持一致。

例如用户 10 当前关注 3 人、拥有 8 个粉丝，其 Value 的逻辑内容是第 1 段为 3、第 2 段为 8，第 3 至第 5 段保留原值或为 0。

固定结构可以一次读取用户全部计数，并通过字节偏移定位字段。Lua 在 Redis 内部完成读取、修改和写回，避免并发请求互相覆盖。

5.7 ZSet 与伪从表的职责

当前同步阶段，关注事务提交后同时维护伪从表和 ZSet。未来接入 Outbox、Kafka 或 Canal 时，事件消费者可以同时执行数据库伪从表更新和 ZSet ZADD/ZREM，查询接口无需改变。ZSet 丢失时不要从 ZSet 反向恢复数据库，应以 tb_follow 为主、以伪从表为辅助回源。

九、关注状态缓存

计数缓存和“当前用户是否关注目标用户”是两个不同问题。

值为 1（已关注）或 0（未关注）。查询流程是：先 Redis GET，未命中时执行 SELECT EXISTS 查询 tb_follow，再把结果写回并设置约 10 至 12 分钟随机 TTL。

关注或取消关注的数据库事务提交后，同时更新这个状态 Key。关注状态可以短 TTL，ucnt:{userId} 计数则依靠同步增量和校验重建维护，不能用关注状态 Key 代替计数。

博客列表批量读取作者状态时，使用 Redis Pipeline；缺失项通过一条 IN 查询回源，并把实际关注的 ID 转成 Set 后回填 1/0，避免 N 次数据库查询。

十一、并发、幂等和一致性

10.1 并发关注

10.2 并发取消

10.3 关注和取消同时发生

最终状态由两个 MySQL 事务的提交顺序决定。每次 Redis 增减都以实际 SQL 影响行数为条件，因此不会因为重复请求重复增减。前端应在请求完成前暂时禁用按钮，避免旧响应覆盖新状态。

10.4 一致性边界

数据库提交成功而 Redis 更新失败时，关系不会回滚。服务应删除计数 Key 或触发重建；下一次读取发现 Key 缺失后从数据库恢复。该方案是数据库强一致、Redis 最终一致，但更新动作在当前请求中同步发起。

十二、当前暂不启用但保留的扩展设计

当前阶段不实现：

  • Kafka 关注事件和计数消费者；
  • Canal 或 Debezium Binlog 监听；
  • Outbox 表和事件重放；
  • following/follower 两张伪从表不会舍弃，当前采用同步双写；
  • Kafka、Canal、Outbox 驱动的异步伪从同步暂不启用；
  • 通过消息异步更新 Redis 计数暂不启用；
  • 关注 Feed 的写扩散收件箱；
  • 共同关注的独立 Redis 列表缓存；关注列表和粉丝列表使用 uf:flws:{userId}、uf:fans:{userId} ZSet。

这些异步方案适合关注规模很大、需要跨服务解耦或允许更长最终一致窗口的场景。雀跃当前保留三张关系表，但使用单体后端事务同步双写和同步写 Redis。未来演进路径如下：

切换到异步模式时，必须先完成历史数据校对，再停止伪从表同步双写，避免同步写和消费者同时修改同一行造成重复处理。

十三、实现检查清单

  1. tb_follow 存在 (user_id, follow_user_id) 唯一索引；
  2. following 和 follower 存在对应唯一索引和分页索引；
  3. 关注和取消关注方法使用 @Transactional，三张关系表同事务写入；
  4. 只有主表 SQL 影响行数为 1 时才写伪从表和更新计数；
  5. 数据库提交前不修改 Redis；
  6. Redis 计数 Key 使用 ucnt:{userId}，Value 固定为 20 字节；
  7. 第 1 段是关注数，第 2 段是粉丝数，使用大端序；
  8. 增减操作通过 Lua 原子执行，并把负数归零；
  9. Redis Key 缺失或长度异常时可以从 tb_follow 重建；
  10. ZSet 使用 uf:flws:{userId} 和 uf:fans:{userId}，member 为用户 ID，score 为关系创建时间戳；
  11. ZSet 未命中时从 following、follower 回源，并设置有限 TTL；
  12. 关注状态使用 qy:state:follow:{userId}:{targetUserId}，不能读取 ucnt 判断单个关系；
  13. 定期抽样比较 Redis 与数据库，发现漂移后加锁重建；
  14. 用户资料和头像从当前 tb_user 读取，不重新引入 tb_user_info；
  15. 将来接入 Kafka、Canal 或 Outbox 时，先保证事件幂等、历史校对和消费者重试，再切换伪从表和 ZSet 的维护方式。
