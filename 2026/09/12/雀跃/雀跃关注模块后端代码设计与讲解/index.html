雀跃关注模块后端代码设计与讲解

本文对应当前 D:\queping\queyue_be-main 后端代码，讲解关注关系、关注状态缓存、粉丝与关注计数、共同关注和关注动态 Feed 的实现。

本文只解释当前后端代码，不修改源代码。接口、方法名称和行为均以当前项目为准。

一、关注模块解决什么问题

关注模块不只是完成“点击关注”这一个动作，它同时承担四类职责：

  1. 在 MySQL 中保存用户之间真实的关注关系；
  2. 幂等地维护用户的关注数和粉丝数；
  3. 在 Redis 中缓存当前用户是否关注某个作者，减少列表页反复查询数据库；
  4. 根据关注关系查询关注用户发布的博客，并通过滚动分页返回关注动态。

八、为什么在事务提交后更新 Redis

8.1 调用关系

核心逻辑：

如果在事务提交前写 Redis，之后 MySQL 回滚，就会出现 Redis 显示“已关注”，但数据库没有关注关系。提交后更新可以避免缓存先于最终事实发生变化。

当方法不在事务同步环境中运行时，代码会直接更新 Redis，保证该工具方法仍可工作。

8.2 一致性模型

当前设计中：

Redis 写入失败不会改变已经提交的 MySQL 关系。旧缓存最多保留到 TTL 到期，之后重新从数据库加载。因此这里采用的是“MySQL 强事实 + Redis 最终一致缓存”。

十二、关注状态如何进入博客响应

关注模块不仅被关注接口调用，也会被博客详情和 Feed 调用。

12.1 博客详情

因此登录用户查看其他作者的博客详情时，可以直接得到 followed 字段并决定按钮状态。

12.2 公共 Feed 和我的收藏

共享 Feed 缓存不保存某个用户专属的 followed。每次返回前才根据当前登录用户批量补充，避免用户 A 的关注状态被用户 B 看到。

12.3 关注动态

关注动态中的作者理论上都是当前用户已经关注的人，因此 followed 通常为 true。仍然批量读取状态，可以保持不同博客列表响应结构一致。

十四、并发和幂等行为

14.1 多次并发关注

数据库唯一索引决定最多只有一个插入成功：

因此同一用户快速点击关注不会造成多条关系或重复增加粉丝数。

14.2 多次并发取消

只有第一个成功删除关系的请求返回 deleted=1，后续请求返回 0，因此只有一次统计减少。

14.3 关注和取消同时发生

关注与取消是两个独立事务。最终结果由数据库实际执行顺序决定，每次统计变化又以关系语句的影响行数为依据。对于单用户界面，前端仍应在请求处理中暂时禁用按钮，避免响应乱序把较旧状态覆盖到界面上。

十五、当前实现的边界和注意事项

15.1 关注动态的同时间戳分页存在跳过风险

当前 Service 计算了相同时间的 offset，但 SQL 条件使用：

严格小于已经排除了所有等于上一页 minTime 的博客，随后再使用 LIMIT offset, size，可能继续跳过下一批更早的数据。也就是说，当前 offset 的设计和 SQL 条件没有完全配套。

常见修正方向有两种：

  1. 保留同时间偏移语义，把时间条件调整为包含 maxTime，再用 offset 跳过已经读取的同时间记录；
  2. 改为 (publish_time, id) 组合游标，下一页使用严格的小于条件，不再使用 offset。

组合游标在数据量较大时更稳定，但需要接口额外返回末条博客 ID。

15.2 关注动态没有写扩散

当前查询是读扩散：每次请求根据 tb_follow 找作者，再从 tb_blog 查询内容。它实现简单且关系变化立即生效，但关注人数和博客数据量很大时，SQL 压力会增加。

当前代码没有在发布博客时把博客 ID 推送到每个粉丝的 Redis 收件箱，也没有 Kafka Feed 事件。

15.3 关注关系采用物理删除

取消关注后关系行被删除，因此数据库不能直接保留历史关注、取消时间和操作次数。如果后续需要风控、推荐训练或关系历史审计，可以增加状态字段和更新时间，改成软删除；如果只关心当前关系，物理删除更简单。

15.4 Redis 是缓存，不是关系事实

qy:state:follow:* 带 TTL，不能用于恢复完整关注关系。MySQL tb_follow 才是最终事实。Redis 丢失后，状态可以通过 Mapper 查询重新回填。

15.5 缓存更新失败的短暂不一致

数据库提交后才写 Redis。如果提交后 Redis 不可用，数据库关系已经正确，但旧缓存可能暂时存在，直到 TTL 到期。若要进一步缩短不一致窗口，可以在失败时删除缓存、记录重试事件，或通过 Outbox/Kafka 异步修复。

15.6 orNot 对不存在目标的行为

关注和取消关注会调用 requireExistingTarget() 校验用户存在；单独查询 /follow/or/not/{id} 不做目标用户存在校验，不存在的目标通常返回 false。调用方不能把 false 理解为目标用户一定存在。

15.7 关注统计是派生数据

fans 和 followee 是为快速展示维护的统计字段，真实关系仍是 tb_follow。如果历史异常或手工修改数据库造成统计漂移，可以通过聚合 tb_follow 重新计算并校正。

15.8 数据库没有声明外键

当前 tb_follow 建表语句没有用户外键。业务层会在新增或取消前校验目标用户，但数据库本身不阻止绕过 Service 的直接写入，也不会在用户被删除时自动清理关系。
