商品收藏页的覆盖时机与用户收藏版本

商品收藏页的计数和用户状态覆盖方式与 Blog 的“我的收藏”一致：

读取来源 计数和用户状态如何处理 写入缓存
Caffeine 命中 直接返回已缓存的用户页面，不重新查询计数和状态 不重新写入
Redis 命中 覆盖最新收藏计数和当前用户收藏状态 将覆盖后的页面写入 Caffeine，Redis 原页面等待原 TTL 到期
MySQL 回源 查询收藏商品并覆盖最新收藏计数和当前用户收藏状态 将覆盖后的页面写入 Redis 和 Caffeine

空页仍使用较短 TTL。Caffeine 默认 10 秒，Redis 非空收藏页 30～49 秒、空页 10～20 秒；本地页面存活期间，其他用户操作带来的收藏计数变化会在下次 Redis 命中或数据库回源时体现。

商品收藏页只读取用户收藏版本 feed:product:myfavs:version:{uid}。当前用户收藏或取消收藏成功后递增该版本，只切换该用户的收藏页 Key。

收藏页完整 Key 为 feed:product:myfavs:{uid}:{version}:{size}:{page}。商品变更版本不参与收藏页和公共 Feed：商品下架后收藏页等待缓存自然过期，公共 Feed 仍根据反向索引定向失效。

商品变更版本仅用于详情，按商品 ID 分开存储为 product:detail:version:{productId}；详情 Key 为 product:detail:{productId}:v1:version:{version}。每次详情读取先从 Redis 读取版本，再查本地缓存；版本不存在时按 0 处理。ProductDetailService.invalidate(id) 先读取旧详情 Key，再执行 INCR，随后删除旧版本 Redis 和本地详情缓存。其他实例读取新版本后也不会命中旧版本详情。

当前 changeStatus() 在写库前和事务提交后均调用详情失效，因此上下架都会递增该商品详情版本，成功一次通常递增两次。详情版本不设置短 TTL，旧版本详情依靠原 TTL 回收。Redis 版本键应持久保存；若清空或丢失版本键，需要同时清理各实例详情本地缓存，避免版本回到 0 后复用旧快照。未来商品编辑也需接入详情失效；当前商铺资料修改尚未接入商品详情版本，仍等待快照过期。

二十、当前方案的边界

  1. 公共 Feed 使用页码 offset，不是游标快照；新商品插入期间继续翻页仍可能发生位移。前端按 ID 去重只能消除重复展示，不能恢复已经跳过的数据。
  2. “我的商品收藏”也使用 offset；前端采用保留取消卡片并补读最后一页缓解漏项。
  3. MySQL 收藏关系、Redis Bitmap/计数和版本号是跨存储写入。当前为同步实现，极端故障下需要补偿；以后可按博客计划引入 Outbox、Canal、Kafka。
  4. 多实例部署必须增加本地缓存失效广播。
  5. 商品关键词搜索暂未实现，未来使用 Elasticsearch 全文检索。
  6. Blog 作者资料和商品所属商铺资料采用快照缓存，资料更新后最多在详情 Redis 的 60～89 秒 TTL 内显示旧值；这是与知光相同的短暂最终一致策略。

21.8 验证和边界

  1. 连续请求同一用户同一游标：第二次不执行 selectFeedOfFollow；清理本地缓存再请求命中 Redis；基础页缓存失效后才回源 MySQL。
  2. 用户 A 和 B 请求同一游标不能串页，点赞/收藏状态每次覆盖；匿名请求仍由当前 SecurityConfig 返回 401。
  3. 至少准备超过两页、发布时间相同的博客；依次使用响应的 minTime/offset 翻页，offset 应持续累计，不能卡在同一页或跳过同时间记录。
  4. 关注、取消关注成功后，旧用户版本的页面不可再次命中；删除或转草稿后，旧内容版本的页面不可再次命中。
  5. 版本键不设置短 TTL；页面依靠短 TTL 回收。Redis 重启后 UUID 版本不会复用仍在 JVM 中的旧页面。
  6. 时间戳加 offset 不是数据库快照。翻页期间删除同一时间分组中的记录仍可能引起位移；严格稳定分页需要升级为 (publishTime,id) 双字段游标并同步改前端。
  7. 数据库与 Redis 更新仍然不是一个事务；Redis 故障时需要重试/补偿，不能把上述版本机制当作分布式事务保证。

二十二、本次商品代码落地差异

商品代码已写入 D:\queping\queyue_be-main，前文商品示例中与下面条目冲突的部分以实际源码为准：

  • 商品详情只返回商品和商铺信息，移除了 createdBy/creatorName/creatorIcon，详情 SQL 不再连接 tb_user。Feed 保留原有兼容字段。
  • 上下架写操作在事务提交后执行第二次缓存失效；收藏计数检查点不修改 update_time，避免收藏操作改变 Feed 顺序。
  • 商品公共 ID 页与 Blog 一样使用 Redis List 普通命令回填：空页 LPUSH 空标记，非空页 RPUSH 商品 ID，再单独设置 TTL 和 hasMore，不再使用 Lua 原子替换。商品片段仍保留 10 分钟，反向索引仍保留 150 秒。
  • 商品收藏页与 Blog 我的收藏采用相同的计数和用户状态覆盖时机：Caffeine 命中直接返回；Redis 命中时覆盖后写入 Caffeine；数据库回源时覆盖后写入 Redis 和 Caffeine。缓存保存该用户的完整页面快照，公开商品过滤在分页 SQL 内完成。
  • 已下架商品仍允许取消收藏。收藏页只保留用户收藏版本 feed:product:myfavs:version:{uid}；商品变更版本改为 product:detail:version:{productId}，只用于商品详情，在 ProductDetailService.invalidate(id) 中递增。公共 Feed 不使用商品变更版本，继续按反向索引失效。
  • 商品公共 Feed 与 Blog 一样使用 ConcurrentHashMap 动态创建回源锁，锁内二次检查缓存，命中或回填成功路径中移除锁。商品详情仍使用固定锁数组。公共 Feed 多实例仍需广播失效；详情通过共享商品版本跳过旧快照。
  • 新增方法及改动方法只添加用途注释。数据库迁移文件为 src/main/resources/db/V5__product_feed_favorite.sql，需在数据库执行一次后再启动这些接口；本次未连接或修改运行中的数据库。

商品公共 Feed 与 Blog 对齐后的实现边界

商品公共 Feed 已按要求使用与 Blog 相同的动态 Map 锁和普通 Redis List 追加回填。这也保留了现有 Blog 的行为边界：已有请求等待旧锁时删除 Map 条目，后续请求可能创建另一把锁；ID 列表仍存在但条目缓存缺失时，再次回填可能追加重复 ID。当前实现不保证分布式互斥或原子页面替换，后续如需修正可同时调整两套 Feed。
