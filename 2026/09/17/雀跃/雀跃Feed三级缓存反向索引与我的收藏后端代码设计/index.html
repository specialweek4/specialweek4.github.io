雀跃 Feed 三级缓存、反向索引与我的收藏后端代码设计

BlogFeed和商品Feed的三级缓存，我的收藏和商品收藏页都差不多主要的一同如下：

对比项 Blog Feed 商品 Feed
数据范围 已发布博客 已上架商品，且商铺营业
排序 发布时间倒序 更新时间倒序
分页 页码、offset，多查一条判断 hasMore 相同
并发回源锁 ConcurrentHashMap 动态锁，锁内二次检查 相同
Redis 页面回填 普通 List 追加，单独设置过期时间 相同
搜索 当前公共 Feed 无关键词搜索 已移除，以后接 Elasticsearch
动态信息 点赞数、收藏数、点赞/收藏/关注状态 收藏数、收藏状态
状态覆盖时机 每次返回前，包括本地命中 相同
Caffeine 页面 TTL 15 秒 15 秒
Redis ID 页面 TTL 60～90 秒 60～90 秒
Redis 商品/博客条目 TTL 当前实际为 60～90 秒 10 分钟
反向索引 TTL 跟随页面，60～90 秒 150 秒
计数读取失败可降级 读取数据库 检查点没有同样的降级

Blog Feed：当前代码通过反向索引只清理本地页面，尚未删除 Redis ID 页面和博客条目，因此可能从 Redis 再次加载旧内容。而商品设计到金钱交易所以这里要定向清理本地页面、Redis ID 页面、hasMore 和商品碎片

来源 处理方式
Caffeine 命中 直接返回已缓存的用户页面
Redis 命中 重新覆盖计数和状态，再写入 Caffeine
MySQL 回源 覆盖计数和状态，再写入 Redis、Caffeine
差异 我的 Blog 收藏 商品收藏
用户版本 Key feed:myfavs:version:{uid} feed:product:myfavs:version:{uid}
动态字段 点赞、收藏、关注相关信息 收藏计数和状态
过滤不可见内容 先分页查收藏 ID，再过滤未发布博客 分页查 ID 时就过滤下架商品、非营业商铺
对分页的影响 已删除博客会占用分页名额，可能不足一页 下架商品不会占用分页名额

商品有一个商品变更版本号：**仅用于商品详情。**公共商品 Feed、商品收藏页都不使用它；商品收藏页只有用户收藏版本号。

设计亮点简介

  • 三级缓存：公共 Feed 按 Caffeine -> Redis -> MySQL 的顺序读取。Caffeine 保存本机完整页面，Redis 使用“ID 页 + Blog 片段”组装页面，只有缓存无法组成完整结果时才回源数据库；回源过程通过 SingleFlight 和锁内二次检查抑制同一页面的并发查询。
  • 反向索引：Redis 使用 blogId -> 本地页面 Key 集合 记录一篇 Blog 出现在哪些 Caffeine 页面中。Blog 更新或删除时，只清理包含该 Blog 的本地页，不需要清空全部 Feed 页面。
  • 小时槽：Feed 的 Redis ID 页、页面登记表和反向索引按当前小时分槽。旧槽随 TTL 自然淘汰，失效时只检查当前槽和上一小时槽，既覆盖跨小时存活的缓存，又避免索引集合持续膨胀；Caffeine 本地页面 Key 不携带小时槽。
  • 我的收藏：MySQL 关系表保存用户收藏事实，Bitmap 和聚合计数承担高速状态判断与计数。收藏列表通过关系表关联 Blog 查询，返回前再补充实时计数和当前用户状态。
  • 版本号失效：每个用户拥有独立的 feed:myfavs:version:{uid}。收藏关系真正发生变化后递增版本号，后续请求直接切换到新版本缓存空间，无需扫描和逐页删除旧收藏缓存，旧版本由 TTL 自动回收。
  • Blog 详情：详情按 Caffeine -> Redis -> MySQL 联表查询 读取。缓存只保存正文、封面和作者快照等基础数据，点赞数、收藏数以及当前用户是否点赞或收藏由 enrich() 在返回前覆盖，从而避免动态状态长期滞留在详情缓存中。
  • 数据库检查点：点赞数和收藏数先在 Redis 中实时更新，并通过 dirty 版本标记变化；定时任务读取实时计数写回 tb_blog。写库后只有 dirty 版本没有再次变化才清除脏标记，兼顾持久化、故障恢复和同步期间的新操作。
  • 还有一个页面登记表存储的是所有的缓存页面。

Redis 页面组装方法

方法内部：

  • range(idsKey, 0, size-1) 按顺序读取当前页 Blog ID；
  • EMPTY_MARK 的值是 __empty__，用于缓存空页；
  • ITEM_PREFIX + id 生成 feed:item:{blogId}；
  • multiGet() 一次批量读取当前页全部 Blog 片段；

  • hasMore Key 已过期时，以 idList.size()==size 临时推断是否可能有下一页。

锁内二次检查和数据库回源

这段代码中：

  • 获得锁后重新调用 assembleFromCache()，因为等待锁期间前一个线程可能已经回填；

Feed 缓存回填

writeCaches() 写入四组数据：

  1. idsKey：当前页的有序 Blog ID List；
  2. hasMoreKey：是否还有下一页；
  3. feed:item:{id}：每篇 Blog 的公共片段；
  4. 页面登记表和反向索引。

随机 TTL 可以降低大量 Key 同时过期造成的缓存雪崩。当前 Blog 片段实际也使用 pageTTL，虽然类中另有 ITEM_TTL=10分钟 常量，但这段代码没有使用它。

实时数据覆盖

  • readCounts() 调用 CounterService.getCountsBatch() 批量读取点赞数和收藏数，异常时降级使用 tb_blog 的检查点值；
  • readFlags() 调用 Bitmap 批量读取当前用户是否点赞、收藏；
  • readFollowed() 批量读取当前用户是否关注作者；
  • 未登录时用户态 Map 为空，最终三个布尔字段都是 false；
  • enrich() 创建新的 DTO，不修改缓存中的公共基础对象。

Blog 详情三级缓存

Blog 详情使用独立缓存，不复用 feed:item:{blogId}。Feed 片段只服务列表卡片，详情还包含正文 URL、权限字段和完整作者快照。

共享缓存只保存与访问者无关的基础详情。liked、favorites、isLike、faved、followed 在返回前重新计算，避免用户状态互相污染。

  • 五个计数和用户状态字段在基础快照中先使用零值，enrich() 返回最终值。

详情三级读取和数据库回源

这段代码依次完成：

  1. detailKey() 生成 blog:detail:{blogId}:v1；
  2. localCache.getIfPresent() 查询本机 Caffeine；
  3. redis.opsForValue().get() 查询 Redis 基础详情；
  4. deserialize() 把 JSON 转回 BlogDetailResponse；
  5. 两级缓存都未命中时，通过 singleFlight 合并当前 JVM 的并发回源；
  6. 锁内再次检查两级缓存，防止等待锁期间其他线程已经完成回填；
  7. selectDetailById() 联表查询 Blog 和作者；
  8. Blog 不存在时缓存 __null__ 30～60 秒，防止相同无效 ID 持续穿透；
  9. 非公开内容只允许作者读取，并且不放入共享缓存；
  10. 已发布详情写入 Redis 和 Caffeine，返回前调用 enrich()。

finally 中的 singleFlight.remove(key, lock) 保证正常返回或抛出异常时都移除锁对象。

Redis 反序列化与坏值修复

  • Redis 没有值时返回 null，让上层继续回源；
  • JSON 无法解析时删除损坏 Key；
  • 删除后同一次请求会继续查询数据库并重新生成正确缓存。

基础详情组装

toBase() 只组装公共基础数据。计数先写为 0，用户态先写为 false，因此缓存值与当前访问者无关。

实时计数和用户状态覆盖

  • CounterService.getCounts() 读取 Redis 中的实时点赞数和收藏数；
  • BitmapStateReader.getFlagsBatch() 读取当前用户对该 Blog 的点赞位和收藏位；
  • FollowStateService.isFollowed() 读取当前用户是否关注作者；
  • 匿名请求的三个用户状态保持 false；
  • enrich() 返回新 DTO，不修改 Caffeine 或 Redis 中的基础对象。

Controller 调用详情服务

Controller 只负责取得 Blog ID 和当前用户 ID。缓存读取、权限检查、数据库回源和动态状态覆盖都由 BlogDetailService.detail() 完成。

详情缓存失效

详情缓存通过 Blog ID 可以直接定位，所以不需要 Feed 那样的反向索引。Blog 的正文、标题、封面、作者快照或状态发生变化时，数据库写入前后调用 invalidate()，分别清理 Redis 和当前实例的 Caffeine。

点赞、收藏和关注变化不删除详情基础缓存，因为 enrich() 每次返回前都会覆盖这些动态字段。

草稿首次发布前后删除详情 Key，可以清理之前对该 ID 形成的空值或旧状态；新发布本身不清空已有公共 Feed 页面。

作者昵称和头像属于详情基础快照，用户修改资料后可能在 Redis 60～89 秒 TTL 内显示旧值，缓存过期回源后更新。

数据库检查点

  • fixedDelay 表示上一次任务结束 30 秒后再次执行；
  • initialDelay 表示服务启动 15 秒后首次执行；
  • scanKeysOrEmpty() 使用 SCAN 分批读取 dirty:v1:*，不会使用阻塞式 KEYS；
  • dirty Key 格式为 dirty:v1:{entityType}:{entityId}；
  • 当前只处理 entityType=blog。

单条同步：

syncOne() 先记录 dirty 版本，再读取 Redis 逻辑计数并更新：

最后执行 dirtyConfirmScript。Lua 只有在 dirty Key 仍等于开始时读到的版本时才删除它；同步期间如果又有操作递增版本，脏标记会保留给下一轮。

总结

公共 Feed 用反向索引定位包含某篇 Blog 的本地页面；我的收藏用用户版本号切换缓存命名空间；Blog 详情通过 Caffeine、Redis 和 MySQL 联表查询组成三级缓存，并在返回前补充实时计数和当前用户状态。
