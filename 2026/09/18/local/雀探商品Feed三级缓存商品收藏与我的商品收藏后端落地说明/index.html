当前使用的商品 Feed Key

内容 Key 当前 TTL 或作用
Caffeine 公共页 feed:product:{size}:{page}:v1 配置默认 15 秒，最多 1000 条
Redis 商品 ID 页 feed:product:ids:{size}:{hourSlot}:{page} 60～90 秒
hasMore 标记 ID 页 Key 加 :hasMore 10～20 秒
商品基础片段 feed:product:item:{productId} 当前写入固定 10 分钟
页面登记表 feed:product:pages:{hourSlot} 150 秒，当前只写不读
商品反向索引 feed:product:index:{productId}:{hourSlot} 150 秒

hourSlot 是当前毫秒时间除以一小时的结果，只用于区分 Redis 页面。它不是一小时 TTL。登记表成员和商品反向索引成员都是 size:page，比如 10:2。

当前公共 Feed 的商品失效会删除当前实例的本地页、当前小时和上一小时反向索引对应的 Redis ID 页及 hasMore，并删除商品片段。它不会广播到其他实例的 Caffeine，也不会因为从下架改为上架而主动清空公共页；新上架内容需要等原有页面过期。

GET /product/list/{shopId} 目前仍然直接执行 queryPublicByShop()，没有使用商品 Feed 缓存。代码里删除旧的商铺列表 Key，不代表这个入口已经接入了 Feed 缓存。

当前实现的边界

  • 公共 Feed 的 Redis List 回填不是原子替换，可能出现重复 ID。
  • 商品 Feed 的页面登记表目前只写不读，主要失效依赖商品反向索引。
  • 多实例之间没有广播 Caffeine 失效。
  • 商铺资料变化没有完整触发商品详情和公共 Feed 的关联失效。
  • MySQL 收藏关系与 Redis Bitmap/计数跨存储失败时没有自动补偿。
  • Redis 整体丢失时，现有检查点任务不会从 tb_product_favorite 自动重建 Bitmap。
  • OSS 临时对象的删除依赖存储侧生命周期策略；当前代码提供了删除方法，但没有业务调用。
