关系模块

发表于2026-09-28|更新于2026-09-28|雀跃

整体的设计如下；

Redis的更新放在一个事务中，防止数据库回滚是污染花缓存, redis更新失败是直接删除缓存，不回滚数据。

Redis Key设计

Key 类型 内容 TTL
qy:rel:following:{userId} ZSET member=被关注用户 ID，score=关注时间毫秒 2 小时
qy:rel:followers:{userId} ZSET member=粉丝用户 ID，score=关注时间毫秒 2 小时
qy:rel:following:complete:{userId} String 当前 ZSET 已覆盖全部数据库记录 2 小时
qy:rel:followers:complete:{userId} String 当前 ZSET 已覆盖全部数据库记录 2 小时
qy:state:follow:{from}:{to} String 1 已关注，0 未关注 10~12 分钟
qy:ucnt:rel:{userId} String/SDS 8 字节，关注数和粉丝数各 4 字节 不过期
qy:ucnt:rel:check:{userId} String 抽样检查节流标志 300 秒
qy:lock:ucnt:rel:{userId} String 计数重建锁 5 秒

查用户关注了谁，就是qy:rel:following:{userId}，被谁关注了就查qy:rel:followers:{userId}

这个 complete 是一个标志，就是判断缓存中的数据是否完整，是用来判断整个Zset是否完整，不完整的话查询数据库回填。complete 写入就是当缓存未命中的时候，如果查询到数据库返回的数量小于n个说明数据库中的数据已经查完了，complete = 1 下次查询就不查数据库了直接返回空。

RelationCacheService

其中那个refillPrefix方法是填补他不是分页查询时，偏移量查询，当执行这个方法的时候一般是查到了Zset的最后或者是Zset不存在，但是数据库中可能还有几个没有同步的最新的几条数据，就看这个complete如果它为true就说明数据库有的数据ZSET中也有了。每次是读取min(need,1000)条数据，重建或者替换掉以前的ZSET。其实就是重建。

onRelationChanged这个方法他在关注成功和取消关注成功的时候执行，更新缓存中的关系（不是计数），他通过Lua脚本更新的是这三个缓存的关注Zset，被关注者的粉丝Zset，还有单个用户的关注状态缓存。

脚本中也维护了 complete 标示，如果标示一直是 1 的话因为再更新数据库的同时会执行ZADD，你增加一个关注成功后，ZSET依然是完整的所以 complete 依然为1所以这里这个刷新了complete的过期时间。更新失败会删除这些缓存，从新读取，保证一致性。当ZSET不存在的时候他不会创建ZSET而是返回失败，然后就会删除所有的关系缓存。但是这只是缓存更新失败数据库中的那一条数据已经写入成功了，下次来查询Zset的时候就会执行refillPrefix() 来重建Redis，保证了缓存和数据库数据的一致。
